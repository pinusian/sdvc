**설계 결정 (사용자 확인 없이 직접 판단, 근거 명시)**:
- **요청했을 때만 만든다.** 소개 페이지 대부분은 필요 없고, 매번 붙으면 유지보수
  프롬프트 토큰만 늘어난다(BL-018 이후 유지보수 프롬프트에는 이미 현재 파일
  전체가 실리므로, PWA 파일까지 매번 끼면 원가가 새는 방향이다).
- **아이콘은 SVG로만.** 모델은 PNG 같은 그림 파일을 직접 만들 수 없다. 이 한계를
  숨기지 않고 사용자에게 그대로 알리게 했다 — [P7-12]("안 되는 것은 조용히
  넘기지 않는다")와 같은 원칙.
- **"네이티브 앱이 되는 것은 아니다"를 지시문에 못 박았다.** PWA와 네이티브 앱을
  섞어 이해하면 사용자가 앱스토어 등록 같은 걸 기대하게 된다.

**어디까지 되고 어디부터 안 되는지**: 홈 화면에 아이콘이 생기고 오프라인에서도
핵심 화면이 열리는 것까지는 이 변경으로 된다. 앱스토어·플레이스토어 등록,
푸시 알림, 카메라 같은 기기 API 접근은 여전히 안 된다 — 그건 Swift·Kotlin 같은
완전히 다른 기술이 필요한 별개 제품이다.

> 회원가입·게시판(FR-020류)과 예약·주문·결제 처리는 이것과 다르다 — 산출물마다
> 격리된 백엔드가 새로 필요한 큰 작업이고, 결제 쪽은 법적 지위까지 걸린다.
> 두 항목 모두 지금 범위 밖으로 **유지**한다.

## Phase 11 — 산출물의 사용자(방문자) 계정 (2026-09-18 착수)

**맥락**: "독서활동" 프로젝트에 실제로 필요해진 것 — 한 산출물을 여러 사람이
쓰되, 각자 로그인해서 **자기 기록만** 쓰고 본다. 바로 위 경고문에서 "범위 밖"
이라 적었던 항목이지만, 이번엔 **개발자가 명시적으로 요청**해 정식 착수한다.

**용어**: 시스템관리자 — 개발자(교수) — 사용자(학생) 세 층. 앞의 둘은 이미
있는 `profiles.role`(admin/developer) 그대로이고, 이번에 **사용자** 층을
새로 만든다.

**설계 결정 (사용자 확정)**:
1. **DB는 새로 만들지 않는다** — 지금 쓰는 Supabase 그대로, 표만 추가(`site_users`·`site_records`). `project_id`로 격리, RLS 켜고 정책 없음(기존 표와 같은 원칙).
2. **AI 기능이 필요하면 사용자 본인의 API 키로, 본인이 과금한다.** Story-Doing이 했던 "브라우저가 직접 호출"(BL-024에서 지적한 보안 허점 — 개발자도구에 키가 그대로 보임)은 반복하지 않는다. 서버가 사용자 본인의 **암호화 저장된** 키를 대신 써서 호출한다.
3. **선생님 = 개발자**(기본). 다른 사람일 수도 있으나, 별도 말 없으면 이 매핑으로 간다.
4. **개발자 관리 탭에서 사용자 차단 + 프로젝트 로그인 켜기/끄기** 가능하게 — 기존 `profiles.suspended_at`·`projects.blocked_at` 패턴을 그대로 재사용.

### [P11-4] 완료 — 사용자 API 키 등록 + AI 요약 프록시

- **Story-Doing의 실수(BL-024)를 정반대로 고쳤다**: 그쪽은 브라우저가 사용자 키로 Claude를 직접 불러 개발자도구 네트워크 탭에 키가 그대로 보였다. 이번엔 **서버**(`src/lib/site-accounts/ai-proxy.ts`)가 그 사용자의 암호화 저장된 키를 대신 써서 부른다 — 키가 브라우저에 한 번도 노출되지 않는다. 모델은 같은 이유로 `claude-sonnet-5`(날짜 박힌 스냅샷 금지).
- **키 등록은 쓰기 전용**(`POST /api/site/[slug]/settings/api-key`): `sk-ant-`로 시작·최소 길이만 가볍게 검사하고 저장. 등록 여부는 `GET`으로 확인할 수 있지만 값 자체는 이 서버조차 다시 보여주지 않는다(비밀번호와 같은 취급).
- **AI 프록시**(`POST /api/site/[slug]/ai/summarize`): 본인 키가 없으면 400 + 등록 안내. Anthropic 실패 시 응답 본문(사용자 키 일부가 에코백될 수 있음)을 그대로 노출하지 않고 상태 코드만 전달한다.
- **의도적으로 범위 밖으로 둔 것**: AI 기능 사용 로그(누가 몇 번 썼는지)는 만들지 않았다 — 과금이 플랫폼이 아니라 사용자 본인에게 나가므로 원가 집계용으로 필요하지 않다. 필요해지면 별도 요청으로 추가.
- **검증**: lint 0 / 단위 83파일·836건(`dormant.test.ts`에 [P11-6] 몫 3개만 남음) / 클린 빌드. 커밋 `b782c22`(RED)→`ff73aab`(GREEN).

### [P11-5] 완료 — 산출물 프롬프트에 방문자 API 호출 안내 배선

- **다른 슬라이스와 달리 코드가 아니라 프롬프트 지시문**: `src/lib/sdvc/blocks.ts`에 `SITE_ACCOUNTS_GUIDANCE_LINES`를 새로 추가해 구현(5)·유지보수(6) 두 블록 지시문에 공통으로 넣었다 — PWA([P7-13])·BL-023·BL-024 때와 같은 자리, 같은 방식.
- **안내 내용**: P11-1~4에서 실제로 만든 다섯 라우트(`auth/signup`·`auth/login`·`records` GET/POST·`settings/api-key` GET/POST·`ai/summarize`)의 요청/응답 형태를 그대로 적었다. 로그인 요청이 실제로 있을 때만 내라는 원칙은 PWA와 같다.
- **slug를 프롬프트에 박아 넣지 않았다**: 산출물을 만드는 시점의 AI는 배포될 최종 주소(slug)를 모른다. 대신 `location.pathname.split("/")[2]`로 **런타임에** 읽게 안내했다 — 슬러그가 바뀌어도 코드를 다시 낼 필요가 없다.
- **`localStorage`로 계정을 흉내 내지 말라고 못 박았다** — Story-Doing이 서버 없이 브라우저 저장으로 계정을 흉내 냈던 것과 같은 실수가 반복되지 않게(BL-024와 같은 뿌리).
- **`BROWSER_CLAUDE_CALL_LINES`(브라우저 직접 호출) 쪽에 상호 참조를 덧붙였다**: 방문자 계정이 있는 프로젝트는 반드시 이번에 만든 AI 프록시를 쓰고, 브라우저 직접 호출은 계정이 없는 프로젝트에서만 쓰도록 갈라놓았다 — 안 그러면 계정 시스템을 만들면서도 여전히 키를 브라우저에 노출하는 절반짜리 보안이 나올 수 있다.
- **실제 Claude 호출로 검증**: "방문자 로그인 + 내 기록 + AI 요약"을 요청하는 실제 유저 메시지로 `claude-sonnet-5`를 직접 불러 확인했다. 버티컬 슬라이스 원칙대로 가입·로그인부터 만들었고, `auth/signup`·`auth/login`·`/records`를 실제 경로 그대로 불렀으며, slug는 `location.pathname`에서 뽑았다. `localStorage`는 비밀번호나 세션 토큰이 아니라 인사말 표시용 이메일 한 줄이었고(자체 보고서에도 "새로고침하면 다시 로그인 화면부터 시작"이라고 적어, 세션 판단에 쓰지 않음을 스스로 밝힘) — 계정 흉내 내기가 아니었다.
- **검증**: lint 0 / 단위 83파일·842건(신규 6건, `dormant.test.ts` 영향 없음 — 새 함수가 아니라 문자열 상수) / 클린 빌드. 커밋 `0719e94`(RED)→`7c8a46d`(GREEN).
- **새 환경변수·마이그레이션 없음.**
