# 실전 트러블슈팅 — 실제로 겪은 문제와 교훈

> 실제 완주 프로젝트에서 만났던 문제들. 바이브코딩을 하다 보면 반드시 비슷한 상황을 만난다.
> 에러나 이상 동작을 만나면 이 목록의 교훈부터 적용해본다.

## 실제 사례 모음

| 문제 | 원인 | 교훈 |
|---|---|---|
| 라이브러리 충돌 (passlib ↔ bcrypt 버전 비호환) | 두 라이브러리의 최신 버전이 서로 안 맞음 | 라이브러리 조합 문제는 검색으로 씨름하기보다 **'더 단순한 대안으로 바로 교체'**하는 것이 빠를 때가 많다 (예: passlib을 걷어내고 bcrypt 직접 사용) |
| 파일 업로드가 안 됨 (python-multipart 누락) | 필요한 패키지가 requirements.txt에 빠져 있었음 | **에러 메시지를 그대로 읽으면 대부분 해결책이 메시지 안에 있다** — 패닉 대신 정독 |
| 백그라운드 작업이 테스트용 가짜 DB를 우회하고 운영 DB를 건드림 | DB 세션 팩토리를 직접 import해서 값이 고정됨 | 테스트가 통과해도 **'진짜로 옳은 것을 테스트했는지' 항상 의심**할 것 (상세: 04 문서의 SessionLocal 교훈) |
| 명세의 요구사항이 API 응답에 반영 안 됨 | 계획(plan) 단계에서 누락 | 설계 문서와 실제 구현 사이의 틈은 구현 중에 반드시 나타난다 — **발견 즉시 계약(contract) 문서도 함께 고칠 것** (코드만 고치면 문서가 거짓말이 된다) |
| 분명 코드를 고쳤는데 동작이 그대로 | 이전에 켜둔 옛 서버 프로세스가 포트를 계속 점유 | **'고쳤는데 그대로'면 서버 재시작부터 의심할 것** (포트 점유 프로세스 확인 → 종료 → 재시작) |
| 브라우저 자동화 테스트의 클릭이 가끔 씹힘 | 렌더링 타이밍 문제 | **자동화 도구도 100% 신뢰하지 말고, 결과를 항상 다른 방법으로 재확인**할 것 |
| 절차 순서가 꼬임 (checklist를 plan보다 먼저 실행) | plan.md가 아직 없었음 | 도구가 막아주면 당황하지 말 것 — 무엇이 먼저 필요한지 알려주는 친절한 안내다. 선행 단계를 끝내고 다시 실행하면 된다 |

## 초보자를 위한 디버깅 순서 (AI가 안내할 것)

1. **에러 메시지 전문을 그대로 복사해서 보여달라고 한다.** 요약본이 아니라 원문. 대부분 답이 그 안에 있다.
2. **최근에 바꾼 것이 무엇인지 확인한다.** git 커밋을 단계마다 남겨뒀다면 `git diff`로 바로 좁힐 수 있다 — 이것이 커밋 규율의 실전 보상이다.
3. **환경 문제인지 코드 문제인지 구분한다.** 서버 재시작, 패키지 재설치, 캐시 삭제로 사라지는 문제는 환경 문제다.
4. **테스트를 돌린다.** 어느 테스트가 깨지는지가 문제 위치를 알려준다. 테스트가 전부 통과하는데 실제 동작이 이상하면 → 테스트가 놓치고 있는 케이스를 새 테스트(RED)로 먼저 추가한다.
5. **고친 뒤에는 전체 테스트를 다시 돌린다.** 한 곳을 고치면 다른 곳이 깨질 수 있다.

## '고쳤다고 착각'을 막는 원칙

- 버그를 고치기 전에, **그 버그를 재현하는 실패 테스트를 먼저 쓴다.** 그 테스트가 통과로 바뀌는 것이 '고쳐졌다'의 유일한 증거다.
- 화면이 있는 기능은 테스트 통과 후에도 **실제 브라우저에서 한 번 직접 확인**한다(quickstart 시나리오).
- 수정 내역은 반드시 커밋으로 남기고, 원인과 해결책을 커밋 메시지나 작업보고서에 한 줄이라도 적는다 — 같은 문제를 두 번 만났을 때 과거의 내가 미래의 나를 구한다.
