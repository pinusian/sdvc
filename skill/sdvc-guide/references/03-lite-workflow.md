# B코스 — 경량 내장 워크플로 (Spec Kit 없이)

> Spec Kit을 설치하지 않은(또는 설치할 수 없는) 환경에서, AI가 직접 같은 절차를 재현할 때 사용한다.
> 핵심: 도구가 없어도 **문서와 게이트(관문)는 똑같이** 만든다. 도구는 절차를 편하게 해줄 뿐, 절차 자체는 문서로 지킨다.

## 폴더 구조

프로젝트 루트에 다음을 만든다 (기능 이름은 `001-기능명` 형식으로 번호를 붙인다):

```
프로젝트/
├── docs/
│   ├── constitution.md          # 헌장 (프로젝트당 1개)
│   └── task-reports/            # 완료 보고서 모음
└── specs/
    └── 001-기능명/
        ├── spec.md              # 무엇을 만들지
        ├── plan.md              # 무엇으로 어떻게
        ├── tasks.md             # 작업 목록
        └── checklist.md         # 요구사항 품질 점검표 (사람이 체크)
```

## 단계별 진행

### 1단계: 헌장 (constitution.md) — 프로젝트당 1회

사용자와 대화하며 5~7개의 '절대 규칙'을 정한다. 초보자용 기본 틀:

```markdown
# 프로젝트 헌장 v1.0.0
1. TDD (양보 불가): 모든 기능은 실패하는 테스트 작성(RED) → 최소 구현(GREEN) → 정리(REFACTOR) 순서로 만들고, 각 단계를 별도 커밋한다.
2. 기록: 기능 완료마다 docs/task-reports/에 작업보고서를 남긴다.
3. 보안: API 키·비밀번호는 절대 커밋하지 않는다. .env는 .gitignore에 넣고 .env.example만 커밋한다.
4. 커밋 컨벤션: {type}: {제목} - {TDD단계} ({작업ID})
5. 금지: 테스트 없는 구현, main 브랜치 직접 커밋, 사용자 승인 없는 방향 전환.
```

방향이 크게 바뀌면 헌장을 다시 세우되, 파일 상단에 '무엇이 왜 바뀌었는지'를 주석으로 남기고 버전을 올린다.

### 2단계: 명세 (spec.md)

사용자에게 먼저 묻는다: "만들고 싶은 것을 자유롭게 설명해주세요. 화면 스케치나 예시가 있으면 더 좋습니다." 받은 내용을 다음 형식으로 정리한다. **기술 용어(언어·DB·프레임워크)는 여기에 쓰지 않는다.**

```markdown
# 명세: {기능 이름}
## User Stories (우선순위 P1/P2/P3)
- US1 (P1): 사용자는 ~할 수 있다.
## 인수 시나리오 (스토리마다 2개 이상)
- 주어진(Given) ~상태에서 / ~할 때(When) / 그러면(Then) ~된다.
## 기능 요구사항
- FR-001: 시스템은 ~해야 한다. (검증 가능한 문장으로)
## 성공 기준 (숫자로 측정 가능하게)
- SC-001: ~을 N초/N% 이내에 ~할 수 있다.
## 범위 제외 (Assumptions)
- 이번에는 ~은 만들지 않는다.
```

### 3단계: 명확화 (Clarify 게이트)

spec.md를 다시 읽고 애매한 지점을 찾아 **최대 5개**의 질문을 만든다. 각 질문에 추천안을 붙여 객관식으로 제시한다(AskUserQuestion 활용). 답은 spec.md에 `## Clarifications` 절로 기록하고, 관련 FR을 추가·수정한다. **이 게이트를 통과하기 전에는 4단계로 넘어가지 않는다.**

### 4단계: 계획 (plan.md)

- 기술 스택을 고르되, **각 선택의 근거와 기각한 대안**을 함께 적는다. 초보자 로컬 환경이면 설치가 필요 없는 가벼운 것(예: SQLite)을 우선 추천한다.
- 외부 유료 API를 쓰게 되면 반드시 사용자에게 알리고 선택받는다. `.env` 빈 틀만 만들고 키 값은 사용자가 직접 넣게 한다.
- 데이터 구조(어떤 표에 어떤 필드), 화면-서버 통신 규격, 그리고 **구현 완료 후 사용자가 직접 눈으로 확인할 시나리오 목록(quickstart)**을 함께 적는다.
- 마지막에 '헌장 자가 점검' 표를 만든다: 각 헌장 원칙에 대해 PASS 또는 DEVIATION(+이유, +대안, +복귀 방법).

### 5단계: 점검표 (checklist.md)

spec.md의 요구사항 '문장'이 잘 쓰였는지 점검하는 질문 목록(10~20개)을 만든다 — 완결성·명확성·일관성·측정가능성·경계조건 5가지 관점. **AI는 목록만 만들고 체크 표시는 절대 하지 않는다.** 지금 답하기 어려운 항목(비용, 개인정보 등)도 정직하게 넣고 미체크로 남긴다.

### 6단계: 작업 분해 (tasks.md)

`04-tdd-vertical-slice.md`의 방식대로: 공통 기반(Foundational) Phase를 먼저 빼고, User Story마다 슬라이스 하나씩, 슬라이스 안은 RED→GREEN→REFACTOR. 각 Task에 ID(T001…)와 커밋 메시지를 미리 정한다.

### 7단계: 모순 점검 (Analyze 게이트)

구현 시작 전에 spec/plan/tasks를 교차 검증한다:
- 명세의 모든 FR에 대응하는 Task와 테스트가 있는가?
- 계획에 없는 것을 Task가 전제하고 있지 않은가? (예: 존재하지 않는 API)
- 두 문서가 서로 모순되는 서술이 없는가?
- 접근 제어·에러 처리 같은 공통 요구가 모든 기능에 고르게 적용됐는가?

발견한 문제는 심각도(CRITICAL/HIGH/MEDIUM/LOW)를 붙여 **보고서로만 제시**하고, 사용자가 승인한 수정안만 반영한다.

### 8단계: 구현

- 시작 전 checklist.md의 미체크 항목을 보여주고 진행 여부를 확인받는다. "나중에 검토" 항목은 tasks.md 후반에 Task로 추가한다.
- tasks.md 순서대로, TDD 규율(`04-tdd-vertical-slice.md`)을 지키며 구현한다.
- 슬라이스 하나가 끝날 때마다 실제 실행해서 사용자가 눈으로 확인하게 한다.
- 전부 끝나면: 전체 테스트 실행 → quickstart 시나리오 검증 → docs/task-reports/에 보고서 작성 → 남은 숙제 정직하게 기록.

## Spec Kit으로 나중에 갈아타기

B코스로 만든 문서 구조는 Spec Kit과 거의 같으므로, 나중에 `specify init`으로 Spec Kit을 설치하면 기존 spec.md/plan.md/tasks.md를 `specs/{번호-기능명}/`에 그대로 옮겨 이어갈 수 있다.
