# A코스 — Spec Kit 8단계 코치 가이드

> Spec Kit(`/speckit.*` 명령)이 설치된 환경에서 초보자를 단계별로 안내할 때 사용한다.
> 각 단계의 프롬프트 예시는 실제 완주 프로젝트(『바이브코딩 실전 교육교재』 3부)에서 그대로 가져온 것이다.

## 전체 순서와 의존 관계

```
[사람이 미리 준비]                [Spec Kit 파이프라인]
내 헌장 초안(선택)   ──────▶ ① /speckit.constitution
서비스 기획서(권장)  ──────▶ ② /speckit.specify
                                ③ /speckit.clarify
                                ④ /speckit.plan        ← ⑤보다 반드시 먼저!
                                ⑤ /speckit.checklist   (plan.md 없으면 실행 거부됨)
                                ⑥ /speckit.tasks
                                ⑦ /speckit.analyze     (읽기 전용 보고서)
                                ⑧ /speckit.implement
```

실전에서 ⑤를 ④보다 먼저 실행했다가 막힌 사례가 있다 — 도구가 순서를 강제해주므로 당황하지 말고 안내대로 선행 단계를 먼저 끝내면 된다.

## ① Constitution — 헌장 (프로젝트당 1회)

'무슨 일이 있어도 지켜야 할 규칙'을 정한다. 이후 모든 단계가 이 문서를 최상위 기준으로 참조하며, ⑦분석 단계에서 헌장 위반은 자동으로 CRITICAL로 분류된다.

- 초보자에게 권할 핵심 원칙: **TDD(양보 불가), 커밋 컨벤션, 비밀정보 커밋 금지, 완료 시 작업보고서 작성, 금지 행위 목록**
- 사용자가 직접 쓴 헌장 초안 파일이 있으면 `@파일명`으로 지정해 반영시킨다.
- 헌장은 '한 번 정하면 끝'이 아니다. 프로젝트 방향이 바뀌면 다시 세우되, **무엇이 왜 바뀌었는지(Sync Impact Report)를 파일 상단에 기록**한다. 버전은 성격이 바뀌면 MAJOR로 올린다.

## ② Specify — 명세

'어떻게'가 아니라 **'무엇을'만** 정의한다. spec.md에는 언어·DB 같은 기술 얘기가 등장하면 안 된다.

- 가장 효과적인 실전 프롬프트는 단 한 줄이었다: `/speckit.specify @기획서.md`
- **결과물 품질은 프롬프트의 정교함보다 '미리 준비한 입력 자료'가 좌우한다.** 사용자에게 화면 예시·데이터 예시가 담긴 기획서(반 페이지라도)를 먼저 쓰게 하라. 기획서가 있으면 AI는 '추측'이 아니라 '정리'만 하면 된다.
- 산출물 구성: User Story(우선순위 P1/P2/P3) + Given/When/Then 인수 시나리오 + 번호 붙은 기능 요구사항(FR-001…) + 숫자로 측정 가능한 성공 기준(SC-001…) + 범위에서 제외한 것(Assumptions)

## ③ Clarify — 명확화

`/speckit.clarify`만 실행하면 AI가 spec.md를 스캔해 애매한 지점을 최대 5개 질문한다(추천안 포함 객관식). 답은 spec.md의 Clarifications 절과 관련 요구사항에 즉시 반영된다.

- **교육 포인트**: 이 질문들이 구현 도중에 발견되었다면 이미 만든 코드를 되돌려야 했다. Clarify는 '가장 저렴할 때 미리 결정하는' 단계다. (실제 사례: "실습 문제를 언제 생성하나?"라는 질문 하나가 백그라운드 작업 구조 전체를 좌우했다)

## ④ Plan — 계획

처음으로 기술 이야기가 등장한다. 산출물: plan.md(기술 스택, Constitution Check, 구조), research.md(기술 결정과 근거·기각된 대안), data-model.md(데이터 설계), contracts/(API 규격), quickstart.md(구현 후 사람이 직접 확인할 시나리오).

- 외부 AI API 등을 쓸 경우 제공사 선택은 반드시 사용자에게 묻는다. **API 키는 빈 `.env` 틀만 만들어주고 값은 사용자가 직접 입력하게 한다.**
- **DEVIATION(이탈)은 나쁜 게 아니다.** 헌장이 요구한 것(예: PostgreSQL, Celery+Redis)을 환경 사정으로 못 지키면, 무엇을 왜 대체했고 나중에 되돌리려면 뭘 바꾸면 되는지 Complexity Tracking 표로 정직하게 기록하면 된다. (실제 사례: SQLite와 FastAPI BackgroundTasks로 대체하고 그 사실을 기록)

## ⑤ Checklist — 품질 점검표

흔한 오해 주의: 이것은 **코드 검사가 아니라 '요구사항 문장 자체'의 품질 점검표**다('요구사항을 위한 단위 테스트'). "초보자가 이해할 수 있는 수준"처럼 측정 불가능한 표현이 없는지, 누락된 예외 상황이 없는지를 묻는 질문 목록을 만든다.

- 실행하면 초점 영역과 엄격도를 되묻는다 — 처음이면 추천안을 수락하게 안내.
- **AI는 체크리스트를 만들 수만 있고, 체크 표시는 절대 하지 않는다.** 체크는 검토자(사람) 몫이다.
- 지금 답하기 어려운 항목(비용 한도, 개인정보 처리 등)도 정직하게 포함시키고, 미체크 상태로 남겨 추적한다.

## ⑥ Tasks — 작업 분해

지금까지의 모든 문서를 종합해 실행 가능한 작업 목록(tasks.md)을 만든다.

- 권장 조직 방식: **버티컬 슬라이스** — 기능 하나를 백엔드 모델→API→화면→테스트까지 완결한 뒤 다음 기능으로. 상세는 `04-tdd-vertical-slice.md`.
- 실전 사례: 사용자가 "모델→API→화면→테스트" 순서를 요청했는데 이는 헌장의 TDD(테스트 먼저)와 충돌했다. AI는 충돌을 그냥 넘기지 않고 알린 뒤 절충안을 제시했다 — 슬라이스는 유지하되 슬라이스 안에서는 RED(테스트)→GREEN(모델→API→화면)→REFACTOR 순서. **사용자 요청과 헌장이 충돌하면 반드시 짚고 절충안을 제안하라.**
- 각 Task에 커밋 메시지 형식까지 미리 정한다. 병렬 가능한 작업은 [P]로 표시.

## ⑦ Analyze — 모순 점검

구현 직전, spec/plan/tasks 세 문서를 교차 검증한다. **철저히 읽기 전용** — 문제를 발견해도 보고서만 내고, 사람이 "예, 수정안대로 수정해줘"라고 승인해야만 고친다.

- 실제로 잡아낸 문제 유형: 명세에는 있는데 검증 테스트가 계획에 없음 / 요구사항을 구현할 API 엔드포인트 자체가 계획에 없음 / 접근 제어 테스트가 일부 기능에만 있음 / 두 문서가 서로 모순됨. 이런 것들이 구현 전에 잡히면 수정 비용이 거의 0이다.

## ⑧ Implement — 구현

tasks.md 순서 그대로 구현한다. 시작 직전 checklists/를 자동 스캔해 미체크 항목이 있으면 진행 여부를 되묻는다.

- 미체크 항목을 안고 진행하려면 **조건부 승인**을 받는다: "지금은 진행하되 ○○ 항목은 나중에 반드시 재검토" — 그리고 그 약속을 tasks.md의 후반 Phase에 Task로 박아 넣어 허공으로 사라지지 않게 한다.
- 구현 규율은 `04-tdd-vertical-slice.md`를 따른다.
- 완료 후: quickstart.md 시나리오를 사용자와 함께 실행해 눈으로 확인하고, docs/task-reports/에 작업보고서를 남긴다.
