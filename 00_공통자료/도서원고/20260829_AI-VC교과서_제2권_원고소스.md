# 제2권을 시작하며

## 이 권에서 할 일

제1권에서 AI-VC의 7단계와 3대 원칙을 배웠습니다. 제2권에서는 그것을 **하나의 실제 서비스**에 처음부터 끝까지 적용합니다.

만들 것은 **독서활동 서비스**입니다. 학생이 책을 읽고 기록을 남기면, AI가 내용을 정리해주고, 비슷한 책을 추천해주고, 토론 주제를 던져주고, 함께 토론한 뒤, 마지막에 그 모든 것을 담론(에세이) 형식의 글로 정리해주는 서비스입니다.

> **[예시 서비스] 독서활동이란?**
> 학생이 책을 읽고 ① 간단한 줄거리·인상 깊은 구절·자신의 생각을 기록하면, AI가 ② 전체 줄거리·핵심 주제·주요 상징·작가의 의도·인물 분석까지 깊이 있게 정리해주고, ③ 비슷한 주제의 책을 추천해주고, ④ 토론 주제를 제안한 뒤 ⑤ 학생과 계속 대화하며 토론해주고, 마지막으로 ⑥ 이 모든 내용을 종합해 담론 형식의 글로 만들어주는 서비스입니다.

## 왜 이 서비스를 예제로 골랐나

1. **누구나 이해할 수 있는 주제입니다.** 책을 읽고 기록한다는 행위는 설명이 필요 없습니다.
2. **AI를 실제로 써야만 성립하는 서비스입니다.** 단순 CRUD(입력·조회·수정·삭제) 연습이 아니라, AI 호출·비용·품질 문제를 실제로 겪게 됩니다.
3. **기능이 6개로 적당히 많습니다.** 버티컬 슬라이스의 이점을 체감하기에 알맞은 규모입니다.
4. **확장 방향이 자연스럽습니다.** 노션 저장, 학부모 메일 발송, 개인정보 보호 등 19부·20부에서 다룰 주제로 매끄럽게 이어집니다.

# 8부. 실습 준비 — 환경과 도구 세팅

> **이 부에서 답하는 질문**
> 1. 무엇을 설치해야 하는가?
> 2. 터미널이 무엇이고 어떻게 쓰는가?
> 3. API 키는 어떻게 발급받고 어디에 넣는가?

## 8.1 준비물 한눈에 보기

| 순번 | 준비물 | 용도 | 필수 여부 |
|---|---|---|---|
| 1 | 컴퓨터(Windows 또는 macOS) | 작업 환경 | 필수 |
| 2 | 터미널(PowerShell / 터미널.app) | 명령 입력 | 필수 |
| 3 | Claude Code | AI 개발 파트너 | 필수 |
| 4 | Node.js | 화면(프론트엔드) 실행 | 필수 |
| 5 | Python | 서버(백엔드) 실행 | 필수 |
| 6 | Git | 변경 이력 관리 | 필수 |
| 7 | VS Code(편집기) | 파일 내용 확인 | 강력 권장 |
| 8 | uv | Spec Kit 설치 도구 | Spec Kit 사용 시 |
| 9 | Anthropic API 키 | AI 기능 호출 | 필수(유료) |
| 10 | GitHub 계정 | 코드 백업·공유 | 선택 |

> **[개념] 왜 이렇게 많은 게 필요한가요?**
> 실제로는 **네 가지 역할**뿐입니다. ① 명령을 입력할 창(터미널), ② 프로그램을 실행할 엔진(Python·Node.js), ③ 변경 이력을 남길 장치(Git), ④ AI(Claude Code + API 키). 나머지는 이 넷을 편하게 쓰기 위한 보조 도구입니다.

## 8.2 터미널 — 가장 낯설지만 가장 중요한 것

### 터미널이 무엇인가

> **[개념] 마우스 대신 글자로 지시하는 창**
> 파일 탐색기에서 폴더를 더블클릭하는 대신 `cd 폴더이름`이라고 타이핑하는 것입니다. 불편해 보이지만, **AI가 명령을 실행하고 그 결과를 읽으려면 이 창이 필요합니다.** 제1권 제2원칙(증거 기반 보고)이 가능한 물리적 이유가 바로 여기 있습니다.

### 여는 법

| 운영체제 | 여는 방법 |
|---|---|
| Windows | 시작 메뉴에서 `PowerShell` 검색 → 실행 |
| macOS | Spotlight(⌘+Space)에서 `터미널` 검색 → 실행 |

### 최소한 알아야 할 명령 5개

| 명령 | 하는 일 | 예 |
|---|---|---|
| `cd 경로` | 그 폴더로 이동 | `cd C:\Users\사용자\reading-activity` |
| `cd ..` | 상위 폴더로 이동 | |
| `dir` (Win) / `ls` (mac) | 현재 폴더의 파일 목록 | |
| `mkdir 이름` | 새 폴더 만들기 | `mkdir reading-activity` |
| (위쪽 화살표) | 직전 명령 다시 불러오기 | 오타 났을 때 유용 |

> **[실전] 경로를 손으로 타이핑하지 마십시오**
> 파일 탐색기에서 폴더를 연 뒤 주소창을 클릭해 경로를 복사하고, 터미널에 `cd ` 를 입력한 다음 붙여넣으면 됩니다. 오타로 인한 시간 낭비를 막는 가장 실용적인 요령입니다.

## 8.3 Node.js 설치

화면(프론트엔드)을 실행하는 데 필요합니다.

1. `nodejs.org` 접속
2. **LTS** 버전 내려받기 (LTS = 장기 지원, 안정 버전)
3. 설치 파일 실행 후 기본 설정으로 진행
4. 터미널을 **새로 열고** 확인

```
node --version
npm --version
```

버전 숫자가 나오면 성공입니다.

> **[주의] 설치 후에는 터미널을 반드시 새로 여십시오**
> 설치 프로그램이 시스템 경로(PATH)를 갱신하는데, 이미 열려 있던 터미널 창은 그 변경을 모릅니다. "분명히 설치했는데 명령을 못 찾는다"는 문제의 90%가 이것입니다.

## 8.4 Python 설치

서버(백엔드)를 실행하는 데 필요합니다.

1. `python.org` 접속 → 최신 안정 버전 내려받기
2. **Windows 사용자 주의**: 설치 첫 화면의 **"Add Python to PATH"** 체크박스를 반드시 켜십시오
3. 설치 후 새 터미널에서 확인

```
python --version
```

macOS에서는 `python3 --version`을 쓸 수도 있습니다.

## 8.5 Git 설치

변경 이력을 남기고 되돌릴 수 있게 해주는 도구입니다.

1. `git-scm.com` 접속 → 내려받기 → 기본 설정으로 설치
2. 새 터미널에서 확인 후 최초 1회 설정

```
git --version
git config --global user.name "내 이름"
git config --global user.email "내메일@example.com"
```

> **[개념] 이름과 메일을 왜 등록하나요?**
> 커밋(변경 저장)마다 "누가 했는지"가 기록되기 때문입니다. 혼자 쓰더라도 나중에 이력을 볼 때 필요합니다. 공개 저장소에 올릴 계획이라면 이 메일 주소가 공개된다는 점을 유념하십시오.

## 8.6 VS Code 설치 (권장)

파일 내용을 눈으로 확인할 편집기입니다. AI가 만든 `spec.md`, `plan.md`를 읽으려면 필요합니다.

1. `code.visualstudio.com` 접속 → 내려받기 → 설치
2. 실행 후 좌측 상단 **File > Open Folder**로 프로젝트 폴더를 엽니다

> **[실전] 메모장으로도 됩니다만**
> `.md` 파일은 메모장으로도 열립니다. 다만 VS Code는 표와 제목을 알아보기 쉽게 보여주고, 폴더 구조를 한눈에 볼 수 있어 훨씬 편합니다. 코드를 편집할 일이 없더라도 "읽기용"으로 설치할 가치가 있습니다.

## 8.7 Claude Code 설치와 첫 실행

### 설치

터미널에서 다음을 실행합니다.

```
npm install -g @anthropic-ai/claude-code
```

> **[주의] 위 명령은 예시이며 재확인이 필요합니다**
> 설치 명령과 패키지 이름은 도구 갱신에 따라 달라질 수 있습니다. 반드시 Claude Code 공식 문서에서 현재 설치 방법을 확인하십시오.

### 첫 실행

1. 작업할 폴더를 만들고 그 폴더로 이동합니다.

```
mkdir reading-activity
cd reading-activity
```

2. Claude Code를 실행합니다.

```
claude
```

3. 최초 실행 시 로그인(계정 인증) 절차가 진행됩니다. 안내에 따라 브라우저에서 인증하면 됩니다.

### 첫 대화로 확인하기

```
사용자:
지금 폴더의 경로와 안에 있는 파일 목록을 보여줘.
```

경로와 목록이 나오면 정상 연결된 것입니다.

## 8.8 Spec Kit 설치 (선택이지만 권장)

AI-VC의 7단계를 `/speckit.*` 명령으로 쓰려면 Spec Kit을 설치합니다.

### 1단계 — uv 설치

uv는 Python으로 만든 프로그램을 쉽게 설치·관리해주는 도구입니다.

Windows PowerShell:

```
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

> **[주의] 설치 후 창을 새로 열 것**
> 설치가 끝나면 `uv` 실행 파일이 사용자 폴더 아래(`.local\bin\`)에 놓입니다. PowerShell을 닫았다가 새로 열어야 이 위치가 경로에 반영됩니다. 새 창에서 `uv --version`을 입력해 버전이 나오면 성공입니다.

### 2단계 — specify CLI 설치

```
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
```

설치 확인:

```
specify --version
specify check
```

`specify check`는 내 컴퓨터에 어떤 AI 코딩 도구가 설치되어 있는지 자동으로 스캔해 보여줍니다. `Claude Code (available)`처럼 나오면 정상 연결된 것입니다.

### 3단계 — 프로젝트 폴더에 적용

| 경우 | 명령 |
|---|---|
| 새 폴더를 만들며 시작 | `specify init reading-activity --ai claude` → `cd reading-activity` |
| 이미 만든 폴더에 적용 | `cd reading-activity` → `specify init --here --ai claude` |

`--ai claude`는 "이 프로젝트를 Claude Code와 함께 쓰겠다"는 뜻입니다. `--here`는 "이미 파일이 있는 폴더에도 그 위에 구조를 덧씌워라"는 뜻입니다.

### 4단계 — 설치 확인

폴더 안에 다음 두 가지가 새로 생기면 성공입니다.

| 생성물 | 역할 |
|---|---|
| `.specify/` | Spec Kit 엔진의 설정·템플릿·스크립트 |
| `.claude/` (또는 해당 AI 도구 폴더) | `/speckit.*` 명령(스킬)들의 실제 정의 |

### 5단계 — 실제로 써보기

```
(터미널에서)        claude
(Claude Code 안에서) /speckit.constitution
```

### 자주 걸리는 문제

| 증상 | 원인 | 해결 |
|---|---|---|
| `uv`를 못 찾음 | 설치 후 창을 새로 열지 않음 | 터미널 재시작 |
| `specify`를 못 찾음 | uv tool 경로 미반영 | 터미널 재시작, `uv tool list`로 확인 |
| `specify check`에 Claude Code가 안 보임 | Claude Code 미설치 또는 경로 문제 | Claude Code 재설치 후 재확인 |
| 실행 정책 오류(Windows) | PowerShell 보안 정책 | 위 설치 명령의 `-ExecutionPolicy ByPass` 옵션 확인 |

## 8.9 Anthropic API 키 발급과 설정

### 왜 필요한가

Claude Code로 코드를 만드는 것과, **여러분이 만든 서비스가 스스로 AI를 호출하는 것**은 별개입니다. 독서활동 서비스는 "학생이 글을 올리면 AI가 정리해주는" 기능이 핵심이므로, 그 서비스 자신이 AI를 호출할 수 있어야 합니다. 그 호출 권한을 증명하는 것이 API 키입니다.

> **[개념] API 키는 회원증입니다**
> 헬스장 회원증과 같습니다. 이것을 보여줘야 시설을 쓸 수 있고, 남에게 빌려주면 그 사람이 쓴 요금이 내게 청구됩니다. 그래서 **절대 남에게 보이지 않는 곳에 보관**해야 합니다.

### 발급 절차

1. Anthropic 콘솔(`console.anthropic.com`)에 접속해 계정을 만듭니다.
2. 결제 수단을 등록하고 사용 한도를 설정합니다.
3. API Keys 메뉴에서 새 키를 생성합니다.
4. **생성 직후 한 번만 전체 값이 보입니다.** 이때 복사해 안전한 곳에 보관하십시오.

> **[주의] 사용 한도를 반드시 먼저 설정하십시오**
> 코드에 실수가 있으면 AI를 반복 호출하는 무한 루프가 생길 수 있습니다. 월 한도(예: 2만 원)를 미리 걸어두면 최악의 상황을 막을 수 있습니다. 이것은 20부에서 다시 다룹니다.

### `.env` 파일에 넣기

프로젝트 폴더 루트에 `.env`라는 이름의 파일을 만들고 다음과 같이 적습니다.

```
ANTHROPIC_API_KEY=sk-ant-여기에_내_키_값
```

그리고 `.env.example`이라는 파일을 하나 더 만들어 **값 없이 항목만** 적어둡니다.

```
ANTHROPIC_API_KEY=
```

| 파일 | 저장소에 올리나 | 역할 |
|---|---|---|
| `.env` | **절대 안 됨** | 실제 키 값 보관 |
| `.env.example` | 올림 | "이 프로젝트는 이런 항목이 필요하다"는 안내 |

### `.gitignore` 확인

프로젝트 루트의 `.gitignore` 파일에 다음 줄이 있는지 반드시 확인하십시오.

```
.env
```

> **[주의] AI에게 키 값을 알려주지 마십시오**
> 선행 프로젝트에서 사용자는 AI에게 **"너가 루트에 `.env` 파일을 만들고 내가 API 키를 넣을 수 있게 해줘"**라고 지시했습니다. 빈 틀만 만들게 하고 값은 직접 넣은 것입니다. 이 책 전체에서 가장 중요한 보안 습관입니다. 만약 이미 대화창에 키를 붙여넣었다면, 그 키를 즉시 폐기하고 새로 발급하십시오.

# 9부. 만들 서비스 — 독서활동 서비스 기획

## 9.1 서비스 한 줄 정의

> **중학생~고등학생이 읽은 책에 대해 짧게 기록을 남기면, AI가 그 기록을 바탕으로 깊이 있는 분석·도서 추천·토론·담론 작성까지 도와주는 독서 학습 서비스.**

## 9.2 이 서비스가 겨냥하는 불편

기획서 ②번 항목(왜 필요한가)에 해당하는 부분입니다. 추상적으로 "독서 교육이 중요하다"고 쓰는 대신, **구체적 장면**으로 씁니다.

1. 학생은 책을 읽고 나서 "느낀 점"을 쓰라는 과제를 받지만, 무엇을 어떻게 써야 할지 막막합니다. 결국 인터넷 검색 결과를 옮겨 적습니다.
2. 교사는 학생 30명의 독후감을 읽고 각각에게 개별 피드백을 줄 시간이 없습니다.
3. 학생이 스스로 생각을 발전시키려면 누군가 되물어줘야 하는데, 그 역할을 해줄 사람이 옆에 없습니다.
4. 몇 달 뒤 생활기록부나 자기소개서를 쓸 때, 그때 무엇을 읽고 무엇을 느꼈는지 남아 있지 않습니다.

> **[실전] 왜 이렇게 구체적으로 쓰나요?**
> AI는 "독서 교육 개선"이라는 목표에서는 아무 요구사항도 도출하지 못합니다. 반면 "몇 달 뒤 생활기록부를 쓸 때 기록이 남아 있지 않다"는 문장에서는 **"기록을 저장하고 다시 조회할 수 있어야 한다"**, **"재독 기록도 별도로 남아야 한다"** 같은 요구사항이 자동으로 도출됩니다. 불편은 구체적일수록 좋습니다.

## 9.6 이번에 하지 않을 것

기획서 ⑥번 항목입니다. **이 절이 가장 많은 시간을 아낍니다.**

1. 학생 간 소셜 기능(친구 추가, 좋아요, 댓글) — 만들지 않습니다.
2. 교사용 관리 화면 — 만들지 않습니다. 1차 범위는 학생 개인용입니다.
3. 모바일 앱 — 만들지 않습니다. 웹 브라우저에서만 동작합니다.
4. 책 정보 자동 조회(ISBN 검색) — 만들지 않습니다. 제목·저자는 직접 입력합니다.
5. 결제 기능 — 만들지 않습니다.
6. 여러 학교·반 단위 관리 — 만들지 않습니다.

> **[주의] "나중에 넣으면 되지"가 함정입니다**
> 명세에 적히지 않은 기능은 만들어지지 않는 것이 정상입니다. 문제는 **적지도 않고 빼지도 않은 애매한 상태**입니다. 이 경우 AI가 "있으면 좋겠다" 싶은 것을 스스로 넣어버리고, 그것을 테스트하고 화면까지 만듭니다. 시간은 시간대로 쓰고 원하지 않은 결과를 얻습니다.

## 9.7 아직 못 정한 것

기획서 ⑦번 항목입니다. 정직하게 적습니다. 이것이 3단계 명확화에서 다뤄질 항목이 됩니다.

1. 같은 책을 다시 읽었을 때, 기존 기록을 덮어쓸지 별도로 남길지 못 정했습니다.
2. AI 분석을 다시 요청했을 때 이전 결과를 지울지 보관할지 못 정했습니다.
3. 토론은 몇 번까지 주고받을 수 있게 할지 정하지 않았습니다.
4. 학생 이름·학교명 같은 개인정보를 어디까지 저장할지 정하지 않았습니다.
5. AI 호출이 실패했을 때 학생에게 무엇을 보여줄지 정하지 않았습니다.

> **[실전] 분량 기준이 왜 있나요?**
> A4 3쪽짜리 기획서로 시작하면, 부족한 부분을 AI가 추측으로 채웁니다. 선행 프로젝트의 기획서는 A4 10쪽이었고, 그 결과 명세 단계에서 사용자가 입력한 프롬프트는 단 한 줄이었습니다. **기획서에 쓴 시간이 이후 모든 단계의 시간을 줄입니다.**

## 9.9 기획서를 파일로 저장하기

완성한 기획서를 프로젝트 루트에 `plan_specify.md`라는 이름으로 저장합니다.

```
reading-activity/
├── plan_specify.md      ← 지금 만든 기획서
└── my_constitution.md   ← 다음 부에서 만들 헌장 초안
```

> **[실전] Cowork에서 만들고 옮겨도 됩니다**
> 제1권 7.2절에서 설명했듯, 기획서 작성은 Claude Cowork가 가장 잘하는 일입니다. Cowork에서 대화하며 기획서를 완성한 뒤, 그 내용을 `plan_specify.md`로 저장해 프로젝트 폴더에 넣으면 됩니다.

# 10부. 1단계 실전 — 헌장(Constitution)

## 10.1 이 단계에서 할 일

프로젝트의 절대 규칙을 정하고 `.specify/memory/constitution.md`에 저장합니다.

## 10.2 실행 프롬프트

```

이 프로젝트는 학생 독서활동 지원 웹서비스다.
아래 규칙을 헌장에 반영해줘.
 - 테스트를 반드시 구현보다 먼저 쓴다 (양보 불가)

 - 학생 개인정보(이름·학교)는 암호화해서 저장한다
 - 기능 하나가 끝날 때마다 결과를 문서로 남긴다
 - 커밋 메시지는 {type}: {제목} - {TDD단계} ({작업번호}) 형식을 따른다

조항은 12개를 넘기지 말고, 각 조항은 판별 가능한 문장으로 써줘.

```

 - TDD 필수 (권장)

docs/progress.md 를 갱신한다.

## VI. 커밋 컨벤션
{type}: {제목} - {TDD단계} ({작업번호}) 형식을 따른다.

## VII. 모듈러 모놀리스
하나의 서버 프로그램으로 두되 내부는 api/models/services/utils 로 분리한다.

계획(Plan)·작업분해(Tasks) 단계는 사용자의 명시적 승인 없이

## IX. 사용자 언어 원칙
사용자는 비전공자다. 기술 용어를 처음 쓸 때 일상 비유로 설명한다.

## X. 파괴적 작업 사전 확인
파일 삭제·저장소 공개 업로드 등은 실행 전 반드시 확인받는다.
```

# 11부. 2단계 실전 — 명세(Specify)

## 11.1 이 단계에서 할 일

기획서를 입력값으로 삼아 `spec.md`를 만듭니다. **기술 이야기는 한 줄도 나오지 않습니다.**

## 11.2 실행 프롬프트

```
사용자:
/speckit.specify @plan_specify.md

조건:
 - 프로그래밍 언어·데이터베이스·프레임워크 이름을 한 번도 쓰지 말 것
 - User Story 에 P1/P2/P3 우선순위를 매길 것
 - 기능 요구사항은 FR-001 부터 "시스템은 ~해야 한다" 형식으로
 - 성공 기준은 SC-001 부터, 반드시 숫자를 포함할 것
 - 기획서의 "이번에 하지 않을 것"을 가정(Assumptions) 절에 그대로 옮길 것
 - 내가 기획서에 쓰지 않은 기능은 추가하지 말 것
```

> **[실전] `@` 기호의 의미**
> `@파일이름`은 "이 파일을 입력값으로 읽어라"는 지시입니다. 프롬프트를 길게 쓰는 대신, 미리 준비한 문서를 통째로 넘기는 방법입니다. 선행 프로젝트에서 2단계 프롬프트는 `/speckit.specify @plan_specify.md` 한 줄이 전부였습니다.

## 11.3 만들어진 User Story 6개

| 번호 | 우선순위 | User Story | 왜 이 우선순위인가 |
|---|---|---|---|
| US1 | P1 | 사용자는 책을 읽고 줄거리·인상 구절·생각을 기록할 수 있다 | 이것이 없으면 서비스가 성립하지 않음 |
| US2 | P1 | 사용자는 AI가 정리한 책 내용 분석을 볼 수 있다 | 이 서비스의 핵심 가치 |
| US3 | P2 | 사용자는 비슷한 주제의 도서를 추천받을 수 있다 | 있으면 가치가 크게 오름 |
| US4 | P2 | 사용자는 AI가 제안한 토론 주제를 볼 수 있다 | US5의 입구 역할 |
| US5 | P2 | 사용자는 AI와 토론하고 그 내용을 이어서 볼 수 있다 | 학습 효과의 핵심이나 P1 없이는 무의미 |
| US6 | P3 | 사용자는 전체 내용을 담론(에세이)으로 출판할 수 있다 | 마지막 단계, 나중에 붙여도 무방 |

> **[개념] 우선순위가 곧 개발 순서입니다**
> 5단계에서 P1부터 슬라이스를 구성합니다. 그래서 US1·US2만 끝난 시점에도 "책을 기록하면 AI가 정리해주는 서비스"라는 **동작하는 최소 제품**이 완성됩니다. 여기서 멈춰도 쓸 수 있는 것이 남는다는 점이 중요합니다.

## 11.4 기능 요구사항(FR) 발췌

실제로 작성된 요구사항 중 대표적인 것들입니다.

| 번호 | 내용 |
|---|---|
| FR-001 | 시스템은 로그인한 사용자가 책 제목, 저자, 줄거리, 인상 깊은 구절, 생각을 입력해 독서 기록을 생성할 수 있어야 한다. |
| FR-002 | 시스템은 같은 책에 대해 여러 번 기록을 남길 수 있도록 허용해야 한다(재독 기록). |
| FR-003 | 시스템은 독서 기록 저장 시 AI 분석을 백그라운드로 시작하고, 사용자에게 즉시 응답해야 한다. |
| FR-004 | 시스템은 AI 분석 결과로 전체 줄거리, 핵심 주제, 주요 상징, 작가의 의도, 인물 분석을 제공해야 한다. |
| FR-005 | 재생성 시 이전 버전은 삭제하지 않고 보관하며, 사용자가 과거 버전을 조회할 수 있어야 한다. |
| FR-006 | 시스템은 분석 결과의 주제·상징에 근거해 도서 3~5권을 추천해야 한다. |
| FR-007 | 시스템은 추천 도서마다 추천 이유를 함께 제시해야 한다. |
| FR-008 | 시스템은 분석 결과를 바탕으로 토론 주제를 3개 제안해야 한다. |
| FR-009 | 시스템은 토론 세션의 대화 내용을 저장하고, 다시 방문했을 때 이어서 확인할 수 있어야 한다. |
| FR-010 | 시스템은 사용자 본인이 작성한 기록만 조회·수정할 수 있도록 접근을 제한해야 한다. |
| FR-011 | 시스템은 AI 호출 실패 시 사용자에게 실패 사실과 재시도 방법을 안내해야 한다. |
| FR-012 | 시스템은 담론 초안을 문서 파일로 내려받을 수 있게 제공해야 한다. |

> **[주의] FR-010 같은 '공통 규칙'에 주의하십시오**
> "본인 것만 조회 가능"은 모든 기능에 적용되어야 하는 규칙입니다. 그런데 실제로는 기록 조회에만 적용되고 토론·담론에는 빠지는 일이 흔합니다. 6단계 분석이 잡아내는 대표적 문제가 바로 이것입니다.

## 11.5 성공 기준(SC)

| 번호 | 내용 |
|---|---|
| SC-001 | 독서 기록 저장 후 5분 이내에 완성된 AI 분석을 확인할 수 있다. |
| SC-002 | 저장 버튼을 누른 뒤 2초 이내에 "분석 중" 화면으로 전환된다. |
| SC-003 | 추천 도서는 항상 3권 이상 5권 이하로 제시된다. |
| SC-004 | 토론 세션은 최소 10회의 주고받기를 지원한다. |
| SC-005 | 담론 초안은 1,500자 이상 2,500자 이하로 생성된다. |
| SC-006 | 중학생 수준의 어휘로 작성되어, 별도 설명 없이 읽을 수 있다. |

> **[실전] SC-006 같은 정성적 기준은 어떻게 하나요?**
> "중학생 수준"은 숫자가 아닙니다. 이런 항목은 4단계 체크리스트에서 **"객관적으로 측정 가능한 기준이 정의되어 있는가?"**라는 점검 질문으로 다시 등장하게 됩니다. 정직하게 "미정"으로 남겨두고 나중에 판단하는 것이 정답입니다. 선행 프로젝트에서도 동일한 성격의 항목(CHK006)이 실제로 그렇게 처리되었습니다.

## 11.6 인수 시나리오 예시

```
US1 — 독서 기록 작성

시나리오 1 (정상)
  Given 로그인한 사용자가 기록 작성 화면에 있을 때
  When  책 제목·저자·줄거리·인상 구절·생각을 입력하고 저장을 누르면
  Then  기록이 저장되고 목록 화면으로 이동하며,
        해당 기록의 상태가 "분석 중"으로 표시된다

시나리오 2 (필수값 누락)
  Given 로그인한 사용자가 기록 작성 화면에 있을 때
  When  책 제목을 비워둔 채 저장을 누르면
  Then  저장되지 않고 "책 제목을 입력해주세요" 안내가 표시된다

시나리오 3 (재독)
  Given 사용자가 '데미안'에 대한 기록을 이미 1건 가지고 있을 때
  When  같은 책 제목으로 새 기록을 저장하면
  Then  기존 기록은 그대로 유지되고 새 기록이 별도로 추가된다
```

> **[개념] 이 시나리오가 그대로 테스트가 됩니다**
> 7단계 RED 단계에서 AI는 위 시나리오를 읽고 자동화 테스트 코드로 옮깁니다. 즉 **여러분이 인수 시나리오를 잘 쓸수록 테스트가 촘촘해집니다.** 코드를 못 써도 테스트의 품질에 직접 기여할 수 있는 지점이 여기입니다.

## 11.7 가정(Assumptions)

```
이번 범위에서 제외:
 - 학생 간 소셜 기능(친구·좋아요·댓글)
 - 교사용 관리 화면
 - 모바일 앱 (웹 브라우저 전용)
 - ISBN 기반 도서 정보 자동 조회
 - 결제 기능
 - 학교·학급 단위 관리

전제:
 - 사용자는 1인 1계정으로 사용한다
 - 동시 접속자는 소수(교실 단위 이하)를 가정한다
 - AI 분석은 외부 AI 서비스 호출로 처리하며 비용이 발생한다
```

## 11.8 체크포인트

- [ ] `spec.md` 어디에도 기술 이름이 없다
- [ ] 모든 FR이 "시스템은 ~해야 한다"로 끝난다
- [ ] 모든 SC에 숫자가 있다(정성 항목은 미정으로 표시)
- [ ] User Story마다 인수 시나리오가 최소 1개 있다
- [ ] 가정 절에 "하지 않을 것"이 옮겨졌다
- [ ] 기획서에 없던 기능이 추가되지 않았다

# 12부. 3단계 실전 — 명확화(Clarify)

## 12.1 이 단계에서 할 일

AI가 `spec.md`를 다시 읽고 애매한 지점을 찾아 질문합니다. 여러분의 답이 명세에 즉시 반영됩니다.

## 12.2 실행 프롬프트

```
사용자:
/speckit.clarify

각 질문마다 선택지와, 네가 추천하는 답, 그리고
"이 결정을 나중에 바꾸려면 얼마나 어려운지"를 함께 알려줘.
```

## 12.3 실제로 오간 질문과 답

### 질문 1 — 재생성 시 이전 버전 처리

```
Claude:
Q1. AI 분석을 다시 요청했을 때 이전 결과는 어떻게 할까요?
  A. 덮어쓴다 (저장 공간 절약, 구조 단순)
  B. 이전 버전을 보관하고 조회할 수 있게 한다 (권장)
  C. 최근 3개까지만 보관

  추천: B
  이유: 기획서 ②번에 "몇 달 뒤 생활기록부를 쓸 때 기록이 없다"는
        불편이 적혀 있습니다. 버전 보관은 이 목적에 직접 부합합니다.
  되돌리기 비용: 높음. 데이터 구조(버전 필드·이력 테이블)를
        나중에 추가하려면 기존 데이터 이전 작업이 필요합니다.

사용자:
B로 해주세요.
```

→ 이 답이 **FR-005**로 명세에 추가되었습니다.

### 질문 2 — 재독 기록 처리

```
Claude:
Q2. 같은 책을 다시 읽고 기록하면 어떻게 할까요?
  A. 기존 기록을 수정하게 한다
  B. 별도 기록으로 추가한다 (권장)

  추천: B — 재독 시점의 생각 변화를 비교하는 것이 학습 가치가 큽니다.
  되돌리기 비용: 중간.

사용자:
B요. 1학년 때랑 3학년 때 같은 책을 읽으면 생각이 다를 테니까요.
```

→ **FR-002**로 반영되었습니다.

### 질문 3 — 토론 응답의 형식

```
Claude:
Q3. 토론에서 AI의 응답 형식을 어떻게 할까요?
  A. 선택지를 제시하는 정형 응답 (채점·분석이 쉬움)
  B. 자유 형식 대화 응답 (권장, 자연스러움)

  추천: B
  되돌리기 비용: 중간. 나중에 바꾸려면 대화 저장 구조를 조정해야 합니다.

사용자:
B. 실제 토론처럼 자연스러워야 의미가 있어요.
```

### 질문 4 — AI 호출 실패 시 처리

```
Claude:
Q4. AI 분석 호출이 실패하면 사용자에게 무엇을 보여줄까요?
  A. "잠시 후 다시 시도해주세요"만 표시
  B. 실패 사실 + 재시도 버튼 제공 (권장)
  C. 자동으로 3회 재시도 후 실패 시 안내

  추천: B — 자동 재시도는 비용이 예측 불가능해집니다.
  되돌리기 비용: 낮음.

사용자:
B로 해주세요. 자동 재시도는 돈 나가는 게 무서워요.
```

→ **FR-011**로 반영되었습니다.

> **[교육 포인트] 왜 구현 전에 물어봐야 하나요?**
> 이 4가지 질문 중 하나라도 구현 도중에 발견됐다면 이미 만든 코드를 되돌려야 했을 것입니다. 특히 1번(재생성 시 버전 보관)은 **데이터 구조 자체를 좌우**하므로, 늦게 발견될수록 수정 비용이 급격히 커집니다.

## 12.4 개인정보 질문 — 답을 미룬 사례

```
Claude:
Q5. 학생 이름·학교명을 저장할까요?
  A. 저장하지 않는다 (계정 식별자만 사용)
  B. 저장하되 암호화한다
  C. 담론 출판 시에만 임시로 입력받는다

사용자:
지금은 결정하기 어려워요. 일단 저장하지 않는 것(A)으로 진행하고,
담론 출판 기능을 만들 때 다시 논의합시다.
이 항목을 "추후 결정"으로 명시해주세요.
```

> **[실전] "지금 결정할 수 없다"도 정당한 답입니다**
> 중요한 것은 **결정하지 않았다는 사실을 문서에 남기는 것**입니다. 이렇게 하면 나중에 담론 출판 기능을 만들 때 이 항목이 다시 떠오릅니다. 결정하지 않은 채 그냥 넘어가면, AI가 임의로 이름 필드를 만들어버리고 아무도 모릅니다.

# 13부. 4단계 실전 — 계획(Plan) ★승인 게이트★

## 13.1 이 단계에서 할 일

처음으로 기술을 결정합니다. 그리고 **여러분의 승인을 받습니다.**

## 13.2 실행 프롬프트

```
사용자:
/speckit.plan

조건:
 - 기술 선택마다 왜 그것을 골랐는지 research.md 에 근거를 남길 것
 - 내 컴퓨터에서 별도 설치 없이 또는 간단한 설치로 실행 가능한 것만 고를 것
 - 헌장을 못 지키는 항목은 DEVIATION 으로 표시하고
   사유·대체 수단·복구 방법을 적을 것
 - .env 는 빈 틀만 만들 것. 키 값은 내가 직접 넣는다
 - quickstart.md 는 내가 완성 후 직접 눌러볼 시나리오로 써줄 것
 - 전문 용어는 일상 비유를 붙여 설명할 것
계획이 끝나면 요약해서 보여주고 내 승인을 받은 뒤 다음 단계로 넘어가.
```

## 13.3 AI의 제안과 승인 대화

```

 - 백엔드(서버, '주방'에 해당):  Python + FastAPI
     이유: 설치가 간단하고 예제가 많아 문제 해결이 쉽습니다.

 - 데이터 저장:                  SQLite
     이유: 파일 하나로 동작해 별도 데이터베이스 설치가 필요 없습니다.
     ('엑셀 파일 하나에 표를 여러 장 담아두는 것'과 비슷합니다)

     이유: 목록·입력폼·대화창 구성에 적합하고 자료가 풍부합니다.

     이유: 저장 응답은 즉시 주고 AI 분석은 뒤에서 진행하기 위함입니다.
     ('주문을 받아 번호표를 먼저 주고 요리는 뒤에서 하는 것')

이 계획대로 진행해도 될까요?
 - 예, 이대로 진행 (권장)
 - 일부 수정하고 싶어요

사용자:
질문 하나만요. SQLite로 하면 나중에 학생 100명이 동시에 쓸 때
문제가 생기나요? 그리고 그때 바꾸기 어렵나요?

Claude:
좋은 질문입니다.
 - 동시 쓰기가 많아지면 SQLite는 병목이 생길 수 있습니다.

   설정 변경과 데이터 이전 작업으로 전환할 수 있습니다.
   이 구조를 미리 지키도록 plan.md 에 명시해두겠습니다.

사용자:

## 데이터베이스 선택

### data-model.md — 데이터 표 구조

| 표 이름 | 저장하는 것 | 주요 항목 |
|---|---|---|
| User | 사용자 계정 | 식별자, 로그인 정보, 가입일 |
| ReadingRecord | 독서 기록 | 책 제목, 저자, 줄거리, 인상 구절, 생각, 작성일, 상태 |
| Analysis | AI 분석 결과 | 기록 참조, 버전 번호, 줄거리, 주제, 상징, 작가 의도, 인물 |
| BookRecommendation | 추천 도서 | 분석 참조, 책 제목, 저자, 추천 이유 |
| DiscussionTopic | 토론 주제 | 분석 참조, 주제 문장, 유형 |
| DiscussionSession | 토론 세션 | 기록 참조, 선택 주제, 시작일 |
| DiscussionMessage | 토론 대화 | 세션 참조, 발화자, 내용, 시각 |
| Essay | 담론 초안 | 기록 참조, 본문, 생성일, 글자 수 |

> **[개념] 왜 표를 여러 개로 나누나요?**
> 하나의 표에 모든 것을 넣으면, 토론 대화가 100번 오갔을 때 독서 기록 한 줄이 100번 반복 저장됩니다. **"여러 개 생길 수 있는 것"은 별도 표로 분리**하는 것이 원칙입니다. 독서 기록 1건에 분석 여러 버전, 분석 1건에 추천 도서 여러 권, 세션 1건에 대화 여러 개 — 이 관계가 표 분리의 근거입니다.

### quickstart.md — 완성 후 확인 시나리오

```markdown
1. 서버와 화면을 실행한 뒤 브라우저에서 접속한다
2. 회원가입 → 로그인한다
3. [+ 새 기록]을 눌러 '데미안 / 헤르만 헤세'로 기록을 저장한다
4. 목록에서 해당 기록의 상태가 "분석 중"으로 표시되는지 확인한다
5. 5분 이내에 상태가 "분석 완료"로 바뀌는지 확인한다
6. 기록을 열어 줄거리·주제·상징·작가 의도·인물 분석이 모두 있는지 확인한다
7. [비슷한 책 보기]에서 3~5권과 추천 이유가 나오는지 확인한다
8. [토론 시작]에서 주제 3개가 나오는지 확인하고 하나를 고른다
9. 3회 이상 대화를 주고받은 뒤 화면을 새로고침해 대화가 남아 있는지 확인한다
10. [담론 작성]으로 초안을 만들고 문서 파일로 내려받는다
11. 로그아웃 후 다른 계정으로 로그인해, 앞 계정의 기록이 보이지 않는지 확인한다
```

> **[실전] 비전공자가 가장 먼저 읽어야 할 문서**
> 위 11단계가 여러분이 상상한 서비스와 일치합니까? 다르면 **지금** 말해야 합니다. 특히 11번(다른 계정으로 로그인)처럼 **"되면 안 되는 것"을 확인하는 항목**이 들어 있는지 보십시오. 이런 항목이 없으면 접근 제어가 빠질 가능성이 높습니다.

# 17부. 트러블슈팅 사례집

> 바이브코딩을 하다 보면 반드시 비슷한 상황을 만납니다. 여기 모은 사례는 선행 실습 기록에서 실제로 발생한 것과, 그 유형에서 파생되는 대표적인 상황입니다.

## 17.1 API 키가 분명히 맞는데 계속 실패

**증상**: `.env`에 키를 넣었는데 AI 기능만 실행하면 인증 오류가 납니다.

**실제로 있었던 진단 과정**

> **[실전]** 이 문제는 다음 순서로 해결되었습니다. ① AI가 Anthropic API에 키를 직접 테스트 호출해 `API key is invalid` 응답을 확인했습니다. ② 새 키를 발급받아 넣었는데도 여전히 실패했습니다. ③ **실행 중인 서버 프로세스를 찾아 종료한 뒤 재시작**하자 정상 동작했습니다. ④ 브라우저에서 회원가입→로그인→AI 기능 호출까지 전 과정을 다시 실행해 확인했습니다.

**원인**: 서버 프로그램은 시작할 때 `.env`를 한 번 읽습니다. 파일을 고쳐도 **이미 돌고 있는 서버는 예전 값을 계속 씁니다.**

**해결 순서**

| 순서 | 확인 | 명령/방법 |
|---|---|---|
| 1 | 키 값 자체가 유효한가 | AI에게 "이 키로 최소 호출을 한 번 시도해봐"라고 요청 |
| 2 | `.env` 위치가 맞는가 | 프로젝트 루트인지 확인 |
| 3 | 서버를 재시작했는가 | 터미널에서 서버 종료(Ctrl+C) 후 재실행 |
| 4 | 유령 프로세스가 남았는가 | 포트를 점유한 프로세스 확인 후 종료 |
| 5 | 실제 화면에서 확인 | 회원가입→로그인→AI 기능까지 전 과정 재실행 |

> **[주의] "됐겠지"라고 추측하지 말 것**
> 위 사례의 핵심은 마지막 단계입니다. 코드를 고친 뒤 "이제 될 것"이라고 넘어가지 않고 **전 과정을 다시 실행해 확인**했습니다. 이것이 제2원칙의 실천입니다.

## 17.2 순서가 꼬여 명령이 실행되지 않음

**증상**: 체크리스트 생성 명령을 실행했더니 "계획이 없어 진행할 수 없다"며 멈춥니다.

> **[실전]** 선행 프로젝트에서 실제로 있었던 일입니다. 사용자가 계획 단계(④)보다 체크리스트 단계(⑤)를 먼저 시도했고, 도구가 이를 막았습니다. 계획을 먼저 완성한 뒤 다시 실행해 성공했습니다.

**교훈**: 순서를 지키지 않아도 도구가 친절하게 막아주고 무엇이 먼저 필요한지 알려줍니다. **오류 메시지를 끝까지 읽으십시오.** 대부분의 답이 그 안에 있습니다.

## 17.3 테스트는 통과하는데 실제로는 안 됨

**증상**: `42 passed`인데 브라우저에서는 오류가 납니다.

**원인 후보**

| 후보 | 확인 방법 |
|---|---|
| 테스트가 AI를 가짜 응답으로 대체 중 | "실제 API를 호출하는 검증을 한 번 해줘" |
| 화면(프론트엔드)은 테스트 범위 밖 | 브라우저 개발자 도구 콘솔 확인 요청 |
| 서버는 켜졌으나 화면 서버가 안 켜짐 | 터미널 두 개가 모두 실행 중인지 확인 |
| 테스트용 데이터와 실제 데이터가 다름 | 실제 입력값으로 재현 요청 |

> **[실전] 이렇게 요청하십시오**
> "테스트는 통과하는데 브라우저에서는 실패합니다. 테스트가 실제 상황과 다르게 설정된 부분이 있는지 확인하고, 실제 값으로 재현되는 테스트를 하나 추가해주세요."

## 17.4 AI가 대화 중간에 맥락을 잃음

**증상**: 조금 전 결정한 것을 AI가 다시 물어보거나, 다른 방식으로 만들기 시작합니다.

**대응**

1. 즉시 중단시키고 `docs/progress.md`를 읽게 합니다.
2. 그래도 어긋나면 새 대화를 시작하고 `progress.md`부터 읽게 합니다.
3. 반복되는 지점이면 `CLAUDE.md`에 규칙으로 명시합니다.

> **[주의] 맥락 유실은 대화를 길게 끌수록 심해집니다**
> 한 대화에서 여러 슬라이스를 연속으로 진행하지 마십시오. **슬라이스 하나가 끝나면 기록을 저장하고 새 대화로 시작**하는 것이 오히려 안정적입니다.

## 17.5 AI가 요청하지 않은 기능을 만들어 놓음

**증상**: 명세에 없던 "즐겨찾기" 버튼이 화면에 있습니다.

**대응**

```

 3) 제거 계획을 보여주고 제 승인 후 진행해주세요
```

**예방**: 프롬프트에 **"내가 요청하지 않은 기능은 추가하지 마"**를 상시 포함하고, `CLAUDE.md` 금지 사항에도 넣어두십시오.

## 17.6 어디가 문제인지조차 모르겠음

**증상**: 화면이 하얗게 뜨거나 아무 반응이 없습니다.

**질문 템플릿**

```
사용자:
지금 화면이 하얗게 뜹니다. 다음을 순서대로 확인해서 알려주세요.
 1) 서버가 실행 중입니까? 실행 명령과 출력을 보여주세요
 2) 화면 서버가 실행 중입니까? 마찬가지로 보여주세요
 3) 브라우저 콘솔에 오류가 있습니까?
 4) 서버 쪽 로그에 오류가 있습니까?
 5) 위 정보로 추정되는 원인 후보를 가능성 순으로 3개만 알려주세요
   (아직 고치지는 마세요)
```

> **[실전] "아직 고치지는 마세요"가 핵심입니다**
> 원인을 특정하기 전에 고치기 시작하면, AI가 여러 곳을 동시에 바꿔 상황이 더 복잡해집니다. **진단과 처치를 분리**하는 것은 6단계 분석 단계의 원칙과 같습니다.

## 17.7 사례별 교훈 정리

| 사례 | 교훈 |

| 맥락 유실 | 슬라이스 단위로 세션 끊고 기록으로 인계 |
| 유령 기능 | "요청하지 않은 것은 만들지 마"를 상시 지시 |
| 원인 불명 | 진단과 처치를 분리, 후보 3개를 먼저 받기 |

# 18부. 완성 후 — 실행하고, 기록하고, 내보이기

## 18.1 실행 방법 문서 만들기 (RUN.md)

구현이 끝나면 사전 준비물부터 서버 실행, 종료 방법까지 한 문서로 정리해두십시오. 몇 달 뒤에도 그대로 따라 실행할 수 있습니다.

```markdown
# 독서활동 서비스 실행 방법 (RUN.md)

## 1. 사전 준비물
- Python 3.11 이상  (python.org)
- Node.js LTS       (nodejs.org)
- Anthropic API 키  (console.anthropic.com)

## 2. 프로젝트 내려받기
git clone <저장소 주소>
cd reading-activity

## 3. 백엔드(서버) 실행
pip install -r requirements.txt
(.env 파일에 ANTHROPIC_API_KEY 값을 직접 입력)
uvicorn backend.src.main:app --reload
→ http://localhost:8000 에서 동작

## 4. 프론트엔드(화면) 실행  ※ 새 터미널 창에서
cd webapp
npm install
npm run dev
→ http://localhost:5173 에서 접속

## 5. 자동화 테스트 실행
pytest backend/tests -q

## 6. 종료 방법
각 터미널 창에서 Ctrl + C
```

> **[실전] 터미널 두 개가 번거롭다면**
> 배치파일(`.bat`) 하나로 서버와 화면을 한 번에 실행하도록 만들어두면 편리합니다. AI에게 **"실행 배치파일도 만들어줘"**라고 요청하면 됩니다.

## 18.2 설계서(기록 문서) 남기기

이 책처럼, 완성된 프로젝트도 무엇을 왜 그렇게 만들었는지 한 편의 문서로 정리해두는 것이 좋습니다.

완성한 결과물을 백업하거나 공유하려면 GitHub에 올릴 수 있습니다.

# 19부. 확장 5종 — 스킬·서브에이전트·MCP·Hooks·Plugins

> **이 부에서 답하는 질문**
> 1. 다섯 가지 확장 도구는 각각 언제 쓰는가?
> 2. 독서활동 서비스에 적용하면 어떤 모습인가?
> 3. 어떻게 만들고 어떻게 나눠주는가?

## 19.1 지금까지 배운 것, 이제 배울 것

8부~18부에서는 하나의 절차(AI-VC)로 헌장부터 구현까지 진행했습니다. 그런데 서비스가 커지면 — 학생 수가 늘고, 담론을 학부모에게 보내고, 개인정보를 다뤄야 하면 — 절차 하나만으로는 감당하기 어려운 요구가 생깁니다.

| 도구 | 정체 | 실행 위치 | 발동 방식 | 승인 게이트 |
|---|---|---|---|---|
| 스킬 | `SKILL.md` 지침 파일 | 메인 대화 | AI가 대화 내용 보고 자동 판단 | 있음(대화 중 확인) |
| 서브에이전트 | 에이전트 정의 파일 | **독립 컨텍스트** | 메인이 위임 호출 | 있음 |
| MCP 서버 | 설정 등록(`.mcp.json`) | 외부 서비스 | 도구로 호출 | 있음 |
| Hooks | 스크립트 + 설정 | 이벤트 발생 시 | **조건 충족 시 자동** | **없음** |
| Plugins | 위 넷의 묶음 | 설치 단위 | 설치 명령 | — |

## 19.2 스킬(Skill) — 반복 절차를 저장하기

### 무엇인가

스킬은 **반복되는 절차와 판단 기준을 하나의 지침 묶음으로 저장해 두었다가, 대화 속 특정 표현이 나오면 자동으로 불러오는 도구**입니다. 그 정체는 `SKILL.md`라는 파일 하나입니다.

### 언제 만드나

1. 같은 절차를 **3번 이상 반복 설명**하고 있다
2. 그 절차에 **특별한 도구 권한 제한이 필요 없다** (메인이 가진 도구를 그대로 써도 된다)

반대로 "결과만 받고 과정은 몰라도 되는" 무거운 작업이라면 다음 절의 서브에이전트가 적합합니다.

### 독서활동 예시 — `book-report-formatter`

담론 초안이 완성된 뒤 학교 제출 양식(표지·목차·본문·참고자료)으로 정리하는 작업은 매번 같은 절차를 반복합니다. 이런 반복 작업이 스킬 후보입니다.

```
---
name: book-report-formatter
description: 독서 담론(에세이) 초안이 완성된 뒤 "학교 제출용으로
  정리해줘", "양식 맞춰줘" 같은 요청을 받으면 발동. 표지·목차·본문·
  참고자료 4단 구성으로 재배치하고 글자 수 기준을 검사한다.
---

# 독서 담론 제출 양식 정리
1. 표지: 책 제목·저자·학생명·학년·작성일
2. 목차: 자동 생성
3. 본문: 기존 담론 내용을 그대로 유지하되 소제목 4개로 재구성
4. 참고자료: 인용한 구절의 페이지 번호를 각주로 정리
제약: 학교 규정상 본문 1,500~2,000자 준수. 초과 시 요약 제안.
```

```
사용자:
담론 다 됐어. 이제 학교 제출용으로 정리해줘.

Claude:
book-report-formatter 스킬을 불러왔습니다. 표지·목차·본문·참고자료
순서로 재구성하겠습니다. 현재 본문이 2,300자라 학교 기준(2,000자)을
초과합니다 — 어느 부분을 줄일지 제안해도 될까요?
```

> **[개념] `description`이 자동 발동 스위치입니다**
> 사용자가 이 문구와 비슷한 말을 하면 AI가 판단해서 본문 지침을 불러옵니다. 스킬은 **메인 에이전트가 스스로 "이 지침을 참고해야겠다"고 판단하고 이어서 대화를 계속하는 방식**이며, 다음에 볼 서브에이전트처럼 별도 컨텍스트로 넘어가지 않습니다.

## 19.3 서브에이전트(Subagent) — 통째로 위임하기

### 무엇인가

서브에이전트는 **메인과는 독립된 컨텍스트에서 시작해, 위임받은 작업만 수행하고 최종 결과 하나만 메인에 돌려주는 별도의 에이전트**입니다. 스킬이 "메인이 직접 이어서 하는 것"이라면, 서브에이전트는 **"다른 사람에게 통째로 맡기고 결과만 받는 것"**에 가깝습니다.

### 독서활동 6종 설계

6개 User Story를 그대로 서브에이전트 6개에 대응시킵니다. 한 에이전트가 여러 역할을 겸하면 지침이 복잡해지고, 결과를 검증할 때 "작성자가 자기 결과를 스스로 채점"하는 문제가 생깁니다. 그래서 **작성 역할과 검증 역할은 반드시 분리**합니다.

| 에이전트 | 역할 | 도구 | 입력 | 출력 |
|---|---|---|---|---|
| `book-analyst` | 심층 문학 분석 | Read, Write | 독서기록 | 분석보고서 |
| `book-curator` | 유사 도서 추천 | Read, Write, WebSearch | 분석보고서 | 추천목록 |
| `topic-maker` | 토론 주제 설계 | Read, Write | 분석보고서 | 토론주제 |
| `discussion-partner` | 토론 상대 | Read, Write | 주제 + 대화이력 | 대화응답 |
| `essay-writer` | 담론 집필 | Read, Write | 위 전부 | 담론초안 |
| `quality-checker` | 품질 검수 | Read | 담론초안 | 검수의견 |

### 정의 파일 예시 — book-analyst

```
---
name: book-analyst
description: 학생의 독서 기록을 받아 심층 문학 분석을 수행.
  줄거리 정리, 주제/상징 분석, 인물 분석 요청 시 사용.
tools: Read, Write
model: sonnet
---

당신은 문학 분석 전문가입니다.

입력: 독서기록 파일 경로 (줄거리·인상 구절·학생 생각)
수행: 1) 전체 줄거리 재구성  2) 핵심 주제 3가지
     3) 주요 상징과 의미  4) 작가의 의도  5) 인물 분석
제약: 학생이 인용한 구절은 반드시 분석에 연결할 것.
     학생 수준(중고등)에 맞는 어휘 사용.
출력: records/분석보고서.md 에 저장 후,
     핵심 요지 5줄 요약만 보고할 것.
```

### 정의 파일 예시 — book-curator

```
---
name: book-curator
description: 독서 분석보고서를 받아 비슷한 주제·상징을 다룬
  도서를 추천. "비슷한 책 추천해줘" 요청 시 사용.

당신은 학교 도서관 사서입니다.

입력: records/분석보고서.md
수행: 1) 핵심 주제·상징과 겹치는 도서 3~5권 탐색
     2) 각 책마다 추천 이유를 분석보고서의 근거와 연결
     3) 학생 학년 수준에 맞는 난이도인지 확인
제약: 실제 존재하는 책만 추천. 확인 안 되면 "확인 필요"로 표시.
출력: records/추천목록.md 저장 후, 책 제목과 한 줄 이유만 보고.
```

### 정의 파일 예시 — quality-checker

```
---
name: quality-checker
description: 완성된 담론 초안의 품질을 검수. "검수해줘",
  "이대로 제출해도 될까" 요청 시 사용. 집필은 하지 않는다.
tools: Read
model: sonnet
---

당신은 독서 담론 검수자입니다. 글을 고치지 않고 의견만 냅니다.

입력: records/담론초안.md, records/분석보고서.md, records/독서기록.md
수행: 1) 담론의 주장이 분석보고서의 근거와 연결되는가
     2) 학생 본인의 생각이 남아 있는가 (AI 문체로 덮이지 않았는가)
     3) 인용 구절이 실제 독서기록에 있는 것인가
     4) 글자 수가 규정 범위인가
제약: 절대 원문을 수정하지 말 것. 발견 사항만 목록으로 보고.
출력: 문제 항목과 근거를 목록으로 보고. 문제 없으면 "이상 없음".
```

> **[주의] 왜 quality-checker의 도구가 Read뿐인가**
> 검수자가 글을 고칠 수 있으면, 문제를 지적하는 대신 조용히 고쳐버립니다. 그러면 **무엇이 문제였는지 사람이 영영 모릅니다.** 도구 권한을 제한하는 것 자체가 설계입니다. 이는 6단계 분석이 "읽기 전용"인 것과 같은 원리입니다.

### 메인과 연결되는 세 통로

1. **프롬프트(입력)** — 서브에이전트는 메인 대화를 보지 못하므로, 메인이 넘기는 지시문에 파일 경로·판단 기준·보고 형식을 모두 담아야 합니다.
2. **최종 메시지(출력)** — 서브에이전트의 마지막 응답 하나만 메인에게 돌아옵니다. 사용자에게는 보이지 않으므로 메인이 중계·요약합니다.
3. **파일(공유 작업대)** — 분석 보고서처럼 큰 산출물은 프롬프트로 주고받지 않고 파일로 저장해, 다음 서브에이전트가 경로만 받아 읽게 합니다.

> **[주의] 서브에이전트는 매번 백지에서 시작합니다**
> 직전 대화의 맥락, 학생이 이미 말한 내용, 이전 서브에이전트의 상세 결과 — 이 중 어느 것도 자동으로 넘어가지 않습니다. 메인이 프롬프트에 명시하지 않은 정보는 서브에이전트에게 **존재하지 않는 정보**입니다.

### 호출 순서와 병렬 가능성

```
독서기록.md
     │
     ▼
 book-analyst  ──▶ 분석보고서.md
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
  book-curator     topic-maker    (병렬 가능 — 서로 의존 없음)
   추천목록.md      토론주제.md
                        │
                        ▼
              discussion-partner ──▶ 토론기록.md
                        │
                        ▼
                  essay-writer ──▶ 담론초안.md
                        │
                        ▼
                 quality-checker ──▶ 검수의견
```

## 19.4 MCP 서버 — 외부 서비스에 연결하기

### 무엇인가

MCP 서버는 Claude를 노션·구글드라이브·이메일·슬랙 같은 외부 서비스에 연결하는 **표준 규격의 플러그**입니다. 스킬·서브에이전트가 "무엇을, 어떻게 할지"를 정의한 지침 파일이라면, MCP 서버는 대개 지침을 새로 쓰는 게 아니라 **이미 만들어진 서버를 프로젝트에 등록하는 설정 작업**에 가깝습니다.

### 독서활동 예시 — 담론 완성 시 자동 저장·발송

담론이 완성되면 ① 노션에 학생별 포트폴리오로 저장하고, ② 학부모 이메일로 완성 알림을 보내는 시나리오입니다.

```json
// .mcp.json (프로젝트 루트)
{
  "mcpServers": {
    "notion": {
      "command": "npx",
      "args": ["-y", "@notionhq/notion-mcp-server"],
      "env": { "NOTION_API_KEY": "${NOTION_API_KEY}" }
    },
    "gmail": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-gmail"]
    }
  }
}
```

```
사용자:
담론 파일 완성됐어. 노션에 올리고 학부모님께 완료 메일 보내줘.

Claude:
notion MCP 서버로 "독서활동 포트폴리오" 데이터베이스에 항목을 만들고,
gmail MCP 서버로 학부모님께 완료 안내 메일 초안을 작성했습니다.
메일 발송 전에 내용을 확인해 주시겠어요?
```

> **[개념] MCP는 "쓰는 것"이 아니라 "연결하는 것"**
> 스킬·서브에이전트는 지침을 직접 작성하지만, MCP 서버는 API 키를 발급받아 설정 파일에 등록하는 절차가 대부분입니다. **API 키 같은 민감 정보는 AI가 대신 입력하지 않고 사용자가 직접 넣는다**는 원칙(8.9절)이 MCP 연결에도 동일하게 적용됩니다.

## 19.5 Hooks — 조건이 맞으면 무조건 실행

### 무엇인가

Hooks는 특정 사건(세션 시작, 파일 저장 전, 도구 실행 전후 등)이 발생하면 **사람의 승인 없이 자동으로 실행되는 스크립트**입니다. 스킬·서브에이전트가 "AI가 판단해서 부르는 것"이라면, Hooks는 **"조건이 맞으면 무조건 실행되는 것"**이라는 점이 결정적으로 다릅니다.

### 독서활동 예시 — 개인정보 자동 마스킹

학생이 독서 기록에 실수로 실명·학교명을 그대로 적어 저장하려 할 때, 저장 직전에 감지해 경고하는 Hook입니다.

```json
// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Write",
      "hooks": [{
        "type": "command",
        "command": "python3 scripts/check_pii.py"
      }]
    }]
  }
}
```

`check_pii.py`는 저장하려는 내용에 실명 패턴이나 학교명이 있으면 저장을 막고 마스킹을 제안하는 간단한 스크립트입니다. 이 Hook은 학생이나 AI가 깜빡하더라도 **항상 동작합니다.**

> **[주의] Hooks에는 승인 게이트가 없습니다**
> 13부·14부에서 계획·작업분해 단계가 승인 없이는 진행되지 않는다고 배웠습니다. Hooks는 정반대입니다. 그래서 **파일을 삭제하거나 외부로 데이터를 전송하는 Hook은 특히 신중하게 설계**해야 하며, 초보자는 **"막고 경고만 하는" 방어적 Hook부터** 시작하는 것을 권합니다.

### 방어적 Hook 예시 3가지

| Hook | 시점 | 하는 일 |
|---|---|---|
| 개인정보 차단 | 파일 저장 전 | 실명·학교명·연락처 패턴 감지 시 저장 차단 |
| `.env` 커밋 방지 | git 작업 전 | 스테이징 목록에 `.env`가 있으면 중단 |
| 진행 기록 상기 | 세션 시작 | `docs/progress.md` 최종 갱신일이 3일 이상 지났으면 경고 |

## 19.6 Plugins — 하나로 묶어 나눠주기

### 무엇인가

Plugins는 스킬·서브에이전트·MCP 서버·Hooks를 **하나의 설치 패키지로 묶어 다른 사람에게 배포하는 단위**입니다.

```
# 플러그인 설치 명령 예시
/plugin marketplace add <배포자>/<플러그인 이름>
```

### 독서활동 예시 — reading-activity-toolkit

19.2~19.5에서 만든 것들을 다른 학교 선생님에게도 통째로 나눠주고 싶다면, 아래처럼 하나의 폴더로 묶습니다.

```
reading-activity-toolkit/
├── plugin.json
├── skills/
│   └── book-report-formatter/SKILL.md
├── agents/
│   ├── book-analyst.md
│   ├── book-curator.md
│   ├── topic-maker.md
│   ├── discussion-partner.md
│   ├── essay-writer.md
│   └── quality-checker.md
├── hooks/
│   └── check_pii.py
└── .mcp.json   (notion, gmail 서버 설정)
```

```json
// plugin.json
{
  "name": "reading-activity-toolkit",
  "version": "1.0.0",
  "description": "학생 독서활동 기록·분석·토론·담론 작성을 돕는 도구 모음"
}
```

> **[개념] 언제 플러그인으로 묶나요?**
> 혼자 쓸 때는 스킬·에이전트 파일을 개별적으로 두어도 충분합니다. 하지만 여러 사람에게 **"설치 한 번으로"** 나눠주고 싶다면 Plugins으로 묶는 것이 정답입니다.

## 19.7 다섯 가지 선택 흐름도

```
반복되는 작업이 있다
   │
   ├─ 과정을 보면서 이어서 하고 싶다 ──────────▶ 스킬
   │
   ├─ 결과만 받으면 되고, 작업이 무겁다 ───────▶ 서브에이전트
   │      └ 검증 역할이면 도구를 Read로 제한
   │
   ├─ 외부 서비스(노션·메일·드라이브)가 필요하다 ▶ MCP 서버
   │
   ├─ 사람이 깜빡해도 항상 지켜져야 한다 ──────▶ Hooks
   │      └ 처음에는 "막고 경고만" 하는 것부터
   │
   └─ 위의 것들을 남에게 통째로 주고 싶다 ─────▶ Plugins
```

## 19.8 확장 로드맵 — 단계별 도입 순서

| 단계 | 도입 | 이유 |
|---|---|---|
| 1 | 아무것도 안 씀 (AI-VC만) | 절차 자체에 익숙해지는 것이 먼저 |
| 2 | Hooks 1개 (`.env` 커밋 방지) | 가장 큰 사고를 가장 싸게 막음 |
| 3 | 스킬 1~2개 | 3번 이상 반복 설명한 절차부터 |
| 4 | 서브에이전트 | 분석·검수처럼 역할 분리가 필요할 때 |
| 5 | MCP 서버 | 외부 연동이 실제로 필요해졌을 때 |
| 6 | Plugins | 남에게 나눠줄 때 |

> **[주의] 1단계를 건너뛰지 마십시오**
> 확장 도구는 절차를 대체하지 않습니다. 승인 게이트·증거 기반 보고·기록 연속성이 몸에 붙지 않은 상태에서 도구만 늘리면, **자동화된 혼란**이 될 뿐입니다.

# 20부. 비용·보안·개인정보 — 아직 남은 숙제

> 이 부는 "완벽한 성공담"이 아니라 **있는 그대로**를 다룹니다. AI-VC로 만든 것을 실제로 쓰기 시작하면 반드시 마주치게 되는 세 가지 문제입니다.

## 20.1 왜 이것을 "숙제"라고 부르는가

선행 프로젝트에서 명세 품질 체크리스트 23개 항목 중 두 개 — **AI 사용 비용**과 **사용자 코드를 외부 AI에 보내는 것에 대한 개인정보 처리** — 는 끝까지 의도적으로 체크되지 않은 채 남았습니다.

> **[실전] 왜 그냥 처리하지 않고 숙제로 남겼나**
> 이 두 항목은 코드를 어떻게 짜느냐의 문제가 아니라, **실제 서비스를 운영할 사람이 결정해야 할 정책**의 문제이기 때문입니다. 체크리스트는 검토자(사람) 소유의 문서라 AI가 임의로 체크할 수 없습니다. 이것 자체가 이 책이 가르치려는 태도입니다 — **모르는 걸 안다고 하지 않고, 결정할 수 없는 걸 마음대로 결정하지 않는 것.**

## 20.2 비용 — AI 호출은 공짜가 아닙니다

### 비용이 발생하는 지점

독서활동 서비스에서 AI를 부르는 곳은 다음과 같습니다.

| 기능 | 호출 빈도 | 입력 크기 | 출력 크기 | 비용 민감도 |
|---|---|---|---|---|
| 책 내용 심층 분석 | 기록 1건당 1회(재생성 시 추가) | 중 | 큼 | 중 |
| 유사 도서 추천 | 분석 1건당 1회 | 중 | 소 | 낮음 |
| 토론 주제 제안 | 분석 1건당 1회 | 중 | 소 | 낮음 |
| **토론 대화** | **세션당 10회 이상** | 누적 증가 | 중 | **높음** |
| 담론 생성 | 기록 1건당 1회 | 큼 | 큼 | 중 |

> **[주의] 토론 대화가 가장 위험합니다**
> 대화가 길어질수록 **이전 대화 전체를 매번 다시 보내야** 하므로 입력 크기가 누적됩니다. 10회째 대화의 입력은 1회째의 수 배가 됩니다. 이것이 계획 단계에서 "토론 응답에는 효율 모델"을 선택한 실질적 이유입니다.

### 비용을 관리하는 5가지 장치

| 장치 | 내용 | 난이도 |
|---|---|---|
| 1. 제공사 콘솔 한도 설정 | 월 사용 한도를 계정 차원에서 설정 | 쉬움 — **반드시 하십시오** |
| 2. 작업별 모델 분리 | 품질이 중요한 곳만 상위 모델 | 계획 단계에서 결정 |
| 3. 사용자별 횟수 제한 | 월 N건 등 (FR-013) | 중간 |
| 4. 대화 길이 상한 | 토론 20회 초과 시 새 세션 유도 | 중간 |
| 5. 자동 재시도 금지 | 실패 시 사용자가 직접 재시도 (FR-011) | 쉬움 |

> **[주의] 실제 단가는 이 책에 적지 않았습니다**
> AI 서비스의 요금은 모델과 시점에 따라 달라집니다. **반드시 제공사의 최신 요금표를 직접 확인**하고, 여러분의 예상 사용량으로 직접 계산하십시오. 계산 방법은 다음과 같습니다.
>
> `월 예상 비용 = (기능별 1회 비용 × 기능별 월 호출 횟수)의 합계`
>
> 이 계산에 필요한 "1회 비용"은 요금표의 입력·출력 단가와 예상 글자 수로 구합니다. AI에게 **"내 예상 사용량으로 월 비용을 계산해줘. 단가는 내가 알려주는 값을 쓰고, 추정하지 마"**라고 요청하는 것이 안전합니다.

### 최소한 이것만은

1. **오늘 당장 제공사 콘솔에서 월 한도를 설정하십시오.** 이것 하나가 최악의 사고를 막습니다.
2. 개발 중에는 실제 AI 호출을 최소화하십시오. 자동화 테스트는 가짜 응답으로 대체하고, 슬라이스 완료 시 한 번만 실제로 호출합니다.
3. 무한 반복 위험이 있는 코드(재시도 루프)를 특히 조심하십시오.

## 20.3 보안 — 키와 비밀 정보

### 3대 원칙

| 원칙 | 내용 |
|---|---|
| 1. 키 값은 사람이 직접 넣는다 | AI에게 값을 알려주지 않습니다. 빈 틀만 만들게 합니다. |
| 2. 키는 `.env`에만 둔다 | 코드 안에 직접 쓰지 않습니다. |
| 3. `.env`는 저장소에 올리지 않는다 | `.gitignore`에 반드시 포함합니다. |

### 유출 시 대응 절차

```
1. 즉시 해당 키를 제공사 콘솔에서 폐기(revoke)한다
2. 새 키를 발급받아 .env 를 갱신한다
3. 실행 중인 서버를 종료하고 재시작한다
4. 사용 이력을 확인해 비정상 호출이 있었는지 점검한다
5. 커밋 이력에서 제거하되, 4번을 생략하지 않는다
```

> **[주의] 이력에서 지우는 것만으로는 부족합니다**
> 공개 저장소에 올라간 키는 자동으로 수집되는 것으로 알려져 있습니다. 이력을 정리하기 **전에** 먼저 키를 폐기하십시오. 순서가 반대이면 의미가 없습니다.

### 그 밖의 점검 항목

- [ ] 비밀번호를 그대로 저장하지 않고 단방향 변환(해시)해 저장하는가
- [ ] 로그인하지 않은 사람이 남의 데이터를 볼 수 없는가
- [ ] 오류 메시지가 내부 구조를 지나치게 노출하지 않는가
- [ ] 로그에 개인정보나 키가 찍히지 않는가

## 20.4 개인정보 — 학생의 글을 외부로 보낸다는 것

### 문제의 성격

독서활동 서비스는 **학생이 쓴 글을 외부 AI 서비스로 전송**합니다. 그 글에는 학생의 생각·감정·때로는 가정사가 담길 수 있습니다.

이것은 기술 문제가 아니라 **정책과 법률의 문제**입니다.

> **[주의] 이 책은 법률 자문을 제공하지 않습니다**
> 실제로 학생을 대상으로 서비스를 운영하려면, 개인정보 보호 관련 법령과 아동·청소년 대상 서비스에 적용되는 요건을 **반드시 전문가에게 확인**하십시오. 이 책은 "무엇을 확인해야 하는지"까지만 안내합니다.

### 최소한 검토해야 할 항목

| 항목 | 질문 |
|---|---|
| 수집 최소화 | 실명·학교명이 정말 필요한가? 식별자만으로 안 되는가? |
| 고지와 동의 | 외부 AI로 전송된다는 사실을 사용자가 알고 있는가? |
| 미성년자 | 사용자가 미성년자라면 보호자 동의가 필요한가? |
| 보관 기간 | 데이터를 언제까지 보관하고 언제 삭제하는가? |
| 삭제 요청 | 사용자가 삭제를 요청하면 어떻게 처리하는가? |
| 외부 서비스 정책 | 사용하는 AI 제공사가 입력 데이터를 어떻게 다루는가? |

### 이 프로젝트가 택한 처리

12부에서 개인정보 저장 여부에 대해 "지금은 결정하기 어렵다"는 답이 나왔고, 그 결정은 **1차 범위에서 실명·학교명을 저장하지 않는 것**으로 정리되었습니다. 그리고 16부 US6 착수 전 게이트에서 다음이 결정되었습니다.

1. 외부 AI 전송 사실을 최초 로그인 시 고지하고, 동의해야 AI 기능을 사용할 수 있게 함(FR-014)
2. 사용자당 월 생성 횟수를 10건으로 제한함(FR-013)

> **[실전] 이것이 완결된 답은 아닙니다**
> 위 처리는 학습 프로젝트 수준의 조치입니다. 실제 서비스라면 보관 기간·삭제 절차·보호자 동의 등을 추가로 설계해야 합니다. 중요한 것은 **미결 항목을 미결로 남기고 추적한 것**이며, 그것이 이 방법론이 요구하는 정직함입니다.

## 20.5 20부 요약

1. 비용·보안·개인정보는 코드의 문제가 아니라 **정책의 문제**이며, AI가 대신 결정할 수 없습니다.
2. 오늘 당장 할 일은 두 가지입니다 — **제공사 콘솔에서 월 한도 설정**, **`.gitignore`에 `.env` 확인**.
3. 미결 항목은 체크리스트에 미체크로 남기고 Task로 추적하십시오. 조용히 넘어가는 것이 가장 나쁜 처리입니다.
4. 실제 사용자를 대상으로 하는 순간, 이 책의 범위를 넘어섭니다. 전문가 검토를 받으십시오.

과정을 보며 이어서 하고 싶으면 스킬, 결과만 받으면 되고 작업이 무거우면 서브에이전트입니다(19.7절 흐름도).

**Q27. Hooks가 위험하다는데 왜 씁니까?**
사람이 깜빡해도 항상 지켜져야 하는 것(예: `.env` 커밋 방지)이 있기 때문입니다. 방어적 Hook부터 시작하십시오.

**Q28. MCP 서버를 직접 만들어야 합니까?**
대부분은 이미 만들어진 것을 등록만 하면 됩니다. 직접 만드는 것은 이 책의 범위를 넘습니다.

**Q29. 플러그인은 언제 필요합니까?**
여러 사람에게 "설치 한 번으로" 나눠줄 때입니다. 혼자 쓸 때는 불필요합니다.

**Q30. 이 방법론을 팀에서 쓸 수 있습니까?**
가능합니다. 다만 팀 규모에서는 코드 리뷰·CI·배포 절차가 추가로 필요하며, 이 책은 그 부분을 다루지 않습니다.

# 부록 2-D. 오류 메시지 대응 사전

| 메시지 유형 | 흔한 원인 | 첫 번째 대응 |
|---|---|---|
| `command not found` / `'xxx'은(는) 인식되지 않습니다` | 설치 후 터미널을 새로 열지 않음 | 터미널 재시작 |
| `ModuleNotFoundError` | 라이브러리 미설치 | `pip install -r requirements.txt` |
| `Cannot find module` | Node 라이브러리 미설치 | `npm install` |
| `Address already in use` / 포트 사용 중 | 이전 서버가 아직 실행 중 | 해당 프로세스 종료 후 재실행 |
| `API key is invalid` | 키 오류 또는 서버 미재시작 | 키 확인 → **서버 재시작** (17.1절) |
| `401 Unauthorized` | 로그인 토큰 만료 | 재로그인 |
| `403 Forbidden` | 접근 권한 없음 | 본인 소유 데이터인지 확인 (정상 동작일 수 있음) |
| `404 Not Found` | 주소 오타 또는 데이터 없음 | 요청 주소와 대상 존재 여부 확인 |
| `500 Internal Server Error` | 서버 내부 오류 | 서버 터미널의 상세 오류 로그 확인 요청 |
| 화면이 하얗게 뜸 | 화면 서버 미실행 또는 JS 오류 | 17.6절 질문 템플릿 사용 |
| 테스트 `FAILED` (RED 단계) | 정상 | 그대로 진행 |
| 테스트 `FAILED` (GREEN 이후) | 구현 미완 또는 회귀 | "실패 내용과 원인을 설명해줘. 아직 고치지 말고" |

> **[실전] 오류 메시지를 그대로 붙여넣으십시오**
> 요약하지 말고 **전문을 그대로** AI에게 주십시오. 마지막 몇 줄에 핵심이 있는 경우가 많은데, 사람이 요약하면 그 부분이 빠지는 일이 흔합니다.
