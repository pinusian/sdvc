# 이 책을 여는 글

## 프로그래밍을 몰라도 만들 수 있는 시대, 그 다음의 질문

2025년을 지나며 "코드를 한 줄도 못 쓰는 사람이 웹서비스를 만들었다"는 이야기는 더 이상 놀라운 소식이 아니게 되었습니다. AI에게 "이런 걸 만들어줘"라고 말하면 실제로 동작하는 화면이 나옵니다. 이것을 사람들은 **바이브코딩(Vibe Coding)**이라고 부릅니다.

문제는 그 다음입니다. 만들어진 것을 조금 고치려고 했더니 어디를 건드려야 할지 모릅니다. AI에게 "이 부분만 바꿔줘"라고 했더니 멀쩡하던 다른 화면이 망가집니다. 2주 전에 왜 그렇게 만들었는지 나도 모르고 AI도 모릅니다. 결국 처음부터 다시 만들게 됩니다.

이 책은 그 "다음 질문"에 답하기 위해 쓰였습니다. 빠르게 만드는 법이 아니라, **만든 것을 내가 계속 통제할 수 있게 만드는 법**을 다룹니다.

## 이 책이 제안하는 것 — AI-VC

이 책은 GitHub이 공개한 **Spec Kit**이라는 명세 기반 개발(Spec-Driven Development) 도구를 뿌리로 삼되, 프로그래밍 비전공자가 혼자서도 끝까지 완주할 수 있도록 재정립한 방법론을 제안합니다. 그 이름이 **AI-VC(AI-assisted Vibe Coding)**입니다.

AI-VC는 새로운 프로그래밍 언어도, 새로운 프레임워크도 아닙니다. **AI와 함께 무언가를 만들 때 지켜야 할 순서와 규칙의 묶음**입니다. 7개의 단계와 3개의 원칙, 그리고 각 단계에서 만들어지는 문서들로 구성되어 있습니다.

> **[핵심 한 줄]**
> AI-VC는 AI의 속도를 그대로 쓰면서, "무엇을 만들지"와 "제대로 만들어졌는지"에 대한 판단 권한만은 끝까지 사람이 쥐고 있게 하는 작업 절차입니다.

## 누구를 위한 책인가

이 책은 다음과 같은 분들을 독자로 상정하고 썼습니다.

1. Claude(클로드)나 ChatGPT를 업무에 써본 적이 있고, Claude Cowork로 문서 정리나 자료 조사를 해본 경험이 있는 분
2. 프로그래밍 전공자가 아니며, `for문`이나 `함수`가 무엇인지 설명할 자신이 없는 분
3. 그럼에도 "내 아이디어를 실제로 동작하는 서비스로 만들어보고 싶다"는 목표가 있는 분
4. 창업 기획, 사내 업무 자동화, 교육 콘텐츠 제작 등 구체적인 용도를 마음에 두고 있는 분

반대로, 이미 실무 개발 경험이 있고 Git·테스트·CI/CD에 익숙한 분에게는 이 책의 설명이 다소 장황하게 느껴질 수 있습니다. 그런 분은 제1권 2부(방법론 구조)와 제2권 실전 기록만 읽으셔도 충분합니다.

## 이 책의 구성 — 두 권으로 나눈 이유

|---|---|---|---|
| 제1권 | 방법론편 | 왜, 무엇을, 어떤 순서로 | 시작하기 전 · 판단이 필요할 때 |
| 제2권 | 실전편 | 독서활동 서비스 따라 만들기 | 손을 움직여 실습할 때 |

제1권은 "지도"이고 제2권은 "여행 기록"입니다. 지도만 보면 실감이 나지 않고, 여행 기록만 보면 왜 그 길로 갔는지 알 수 없습니다. 두 권을 나란히 놓고 보시는 것을 권합니다.

## 표기 규칙

이 책은 다음 규칙을 일관되게 사용합니다.

1. **굵은 글씨**는 처음 등장하는 개념어이거나 반드시 기억해야 할 문장입니다.
2. `고정폭 글씨`는 실제로 컴퓨터에 입력하는 명령어, 파일 이름, 폴더 경로입니다.
3. 회색 인용 상자는 세 종류입니다.
   - `[개념]` 용어를 일상 비유로 풀어 설명합니다.
   - `[실전]` 실제 프로젝트에서 있었던 일을 옮긴 것입니다.
   - `[주의]` 건너뛰면 나중에 반드시 대가를 치르는 항목입니다.
4. 화면 대화 예시는 "사용자:"와 "Claude:"로 구분해 표시합니다.
5. **출처와 검증 수준 표기**: 이 책의 실전 기록은 두 개의 선행 자료 — ① Spec Kit 기반 'AI Code Learning Platform' 개발 전 과정 기록, ② vibecoding-guide 스킬 기반 '독서활동 서비스' 개발 기록 — 에서 가져왔습니다. 두 자료에 근거가 없고 이 책에서 새로 구성한 예시는 `[구성 예시]`로 표기했으며, 독자의 환경에 따라 결과가 달라질 수 있는 명령은 "환경에서 확인 필요"로 명시했습니다.

## 이 책을 읽는 세 가지 방법

1. **통독형** — 제1권을 처음부터 끝까지 읽고, 제2권으로 넘어갑니다. 방법론을 강의하거나 남에게 설명해야 하는 분께 권합니다.
2. **병행형** — 제1권 1~2부만 읽고 바로 제2권 실습으로 넘어간 뒤, 막힐 때마다 제1권 3부의 해당 단계를 펼칩니다. 가장 많은 분께 권하는 방식입니다.
3. **참조형** — 이미 무언가를 만들고 있는 중이라면, 지금 막힌 지점에 해당하는 절만 찾아 읽습니다. 각 부의 첫 페이지에 "이 부에서 답하는 질문"을 적어두었습니다.

# 1부. 왜 AI-VC인가

> **이 부에서 답하는 질문**
> 1. 바이브코딩은 정확히 무엇이며, 무엇이 문제인가?
> 2. 왜 "그냥 AI에게 만들어달라고 하면" 안 되는가?
> 3. AI-VC는 그 문제를 어떻게 해결하는가?

## 1.1 바이브코딩이란 무엇인가

바이브코딩이란 개발자가 코드를 한 줄씩 직접 타이핑하는 대신, **AI에게 "무엇을 만들고 싶은지"를 우리가 평소 쓰는 말(자연어)로 설명하면 AI가 실제 코드를 작성해주는 개발 방식**을 말합니다.

"분위기(vibe)에 따라 코딩한다"는 뜻에서 붙은 이름입니다. 정확한 문법을 몰라도, 원하는 결과물의 느낌만 전달하면 AI가 알아서 구현해준다는 점이 특징입니다.

> **[개념] 통역사에게 일을 맡기는 것과 비슷합니다**
> 외국어를 못하는 사람이 현지에서 집을 구한다고 생각해 보십시오. 통역사에게 "역에서 가깝고 볕 잘 드는 방"이라고 말하면 통역사가 알아서 부동산과 협상해줍니다. 편리합니다. 그런데 계약서에 무슨 조항이 들어갔는지 나는 모릅니다. 나중에 문제가 생기면 통역사를 다시 불러야 하고, 그 통역사가 자리에 없으면 아무것도 할 수 없습니다. 지금의 바이브코딩이 딱 이 상태입니다.

### 무엇이 달라졌나

과거에 프로그램을 만들려면 세 가지가 필요했습니다.

1. 문법 지식 — 어떤 언어로 어떻게 쓰는가
2. 도구 사용 능력 — 편집기, 터미널, 버전관리
3. 설계 능력 — 무엇을 어떤 구조로 만들 것인가

AI는 이 중 **1번을 거의 완전히, 2번을 상당 부분 대신해줍니다.** 그러나 3번은 대신해주지 못합니다. 더 정확히 말하면, AI는 3번을 "대신 해주는 척"할 수 있습니다. 물어보지 않고 알아서 결정해버리기 때문입니다. 이 지점이 모든 문제의 출발점입니다.

## 1.2 실제로 일어나는 일 — 30분과 3일

바이브코딩을 처음 해본 분들이 공통으로 겪는 시간 곡선이 있습니다.

| 시점 | 하는 일 | 걸린 시간 | 기분 |
|---|---|---|---|
| 1일차 오전 | "독서 기록 앱 만들어줘" → 화면이 나옴 | 30분 | 놀라움 |
| 1일차 오후 | 기능 3개 추가 → 다 됨 | 2시간 | 자신감 |
| 2일차 | "저장 버튼이 가끔 안 눌려" → 고쳐달라고 함 | 4시간 | 당황 |
| 3일차 | 고쳤더니 목록 화면이 깨짐 → 다시 고침 → 저장이 또 안 됨 | 하루 종일 | 좌절 |
| 4일차 | 처음부터 다시 만들기로 결정 | — | 포기 |

이 곡선의 원인은 AI의 성능이 아닙니다. **2일차부터 "내가 무엇을 만들었는지"를 아무도 모르는 상태였다는 것**이 원인입니다.

> **[실전] 요리 비유**
> 선행 프로젝트 기획서에 나온 비유를 그대로 옮깁니다. 지금의 바이브코딩은 셰프(AI)가 요리를 다 만들어줘서 맛있게 먹었지만, 나중에 간이 안 맞으면 어디를 고쳐야 할지 모르는 상황과 같습니다. 반면 셰프가 "이 재료는 이래서 넣었고, 이 순서로 해야 이 맛이 나요"라고 설명해주면 나중에 내 입맛대로 수정할 수 있습니다. AI-VC가 하려는 일이 바로 이 "설명을 남기게 하는 일"입니다.

## 1.3 바이브코딩의 네 가지 함정

선행 자료 두 건에서 공통으로 지적된 함정을 정리하면 다음 네 가지입니다.

### 함정 ① 애매한 요청 → 애매한 결과

AI는 물어보지 않으면 스스로 빈칸을 채웁니다. "회원 가입 기능 만들어줘"라고 하면 AI는 이메일 인증을 넣을지 말지, 비밀번호를 몇 자로 할지, 중복 가입을 어떻게 막을지를 **자기 마음대로 결정합니다.** 그 결정은 대화창 어디에도 남지 않고, 코드 안에만 숨어 있습니다.

### 함정 ② 검증 수단의 부재

"다 만들었습니다"라는 AI의 말을 검증할 방법이 없습니다. 화면이 뜨면 된 것 같지만, 다른 사용자가 동시에 접속하면 어떻게 되는지, 이상한 값을 넣으면 어떻게 되는지는 아무도 확인하지 않았습니다.

> **[주의] AI는 실행하지 않고도 "통과했습니다"라고 말할 수 있습니다**
> 이것이 두 번째 함정이 가장 교묘하게 되살아나는 지점입니다. 선행 자료(vibecoding-guide v1.2.0)는 이 문제를 규칙으로 금지했습니다 — 실제 실행 출력 없이 "테스트가 모두 통과합니다", "정상 동작합니다", "88개 테스트 통과" 같은 표현을 쓰지 못하게 한 것입니다. 이 책의 AI-VC 제2원칙(증거 기반 보고)이 여기에서 나왔습니다.

### 함정 ③ 기록의 부재

몇 주 뒤에 다시 열어보면 "이게 왜 이렇게 되어 있지?" 상태가 됩니다. 더 심각한 것은 **AI도 모른다**는 점입니다. AI는 대화창이 바뀌면 이전 내용을 전혀 기억하지 못합니다. 새 대화를 열거나 대화가 길어져 맥락이 압축되면, 어제까지 알고 있던 것을 오늘은 모릅니다.

### 함정 ④ 통제권의 상실

가장 무서운 함정입니다. 처음에는 내가 AI에게 일을 시켰는데, 어느 순간부터 AI가 만든 것을 내가 따라가며 이해하려 애쓰게 됩니다. 무엇을 승인하고 무엇을 막아야 할지 판단할 근거가 없기 때문입니다.

| 함정 | 증상 | AI-VC의 대응 장치 |
|---|---|---|
| ① 애매한 요청 | 원하지 않은 기능이 만들어짐 | 2단계 명세 + 3단계 명확화 |
| ② 검증 부재 | "될 거예요"로 넘어감 | TDD + 증거 기반 보고 원칙 |
| ③ 기록 부재 | 몇 주 뒤 아무도 모름 | 단계별 산출 문서 + progress.md |
| ④ 통제권 상실 | 승인 판단을 못 함 | 승인 게이트(계획·작업분해) |

## 1.4 함정의 공통 원인 — 말은 사라지고 코드만 남는다

네 가지 함정을 한 문장으로 압축하면 이렇습니다. **대화창에서 오간 결정은 사라지고, 그 결정의 결과물인 코드만 남습니다.**

집을 지을 때를 생각해 보십시오. 완성된 집만 남고 설계도가 없다면, 벽 안에 전선이 어디로 지나가는지 알 수 없습니다. 못 하나 박는 일이 큰 사고가 됩니다. 소프트웨어에서 설계도에 해당하는 것이 **명세서·계획서·작업목록**입니다. AI-VC는 이 세 가지를 반드시 파일로 남기게 강제합니다.

> **[개념] 왜 "파일로" 남겨야 하나요?**
> 대화창의 내용은 AI가 다음 세션에 기억하지 못합니다. 그러나 파일은 다릅니다. 프로젝트 폴더에 `spec.md`라는 파일이 있으면, 새 대화를 열어도 AI에게 "이 파일 읽어봐"라고 시킬 수 있습니다. 즉 파일은 **사람과 AI가 공유하는 기억장치**입니다.

## 1.5 AI-VC의 한 줄 정의

이 모든 문제의식을 담아 AI-VC를 정의하면 다음과 같습니다.

> **AI-VC(AI-assisted Vibe Coding)**
> AI에게 코드 작성을 맡기되, ① 무엇을 만들지를 문서로 먼저 확정하고, ② 정해진 지점에서 반드시 사람의 승인을 받으며, ③ 완료 주장은 실행 증거로만 인정하고, ④ 모든 결정과 진행 상황을 파일로 남겨 다음 세션으로 인계하는, 비전공자를 위한 7단계 개발 절차.

음악에 비유하자면 이렇습니다. 일반 바이브코딩이 **즉흥 연주**라면, AI-VC를 적용한 바이브코딩은 **악보를 보며 하는 즉흥 연주**입니다. 즉흥성과 속도는 그대로 살아 있지만, 어디로 가는지는 정해져 있습니다.

## 1.6 이 방법론이 겨냥하지 않는 것

정직하게 한계를 밝혀 두겠습니다. AI-VC는 다음을 보장하지 않습니다.

1. **상업 서비스 수준의 품질** — 이 책의 절차를 그대로 따라도, 수만 명이 동시에 쓰는 서비스를 안정적으로 운영하는 것은 별개의 문제입니다. 부하 분산, 장애 대응, 데이터 백업은 이 책의 범위를 벗어납니다.
2. **보안 감사의 대체** — 개인정보를 실제로 수집하는 서비스를 운영하려면 법적 검토가 별도로 필요합니다. 이 책은 그 필요성을 인식시키는 데까지만 다룹니다.
3. **개발자 없이 모든 것이 가능해짐** — AI-VC는 "혼자서 프로토타입과 소규모 내부 도구를 끝까지 완주할 수 있게" 해줍니다. 그 이상은 사람 개발자의 검토가 필요합니다.
4. **속도의 향상** — 오히려 처음 며칠은 더 느립니다. 문서를 쓰는 시간이 추가되기 때문입니다. AI-VC의 이득은 2주차 이후에 나타납니다.

> **[주의] "이렇게까지 해야 하나요?"라는 질문에 대하여**
> 아주 작은 것(개인용 계산기, 한 번 쓰고 버릴 스크립트)을 만든다면 이 절차는 과합니다. AI-VC가 필요해지는 기준선은 대략 이렇습니다 — **기능이 3개를 넘거나, 화면이 3개를 넘거나, 만드는 데 3일 이상 걸리거나, 나 아닌 다른 사람이 쓸 예정이라면** 절차를 갖추는 편이 결국 빠릅니다. 이것을 이 책에서는 **3·3·3 기준**이라고 부르겠습니다.

## 1.7 1부 요약

1. 바이브코딩은 문법 지식의 장벽을 없앴지만, 설계와 판단의 책임까지 없애지는 못했습니다.
2. 네 가지 함정(애매한 요청·검증 부재·기록 부재·통제권 상실)은 모두 "결정이 파일로 남지 않는다"는 하나의 원인에서 나옵니다.
3. AI-VC는 7단계 절차와 3대 원칙으로 그 결정들을 파일에 붙잡아 둡니다.
4. 3·3·3 기준(기능 3개, 화면 3개, 3일)을 넘으면 절차를 갖추는 것이 결과적으로 빠릅니다.

# 2부. AI-VC 방법론의 구조

> **이 부에서 답하는 질문**
> 1. AI-VC는 어디에서 왔고, 원본과 무엇이 다른가?
> 2. 7단계는 각각 무엇을 하는 단계인가?
> 3. 3대 원칙은 무엇이며 왜 그것들인가?

## 2.1 뿌리 — GitHub Spec Kit과 명세 기반 개발

AI-VC의 뿌리는 GitHub이 공개한 **Spec Kit**(`github.com/github/spec-kit`)입니다. Spec Kit은 **명세 기반 개발(Spec-Driven Development, SDD)**이라는 사고방식을 AI 코딩 도구 위에서 실제로 실행할 수 있게 만든 도구 모음입니다.

명세 기반 개발의 핵심 주장은 단순합니다.

> 코드가 아니라 **명세(spec)**를 프로젝트의 중심 산출물로 삼는다. 코드는 명세로부터 파생되는 것이지, 그 반대가 아니다.

전통적인 개발에서도 요구사항 정의서는 늘 있었습니다. 다만 실무에서는 "문서는 문서대로, 코드는 코드대로" 따로 노는 일이 흔했습니다. AI 시대에 이 관계가 뒤집힙니다. **AI는 문서를 읽고 코드를 씁니다.** 따라서 문서가 정확하면 코드도 정확해지고, 문서가 애매하면 코드도 애매해집니다. 문서가 처음으로 "실행되는 자산"이 된 것입니다.

Spec Kit은 이 사고방식을 8개의 슬래시 명령(`/speckit.*`)으로 구현했습니다. 사용자가 각 명령을 순서대로 실행하면, 헌장 → 명세 → 명확화 → 계획 → 체크리스트 → 작업분해 → 분석 → 구현의 파이프라인이 진행됩니다.

## 2.2 Spec Kit에서 무엇을 가져오고 무엇을 바꿨나

AI-VC는 Spec Kit의 골격을 그대로 계승합니다. 다만 **비전공자 단독 사용**이라는 조건을 만족시키기 위해 세 가지를 조정했습니다.

| 구분 | Spec Kit(원형) | AI-VC(이 책) | 조정 이유 |
|---|---|---|---|
| 진입 방식 | 8개 명령어를 순서대로 암기·입력 | "만들고 싶어" 한마디로 시작, AI가 순서를 안내 | 비전공자는 명령어 순서를 기억하지 못함 |
| 단계 수 | 8단계(체크리스트 별도) | 7단계(체크리스트를 계획 단계에 흡수) | 실습에서 순서 충돌이 가장 잦았던 단계를 통합 |
| 승인 지점 | 명시적 규정 없음(도구가 되묻는 정도) | 4·5단계에 **승인 게이트** 명문화 | 되돌리기 비용이 가장 큰 두 지점을 고정 |
| 완료 보고 | 규정 없음 | **증거 기반 보고** 원칙 강제 | AI의 미검증 완료 선언을 차단 |
| 세션 연속성 | git 이력에 의존 | `docs/progress.md` 6블록 표준화 | git 로그는 "다음에 뭘 할지"를 알려주지 않음 |
| 대상 프로젝트 | 팀 개발 전반 | 1인 + AI, 소규모 서비스 | 실습 완주 가능성 우선 |

> **[개념] 왜 체크리스트 단계를 없앴나요?**
> 원형 Spec Kit에는 `/speckit.checklist`라는 독립 단계가 있습니다. 이것은 "코드를 검사하는 체크리스트"가 아니라 **명세 문장 자체의 품질을 점검하는 체크리스트**를 만드는 단계입니다. 개념적으로 훌륭하지만, 선행 프로젝트 실습에서 이 단계는 계획(plan) 없이는 실행되지 않아 순서가 꼬이는 일이 실제로 발생했습니다. AI-VC에서는 이 기능을 없애지 않고 4단계(계획) 산출물의 일부로 흡수했습니다. 즉 **단계 수는 줄었지만 점검 항목은 그대로 남아 있습니다.**

## 2.3 AI-VC 7단계 전체 지도

AI-VC의 전체 흐름은 다음과 같습니다.

```
[사람이 준비]                [AI-VC 7단계]                    [산출물]

아이디어 메모        ──▶  1단계 헌장(Constitution)        constitution.md
                                    │                       프로젝트 절대 규칙
                                    ▼
서비스 기획서        ──▶  2단계 명세(Specify)             spec.md
(plan_specify.md)                   │                       User Story·FR·SC
                                    ▼
                          3단계 명확화(Clarify)            spec.md 갱신
                                    │                       Clarifications 절 추가
                                    ▼
                          4단계 계획(Plan)  ★승인★        plan.md / research.md
                                    │                       data-model.md
                                    │                       contracts/ · quickstart.md
                                    ▼                       checklists/
                          5단계 작업분해(Tasks) ★승인★    tasks.md
                                    │                       T001~Tnnn 작업 목록
                                    ▼
                          6단계 분석(Analyze)              분석 보고서(읽기 전용)
                                    │
                                    ▼
                          7단계 구현(Implement)            소스코드 + 테스트
                                                            docs/progress.md
                                                            docs/task-reports/
```

각 단계를 한 문장으로 요약하면 다음과 같습니다.

| 단계 | 한글 명칭(영문/명령어) | 한 문장 정의 | 승인 게이트 |
|---|---|---|---|
| 1 | 헌장 (Constitution / `/speckit.constitution`) | 무슨 일이 있어도 지킬 규칙을 정한다 | — |
| 2 | 명세 (Specify / `/speckit.specify`) | **무엇을** 만들지만 정한다(기술 이야기 금지) | — |
| 3 | 명확화 (Clarify / `/speckit.clarify`) | 애매한 지점을 질문·확답으로 없앤다 | — |
| 4 | 계획 (Plan / `/speckit.plan`) | **어떻게** 만들지 기술을 정한다 | ★ 필수 |
| 5 | 작업분해 (Tasks / `/speckit.tasks`) | 실행 가능한 작은 작업으로 쪼갠다 | ★ 필수 |
| 6 | 분석 (Analyze / `/speckit.analyze`) | 세 문서 간 모순을 교차 점검한다 | — |
| 7 | 구현 (Implement / `/speckit.implement`) | 테스트 먼저 쓰고 코드를 만든다 | (슬라이스별 확인) |

> **[개념] 왜 하필 이 순서인가**
> 이 순서는 **되돌리기 비용이 싼 것부터 비싼 것 순서**입니다. 헌장을 바꾸는 데는 5분이 걸리지만, 이미 만든 코드 구조를 바꾸는 데는 며칠이 걸립니다. 그래서 결정의 무게가 가벼운 순서대로 앞에 배치하고, 무거운 결정일수록 뒤로 미룹니다. 3단계 명확화를 반드시 구현 전에 두는 이유도 같습니다 — 그 질문에 대한 답이 데이터 구조를 좌우하기 때문입니다.

## 2.4 제1원칙 — 승인 게이트(Approval Gate)

### 원칙의 내용

**4단계(계획)와 5단계(작업분해)를 마친 시점에, 사용자가 명시적으로 "예"라고 답하기 전까지 AI는 다음 단계로 넘어가지 않는다.**

### 왜 하필 그 두 지점인가

되돌리기 비용을 그래프로 그리면 이 두 지점에서 곡선이 급격히 꺾입니다.

| 지점 | 여기서 잘못되면 | 되돌리는 비용 |
|---|---|---|
| 1단계 헌장 이후 | 규칙 문장 몇 개 수정 | 5분 |
| 2~3단계 명세 이후 | 요구사항 문장 수정 | 30분 |
| **4단계 계획 이후** | 데이터베이스 구조·기술 스택 변경 | **며칠** |
| **5단계 작업분해 이후** | 이미 만든 코드의 순서·구조 재배치 | **며칠~재작업** |
| 7단계 구현 중 | 개별 버그 수정 | 수십 분 |

즉 승인 게이트는 "가장 비싼 실수를 가장 싸게 막는 지점"에 놓인 것입니다.

### 실제로 어떻게 작동하는가

```
Claude:
다음과 같이 만들 것을 제안합니다.
 - 백엔드(서버): Python FastAPI — 설치가 간단하고 예제가 많습니다
 - 데이터 저장: SQLite — 파일 하나로 동작, 별도 설치 불필요
 - 화면: React — 목록·입력폼·대화창에 적합
 - AI 모델: 품질이 중요한 정리 작업에는 상위 모델,
           빈도 높은 대화 응답에는 효율 모델

이 계획대로 진행해도 될까요?
 - 예, 이대로 진행 (권장)
 - 일부 수정하고 싶어요

사용자:
예, 이대로 진행해주세요.
```

> **[주의] 이해하지 못한 채 "예"라고 답하지 마십시오**
> 승인은 형식이 아니라 실질이어야 합니다. 모르는 용어가 나오면 **"그 단어를 초등학생에게 설명하듯 다시 설명해주세요"**라고 요구하십시오. 이것은 무례한 요구가 아니라 방법론이 요구하는 정당한 절차입니다. 제1권 5부에서 승인 시점에 물어야 할 질문 목록을 따로 정리했습니다.

## 2.5 제2원칙 — 증거 기반 보고(Evidence-Based Reporting)

### 원칙의 내용

**AI는 실제 실행 결과 없이 "완료", "통과", "정상 동작"을 주장할 수 없다. 완료를 보고할 때는 실행한 명령과 그 출력을 함께 제시한다.**

### 왜 필요한가

AI는 코드를 작성한 뒤 "이 정도면 될 것"이라는 추론만으로 완료를 선언할 수 있습니다. 악의가 아니라 구조적 특성입니다. 문제는 비전공자 사용자가 **그 주장을 검증할 수단이 없다**는 점입니다. 코드를 읽지 못하기 때문입니다.

증거 기반 보고는 이 비대칭을 해소합니다. 코드를 못 읽어도 **"실행 출력"이 붙어 있는지는 누구나 확인할 수 있기 때문입니다.**

### 금지 표현과 대체 표현

| 금지 (실행 없이) | 대체 |
|---|---|
| "테스트가 모두 통과합니다" | `$ pytest backend/tests -q` → `88 passed in 12.4s` 출력 첨부 |
| "정상 동작합니다" | "브라우저에서 회원가입→로그인→저장까지 직접 실행해 확인했습니다" |
| "88개 테스트 통과" (출력 없이) | 실행 출력에서 인용한 수치만 사용 |
| "아마 될 겁니다" | "이 환경에서는 실행하지 못했습니다. `pytest backend/tests -q`로 직접 확인해주십시오" |

> **[실전] 사용자가 외워야 할 한 문장**
> AI가 출력 없이 "다 됐습니다"라고 하면 이렇게 되물으십시오.
> **"실행한 명령과 그 결과를 그대로 보여주세요."**
> 이 한 문장이 이 책 전체에서 가장 실용적인 문장일 수 있습니다.

## 2.6 제3원칙 — 기록 연속성(Continuity of Record)

### 원칙의 내용

**작업을 마칠 때 진행 상황을 `docs/progress.md`에 남기고, 세션을 시작할 때 그 파일을 가장 먼저 읽는다.**

### 왜 필요한가

AI는 대화창이 바뀌면 이전 내용을 전혀 기억하지 못합니다. 예전에는 사람이 매번 "우리가 어디까지 했더라"를 다시 설명해야 했습니다. 기록 연속성 원칙은 이 부담을 **AI 쪽으로 옮깁니다.** AI가 기록을 읽고 사람에게 요약해 확인받는 구조입니다.

```
사용자: AI바이브코딩 최신버전 작동

Claude: 이전 세션 기록을 찾았습니다.
        - 완료: US1 책 읽기 기록, US2 AI 책 내용 정리
        - 진행 중: US5 토론의 장 — RED 테스트까지 작성 완료
        - 다음 할 일: 자유 형식 응답으로 바꾸는 GREEN 구현
        여기서 이어서 진행할까요?

사용자: 예
```

### progress.md의 6블록 구조

| 블록 | 항목 | 핵심 질문 |
|---|---|---|
| ① | 지금 어디까지 왔나 | 완료 / 진행 중 / 미착수 |
| ② | 방금 세션에서 한 일 | 무엇을, 어느 파일에서, 왜 |
| ③ | 검증 증거 | 실제 실행한 명령과 출력 |
| ④ | **다음 세션이 할 일** | 즉시 실행 가능한 문장, 체크박스 |
| ⑤ | 막힌 것 / 결정 대기 | 사람의 판단이 필요한 항목 |
| ⑥ | 알아둘 함정 | 반복해서 걸린 문제 |

> **[개념] ④번이 왜 핵심인가**
> git 커밋 로그는 "무엇을 했는가"만 알려주고 "다음에 무엇을 해야 하는가"는 알려주지 않습니다. ④번 블록은 그 공백을 메웁니다. 작성 요령은 **"토론 기능 마무리"처럼 모호하게 쓰지 말고, "`backend/src/api/discussion.py`의 `POST /sessions` 응답을 자유 형식으로 바꾸고 테스트 재실행"처럼 즉시 실행 가능한 문장으로 쓰는 것**입니다.

## 2.7 산출물 지도 — 어떤 파일이 언제 생기나

AI-VC를 한 바퀴 돌면 프로젝트 폴더에 다음 파일들이 남습니다. 이 목록 자체가 방법론의 결과물입니다.

| 폴더/파일 | 생성 단계 | 이 파일만 봐도 알 수 있는 것 |
|---|---|---|
| `.specify/memory/constitution.md` | 1단계 | 이 프로젝트가 절대 어기지 않기로 한 규칙 |
| `specs/00N-기능명/spec.md` | 2·3단계 | 이 기능이 **무엇을** 하기로 되어 있는지 |
| `specs/00N-기능명/plan.md` | 4단계 | **어떻게** 만들기로 했는지 |
| `specs/00N-기능명/research.md` | 4단계 | **왜** 그 기술을 골랐는지(근거) |
| `specs/00N-기능명/data-model.md` | 4단계 | 어떤 데이터를 어떤 표로 저장하는지 |
| `specs/00N-기능명/contracts/` | 4단계 | 화면과 서버가 주고받는 규격 |
| `specs/00N-기능명/quickstart.md` | 4단계 | 완성 후 사람이 직접 확인할 시나리오 |
| `specs/00N-기능명/checklists/` | 4단계 | 명세 문장 품질 점검표 |
| `specs/00N-기능명/tasks.md` | 5단계 | 어떤 순서로 만들지(T001~) |
| `backend/`, `webapp/` | 7단계 | 실제 동작하는 프로그램 |
| `backend/tests/` | 7단계 | 그것이 동작한다는 증거 |
| `docs/progress.md` | 7단계(계속 갱신) | 지금 어디까지 왔고 다음에 뭘 할지 |
| `docs/task-reports/` | 7단계 | 기능별 완료 보고 |

> **[개념] 폴더 이름 앞의 세 자리 숫자**
> `specs/001-todo-management`, `specs/004-task-learning-content`처럼 기능 폴더에는 세 자리 번호가 붙습니다. 이는 **개발한 순서**를 뜻합니다. 나중에 방향이 바뀌어 쓰지 않게 된 기능(예: 001)도 삭제하지 않고 남겨두는 것이 원칙입니다. "이 프로젝트가 원래 무엇이었는지"를 추적할 수 있게 하기 위해서입니다.

## 2.8 역할 분담 — 사람은 결정, AI는 실행

AI-VC 전체를 관통하는 역할 분담을 표로 정리하면 다음과 같습니다.

| 항목 | 사람의 역할 | AI의 역할 |
|---|---|---|
| 무엇을 만들지 | **결정** | 정리·문서화 |
| 기술 선택 | 승인 | 후보 제시 + 근거 설명 |
| 작업 순서 | 승인 | 분해·의존관계 계산 |
| 코드 작성 | — | **전담** |
| 테스트 작성 | — | **전담** |
| 실행 결과 확인 | 최종 확인 | 실행 + 출력 제시 |
| 체크리스트 완료 표시 | **전담**(AI 금지) | 항목 생성만 |
| 위험 작업(삭제·공개 업로드) | **승인 필수** | 사전 확인 후 실행 |
| 방향 전환 | **결정** | 영향 범위 분석 |

> **[주의] 체크리스트에 AI가 체크하지 못하게 하는 이유**
> 선행 프로젝트에서 명세 품질 체크리스트 23개 항목 중 두 개(AI 사용 비용 한도, 사용자 코드를 외부 AI에 전송하는 개인정보 처리)는 끝까지 의도적으로 체크되지 않은 채 남았습니다. 이는 실수가 아니라 원칙이었습니다. 이 두 항목은 코드를 어떻게 짜느냐의 문제가 아니라 **서비스를 운영할 사람이 결정해야 할 정책**이기 때문입니다. AI가 임의로 체크해버렸다면, 결정되지 않은 사안이 결정된 것처럼 묻혔을 것입니다.

2. 7단계는 되돌리기 비용이 싼 결정부터 비싼 결정 순서로 배열되어 있습니다.

4. 한 바퀴를 돌면 13종의 문서·폴더가 남으며, 이 산출물 자체가 방법론의 성과물입니다.

# 3부. AI-VC 7단계 상세

> **이 부에서 답하는 질문**
> 1. 각 단계에서 정확히 무슨 일이 일어나는가?
> 2. 그 단계의 산출물을 내가 어떻게 읽고 판단해야 하는가?
> 3. 흔히 저지르는 실수는 무엇인가?

이 부의 각 절은 동일한 6단 구성을 따릅니다.

1. **무엇을 하는 단계인가** — 정의
2. **일상 비유** — 개념 잡기
3. **실제 대화** — 화면에서 벌어지는 일
4. **산출물** — 어떤 파일이 생기고 무엇이 들어가는가
5. **체크포인트** — 다음 단계로 넘어가기 전 확인할 것
6. **흔한 실수** — 미리 알면 피할 수 있는 것

## 3.1 1단계 — 헌장(Constitution)

### 무엇을 하는 단계인가

헌장은 **이 프로젝트에서 무슨 일이 있어도 지킬 규칙**을 정하는 문서입니다. 한 번 정하면 이후 모든 단계(명세·계획·작업분해·구현)가 이 규칙을 기준으로 진행됩니다. 6단계 분석에서는 **헌장을 어기는 것이 무조건 심각한 문제(CRITICAL)로 자동 분류**될 만큼 강한 권위를 가집니다.

### 일상 비유

> **[개념] 회사의 사규(社規)**
> 신입사원이 들어올 때마다 "출근 시간을 몇 시로 할까요?"를 매번 새로 정하지 않습니다. 사규에 이미 적혀 있기 때문입니다. 헌장은 프로젝트의 사규입니다. 규칙이 없으면 "이번엔 테스트를 써야 하나 말아야 하나"를 매 순간 즉흥적으로 결정하게 되고, 그 결정은 매번 달라집니다.

### 실제 대화

```
Claude:
이번 프로젝트에서 절대 지켜야 할 규칙을 골라주세요. (여러 개 선택 가능)
 - TDD 필수 (권장)
 - 보안 규칙: API 키·비밀번호 커밋 금지 (권장)
 - 기록 의무: 완료마다 결과 문서화 (권장)
 - 커밋 컨벤션 (권장)
 - 직접 입력

사용자:
전부 다 좋아요. 추가로, 학생 개인정보(이름·학교)는 반드시
암호화해서 저장한다는 것도 넣어주세요.
```

> **[실전] 처음이라면 "전부 다 좋아요"로 충분합니다**
> 권장 항목은 선행 프로젝트에서 실제로 효과가 검증된 것들입니다. 익숙해진 뒤에 여러분의 상황에 맞는 조항을 덧붙이십시오. 위 예시에서 사용자가 추가한 "개인정보 암호화" 조항이 바로 그런 경우입니다.

### 산출물

`.specify/memory/constitution.md` 한 파일입니다. 이 파일에 담기는 조항의 유형은 대체로 다음과 같습니다.

| 유형 | 예시 조항 | 실무적 의미 |
|---|---|---|
| 개발 규율 | 테스트를 반드시 구현보다 먼저 쓴다(NON-NEGOTIABLE) | 7단계 진행 순서를 강제 |
| 보안 | API 키·비밀번호는 절대 커밋하지 않는다 | `.gitignore` 설정으로 이어짐 |
| 구조 | 모듈러 모놀리스 구조를 따른다 | 4단계 폴더 설계로 이어짐 |
| 기록 | 기능 완료 시마다 작업 보고서를 남긴다 | `docs/task-reports/` 생성 |
| 커밋 | `{type}: {제목} - {TDD단계} ({작업번호})` 형식 | 이력 추적 가능성 확보 |
| 도메인 | 학생 개인정보는 암호화해 저장한다 | 데이터 모델 설계 제약 |

### 버전과 변경 기록

헌장은 "한 번 정하면 끝"이 아닙니다. 선행 프로젝트에서는 서비스 방향 자체가 바뀌자(할일 관리 학습 앱 → AI 코드 학습 서비스) 헌장을 v1.0.0에서 **v2.0.0으로 올려 전면 교체**했습니다. 중요한 것은 바뀌었다는 사실과 이유를 남기는 것입니다. 그 프로젝트는 파일 맨 위에 `Sync Impact Report`라는 주석 블록을 두어 무엇이 왜 바뀌었는지 스스로 기록했습니다.

| 버전 자릿수 | 올리는 경우 | 예 |
|---|---|---|
| MAJOR (2.0.0) | 프로젝트 성격 자체가 바뀜 | 서비스 방향 전면 전환 |
| MINOR (1.1.0) | 조항 추가 | 개인정보 암호화 조항 신설 |
| PATCH (1.0.1) | 문구 명확화 | 표현만 다듬음 |

### 체크포인트

- [ ] 조항이 "지켰는지 안 지켰는지 판별 가능한" 문장인가? ("좋은 코드를 쓴다"는 판별 불가, "테스트를 먼저 쓴다"는 판별 가능)
- [ ] 절대 양보하지 않을 조항에 `NON-NEGOTIABLE` 표시를 했는가?
- [ ] 이 프로젝트에서 다룰 민감정보(개인정보·결제정보 등)에 대한 조항이 있는가?
- [ ] 조항 수가 15개를 넘지 않는가? (너무 많으면 아무도 안 지킵니다)

### 흔한 실수

1. **너무 많은 조항** — 처음부터 30개를 만들면 4단계에서 절반이 DEVIATION으로 표시됩니다. 5~11개가 적정선입니다.
2. **측정 불가능한 조항** — "사용자 친화적으로 만든다" 같은 조항은 아무 역할도 하지 못합니다.
3. **환경을 고려하지 않은 조항** — "PostgreSQL과 Docker를 사용한다"는 조항을 넣었는데 정작 내 컴퓨터에 둘 다 설치되어 있지 않은 경우가 실제로 발생합니다(3.4절 참조).

## 3.2 2단계 — 명세(Specify)

### 무엇을 하는 단계인가

명세 단계는 **"어떻게 만들지"가 아니라 "무엇을 만들지"만 순수하게 정의**하는 단계입니다. 이 단계의 산출물인 `spec.md`에는 프로그래밍 언어나 데이터베이스 종류 같은 기술 이야기가 **전혀 등장하지 않습니다.** 오직 "사용자가 무엇을 할 수 있어야 하는가"만 다룹니다.

> **[개념] 건축으로 치면 "설계도"가 아니라 "요구조건표"**
> "방 3개, 남향, 주차 2대, 예산 5억" — 이것이 명세입니다. "철근콘크리트 라멘조, 단열재는 준불연 등급" — 이것은 다음 단계(계획)입니다. 이 둘을 섞으면 나중에 기술을 바꿀 때 요구사항까지 흔들립니다.

### 세 가지 구성 요소

명세서는 세 가지 요소로 이루어집니다.

| 요소 | 형식 | 예시 |
|---|---|---|
| **User Story(사용자 스토리)** | "사용자는 ~할 수 있다" + 우선순위(P1/P2/P3) | US1(P1) 사용자는 책을 읽고 기록을 남길 수 있다 |
| **기능 요구사항(FR)** | "시스템은 ~해야 한다" + 번호 | FR-002 시스템은 같은 책에 대해 여러 번 기록을 남길 수 있도록 허용해야 한다 |
| **성공 기준(SC)** | 숫자로 측정 가능한 목표 | SC-001 업로드 후 5분 이내에 완성된 결과를 확인할 수 있다 |

여기에 **인수 시나리오(Acceptance Scenario)**가 덧붙습니다. "주어진(Given) — 할 때(When) — 그러면(Then)" 형식으로 쓰는데, 이것이 나중에 7단계에서 **자동화된 테스트로 그대로 옮겨집니다.**

```
Given 로그인한 사용자가 독서 기록 3건을 가지고 있을 때
When  목록 화면에 진입하면
Then  최근 작성순으로 3건이 모두 표시된다
```

### 우선순위를 매기는 법

P1/P2/P3는 "중요도"가 아니라 **"없으면 서비스가 성립하지 않는 정도"**로 매깁니다.

| 등급 | 기준 | 독서활동 서비스 예 |
|---|---|---|
| P1 | 이것이 없으면 서비스라고 부를 수 없음 | 독서 기록 작성, AI 내용 정리 |
| P2 | 있으면 가치가 크게 오르지만 없어도 성립 | 유사 도서 추천, 토론 |
| P3 | 편의 기능, 나중에 붙여도 무방 | 담론 출판, 휴지통/복구 |

> **[실전] 우선순위가 곧 개발 순서입니다**
> 5단계에서 작업을 쪼갤 때 P1부터 완성합니다. 그래서 P1만 끝난 시점에도 **동작하는 최소 제품(MVP)**을 브라우저에서 확인할 수 있습니다. 선행 프로젝트에서는 User Story 1(업로드)만 끝난 시점에 이미 실물 확인이 가능했습니다.

### 산출물

`specs/00N-기능명/spec.md`. 선행 프로젝트의 실제 규모를 참고로 제시하면 다음과 같습니다.

| 항목 | 개수 |
|---|---|
| User Story | 6개 |
| 기능 요구사항 FR | 26개 (FR-001 ~ FR-026) |
| 성공 기준 SC | 6개 (SC-001 ~ SC-006) |
| 가정(Assumptions) | 범위에서 제외한 것 명시 |

**가정(Assumptions) 절을 반드시 쓰십시오.** 여기에는 "이번에 만들지 않기로 한 것"을 적습니다. 예를 들어 선행 프로젝트는 "사용자가 업로드한 코드를 실제로 실행하지 않는다(AI가 시뮬레이션만 한다)"를 가정에 명시했습니다. 이 한 줄이 나중에 수십 시간을 아낍니다.

### 체크포인트

- [ ] `spec.md` 어디에도 프로그래밍 언어·DB·프레임워크 이름이 없는가?
- [ ] 모든 FR이 "시스템은 ~해야 한다"로 끝나는가?
- [ ] 모든 SC에 숫자가 들어 있는가?
- [ ] "이번에는 하지 않을 것"이 가정 절에 적혀 있는가?
- [ ] User Story마다 인수 시나리오가 최소 1개 이상 있는가?

### 흔한 실수

1. **기술을 섞어 쓰기** — "React로 목록 화면을 만든다"는 명세가 아니라 계획입니다.
2. **측정 불가능한 성공 기준** — "빠르게 처리된다" → "5분 이내에 결과를 확인할 수 있다"로 고쳐야 합니다.
3. **한 문장에 여러 요구사항** — FR 하나에 "저장하고 알림을 보내고 목록을 갱신한다"를 다 넣으면 나중에 무엇이 안 됐는지 특정할 수 없습니다.
4. **기획서 없이 시작** — 이것이 가장 흔하고 가장 뼈아픈 실수입니다. 다음 상자를 보십시오.

> **[주의] 결과 품질은 "프롬프트의 정교함"보다 "입력 자료의 충실함"에 좌우됩니다**
> 선행 프로젝트에서 사용자가 2단계에 입력한 프롬프트는 `/speckit.specify @plan_specify.md` 한 줄이 전부였습니다. 대신 그 사용자는 사전에 **A4 10페이지 분량의 서비스 기획서**를 준비해두고 `@` 기호로 그 파일을 입력값으로 지정했습니다. AI에게 "학습 서비스 만들어줘"라고만 하면 AI는 세부 사항을 **추측**해야 하지만, 구체적 기획서가 있으면 AI는 **정리**만 하면 됩니다. 기획서 쓰는 법은 제1권 5.1절에서 다룹니다.

## 3.3 3단계 — 명확화(Clarify)

### 무엇을 하는 단계인가

아무리 꼼꼼하게 명세를 써도 "이 경우는 어떻게 되는 거지?"라는 질문이 반드시 남습니다. 명확화 단계는 **AI가 `spec.md`를 다시 읽으며 애매한 지점을 스스로 찾아내고, 최대 5개까지 질문을 던져 사람의 확답을 받아 명세에 즉시 반영**하는 단계입니다.

### 일상 비유

> **[개념] 계약서 검토 미팅**
> 계약서 초안을 받아 읽다가 "여기 '즉시'라고 되어 있는데 며칠 이내를 말하는 겁니까?"라고 묻는 것과 같습니다. 계약을 이행하기 시작한 뒤에 그 질문을 하면 이미 늦습니다.

### 실제로 오간 질문의 성격

선행 프로젝트에서 실제로 오간 질문 4개의 유형을 보면, 명확화가 무엇을 잡아내는지 분명해집니다.

| 유형 | 질문의 성격 | 늦게 발견되면 |
|---|---|---|
| 경계값 | 파일 크기 상한, 글자 수 제한은? | 검증 로직 전면 수정 |
| 상태 전이 | 재생성 시 이전 버전은 남기나 지우나? | **데이터 구조 자체를 다시 설계** |
| 타이밍 | 실습 문제를 언제 생성하나(업로드 즉시 vs 요청 시)? | **백그라운드 작업 구조 전면 변경** |
| 예외 | AI 호출이 실패하면 사용자에게 무엇을 보여주나? | 화면 흐름 재작업 |

> **[실전] 가장 비싼 질문은 "언제"입니다**
> 위 표에서 굵게 표시한 두 항목은 데이터 구조와 처리 구조를 좌우합니다. 특히 "실습 문제를 언제 생성하는가"는 백그라운드 작업 설계 자체를 결정하므로, 구현 도중에 답이 바뀌면 이미 만든 코드를 상당 부분 버려야 합니다. **명확화 단계는 "가장 저렴할 때 미리 결정하는" 단계입니다.**

### 답변 요령

AI는 각 질문에 **자신이 추천하는 답(Recommended)**을 함께 제시합니다. 여러분은 세 가지 방식으로 답할 수 있습니다.

1. 추천안 수락 — "예" 또는 보기 문자(A/B/C)
2. 다른 보기 선택 — 이유를 한 줄 덧붙이면 명세에 근거가 함께 기록됩니다
3. 직접 입력 — 보기에 없는 답을 서술

> **[주의] "잘 모르겠으니 알아서 해주세요"는 피하십시오**
> 이 답변은 함정 ①(애매한 요청)을 명확화 단계에서 되살립니다. 정말 판단이 어렵다면 **"이 선택지 각각의 장단점과, 나중에 바꾸려면 얼마나 어려운지 알려주세요"**라고 되물으십시오. AI가 되돌리기 비용을 설명하면 대개 판단이 섭니다.

### 산출물

`spec.md`가 갱신됩니다. 두 곳이 바뀝니다.

1. **Clarifications 절 신설** — 질문/답 형태로 그대로 기록
2. **관련 절 즉시 반영** — 기능 요구사항, 예외 상황(Edge Cases) 절에 반영. 선행 프로젝트에서는 답변이 `FR-009a`, `FR-016a`처럼 **새 요구사항 번호로 추가**되었습니다.

- [ ] 답변한 내용이 `spec.md`의 Clarifications 절에 실제로 적혔는가?
- [ ] 그 답변이 기능 요구사항에도 반영되었는가? (기록만 되고 반영이 안 되는 경우가 있습니다)
- [ ] 아직 결정하지 못한 것이 있다면 "미결정"으로 명시되어 있는가?

## 3.4 4단계 — 계획(Plan) ★승인 게이트★

### 무엇을 하는 단계인가

계획 단계에서 **처음으로 "무엇으로 만들 것인가"라는 기술적 이야기가 등장**합니다. 프로그래밍 언어, 데이터베이스, 외부 서비스(AI API) 선택, 폴더 구조, 그리고 헌장을 제대로 지키고 있는지 스스로 점검하는 표까지 이 단계에서 만들어집니다.

**이 단계는 AI-VC의 첫 번째 승인 게이트입니다.** 사용자가 명시적으로 승인하기 전까지 다음 단계로 넘어가지 않습니다.

### 이 단계에서 결정되는 것들

| 결정 항목 | 선행 프로젝트의 선택 | 선택 이유(research.md에 기록) |
|---|---|---|
| 백엔드 언어·프레임워크 | Python + FastAPI | 설치가 간단하고 예제가 많음 |
| 데이터 저장 | SQLite | 파일 하나로 동작, 별도 설치 불필요 |
| 화면 | React (TypeScript) | 목록·입력폼·대화창 구성에 적합 |
| AI 제공사 | Anthropic (Claude) | 사용자가 직접 선택 |
| AI 모델(고품질 작업) | 상위 모델 | 교재 생성 품질이 서비스 핵심 |
| AI 모델(빈도 높은 작업) | 효율 모델 | 채점·Q&A는 호출이 잦아 비용 민감 |
| 백그라운드 처리 | FastAPI BackgroundTasks | Celery+Redis 미설치 환경 대체 |

> **[개념] 백엔드와 프론트엔드**
> 식당으로 비유하면 **프론트엔드는 홀**, **백엔드는 주방**입니다. 손님이 보고 만지는 메뉴판·테이블이 프론트엔드이고, 실제로 재료를 손질하고 요리하고 재고를 관리하는 곳이 백엔드입니다. 손님은 주방을 보지 못하지만, 주방이 없으면 아무것도 나오지 않습니다.

### Constitution Check — 계획이 헌장을 지키는지 스스로 채점하기

계획 문서 안에는 **헌장 점검표**가 들어갑니다. 각 헌장 조항에 대해 이 계획이 PASS인지 DEVIATION(이탈)인지 스스로 표시하는 표입니다.

| 헌장 조항 | 판정 | 비고 |
|---|---|---|
| 테스트 우선(TDD) | PASS | 모든 작업을 RED→GREEN 순서로 배열 |
| 비밀정보 커밋 금지 | PASS | `.env`를 `.gitignore`에 등록 |
| PostgreSQL 사용 | **DEVIATION** | 로컬 미설치 → SQLite로 대체, 운영 전환 시 변경 지점 명시 |
| Celery+Redis 비동기 | **DEVIATION** | 미설치 → BackgroundTasks로 동일 목적 달성 |
| Docker 컨테이너화 | **DEVIATION** | 학습 목적상 보류, 추후 과제로 기록 |

> **[주의] DEVIATION은 실패가 아닙니다**
> 헌장을 100% 지키지 못했다고 실패한 것이 아닙니다. 중요한 것은 **무엇을 못 지켰는지, 왜 못 지켰는지, 대신 무엇으로 같은 목적을 달성했는지**를 숨기지 않고 기록하는 것입니다. 선행 프로젝트는 Celery+Redis 대신 FastAPI의 BackgroundTasks라는 더 가벼운 기능으로 "업로드 응답은 즉시, AI 생성은 뒤에서"라는 동일한 목표를 달성했습니다. 이 기록은 `plan.md`의 **Complexity Tracking** 표에 남습니다.

### API 키를 다루는 원칙

계획 단계에서 외부 AI를 쓰기로 하면 API 키가 필요해집니다. 여기에 이 책 전체에서 가장 중요한 보안 원칙이 있습니다.

> **[주의] API 키는 AI에게 맡기지 않습니다**
> 선행 프로젝트에서 사용자는 "AI가 키를 대신 발급받거나 값을 채워 넣게" 하지 않았습니다. 대신 **"빈 틀(`.env` 파일)만 만들어 달라"**고 지시하고, 실제 키 값은 본인이 콘솔에서 직접 발급받아 손으로 채워 넣었습니다. AI에게 키 값을 알려주면 그 값이 대화 기록에 남고, 실수로 코드에 포함되어 공개 저장소에 올라갈 수 있습니다.

### 산출물

이 단계는 산출물이 가장 많습니다.

| 파일 | 내용 | 비전공자가 확인할 것 |
|---|---|---|
| `plan.md` | 기술 스택, 폴더 구조, 헌장 점검표, Complexity Tracking | DEVIATION 사유가 납득되는가 |
| `research.md` | 각 선택의 근거와 대안 비교 | "왜 그것을 골랐는지" 설명이 있는가 |
| `data-model.md` | 데이터 표 구조와 검증 규칙 | 내가 저장하려던 정보가 다 있는가 |
| `contracts/*.md` | 화면↔서버 통신 규격 | (전공자 아니면 확인 생략 가능) |
| `quickstart.md` | 완성 후 직접 확인할 시나리오 | **내가 기대한 사용 흐름과 같은가** |
| `checklists/*.md` | 명세 문장 품질 점검표 | 미결정 항목이 정직하게 남아 있는가 |

> **[실전] 비전공자가 가장 먼저 열어야 할 파일은 `quickstart.md`입니다**
> 기술 문서 중 유일하게 "사용자 입장에서 무엇을 해보게 되는가"가 적힌 문서이기 때문입니다. 여기에 적힌 시나리오가 내가 상상한 서비스와 다르면, 그 차이는 **지금 지적해야** 합니다.

### 승인 시 확인할 5가지

1. `quickstart.md`의 시나리오가 내가 원한 사용 흐름과 일치하는가?
2. DEVIATION 항목의 사유를 이해했는가?
3. 데이터 모델에 내가 저장하려던 정보가 빠짐없이 있는가?
4. 비용이 발생하는 요소(유료 AI 호출 등)가 무엇이고 어디에서 발생하는가?
5. 모르는 용어가 남아 있지 않은가? (남아 있다면 승인 전에 물어보십시오)

### 흔한 실수

1. **용어를 모른 채 승인** — 가장 흔합니다. 게이트가 무력화됩니다.
2. **`quickstart.md`를 안 읽음** — 계획서에서 유일하게 사용자 언어로 쓰인 문서를 건너뜁니다.
3. **DEVIATION을 그냥 넘김** — 나중에 운영 환경으로 옮길 때 문제가 터집니다.
4. **AI에게 키 값을 알려줌** — 되돌릴 수 없는 실수입니다. 이미 그랬다면 즉시 해당 키를 폐기하고 새로 발급하십시오.
## 3.5 5단계 — 작업분해(Tasks) ★승인 게이트★

### 무엇을 하는 단계인가

지금까지의 모든 문서(`spec.md`, `plan.md`, `data-model.md`, `contracts/`)를 종합해, **실제로 한 걸음씩 실행할 수 있는 작업 목록(`tasks.md`)**을 만드는 단계입니다. 이 단계가 AI-VC의 두 번째 승인 게이트입니다.

### 일상 비유

> **[개념] 이사 계획표**
> "이사한다"는 계획만으로는 아무도 움직일 수 없습니다. "① 3월 1일 견적 3곳 비교 → ② 3월 5일 업체 계약 → ③ 3월 10일 불용품 처분 → ④ 3월 15일 포장" 처럼 **날짜와 순서와 완료 판정 기준**이 붙어야 실행이 됩니다. `tasks.md`가 그 표입니다.

### 버티컬 슬라이스 — 이 단계의 핵심 설계

작업을 쪼개는 방식에는 크게 두 가지가 있습니다.

| 방식 | 진행 순서 | 장점 | 단점 |
|---|---|---|---|
| 수평 레이어 | 모든 기능의 데이터 → 모든 기능의 API → 모든 화면 | 같은 종류 작업을 몰아서 처리 | **전부 끝날 때까지 눈으로 볼 것이 없음** |
| **버티컬 슬라이스** | 기능 1개를 데이터→API→화면→테스트까지 완결 후 다음 기능 | 기능 하나가 끝날 때마다 실물 확인 가능 | 같은 종류 작업을 반복해 오가야 함 |

AI-VC는 **버티컬 슬라이스를 표준으로 채택**합니다. 비전공자에게는 "지금 무엇이 되고 있는지 눈으로 보이는 것"이 완주율을 좌우하기 때문입니다.

> **[실전] 실제로 있었던 충돌과 절충**
> 선행 프로젝트에서 사용자는 처음에 "모델 → API → 화면 → 테스트" 순서를 요청했습니다. 그런데 이 순서는 헌장 제1조(TDD, 양보 불가 — 테스트를 반드시 구현보다 먼저 쓴다)와 정면으로 충돌합니다. AI는 이 충돌을 그냥 넘기지 않고 명확히 알린 뒤 절충안을 제시했습니다 — **기능 단위로 세로로 자르는 것은 그대로 따르되, 슬라이스 안에서는 RED(테스트) → GREEN(모델→API→화면) → REFACTOR 순서를 지키자**는 것입니다. 사용자는 이를 수락했고, 이것이 AI-VC의 표준 작업 조직 방식이 되었습니다.

### tasks.md의 구조

```
Phase 1: Setup           환경·의존성 설치
Phase 2: Foundational    모든 슬라이스가 공통으로 딛고 설 기반
                         (여기가 끝나기 전엔 어떤 슬라이스도 시작 불가)
Phase 3: US1 슬라이스    RED → GREEN(모델) → GREEN(API)
                         → GREEN(화면) → REFACTOR
Phase 4: US2 슬라이스    (동일 구조 반복)
   ⋮
Phase 9: Polish          마무리 점검·문서 정리
```

각 작업(Task)에는 다음이 붙습니다.

| 항목 | 예 | 역할 |
|---|---|---|
| 작업 번호 | T009 | 추적 단위 |
| 제목 | 독서기록 모델 구현 | 무엇을 하는지 |
| TDD 단계 | GREEN | 순서 강제 |
| 커밋 메시지(사전 지정) | `feat: reading-record - GREEN backend (T009)` | 이력 일관성 |
| `[P]` 표시 | `[P]` | **병렬 진행 가능**(서로 다른 파일, 의존성 없음) |
| 완료 판정 | 테스트 3건 통과 | 끝났다고 말할 근거 |

> **[개념] `[P]` 표시의 의미**
> `[P]`가 붙은 작업들은 서로 다른 파일을 건드리고 의존관계가 없어서 **동시에 진행해도 안전한** 작업입니다. 예를 들어 프론트엔드에서 서버를 호출하는 함수를 작성하는 일은, 백엔드 구현과 동시에 진행할 수 있습니다. 혼자 작업할 때도 이 표시는 유용합니다 — 하나가 막혔을 때 손 놓지 않고 옮겨갈 수 있는 작업이 어디인지 알려주기 때문입니다.

> **[실전] 조건부 승인이라는 선택지**
> 선행 프로젝트에서 사용자는 이렇게 답했습니다. "예. 하지만 미체크 항목과 분석에서 발견된 나머지 항목(특히 AI 비용·개인정보 관련)은 나중에 검토할 수 있게 해줘." 이 조건부 승인은 `tasks.md`의 Phase 9(Polish)에 T050이라는 추적 항목으로 박혔습니다. **"나중에 하겠다"는 말이 허공으로 사라지지 않도록 문서에 못 박은 것**입니다. 이것이 좋은 승인의 모범입니다.

### RED-GREEN-REFACTOR

| 단계 | 하는 일 | 커밋 예 |
|---|---|---|
| RED | 아직 없는 기능에 대한 **실패하는 테스트**를 먼저 쓴다 | `test: reading-record - RED (T007)` |
| GREEN | 그 테스트를 통과시키는 **최소한의 구현**을 한다 | `feat: reading-record - GREEN backend (T009)` |
| REFACTOR | 동작은 그대로 두고 **코드를 정리**한다 | `refactor: reading-record - REFACTOR (T012)` |

> **[개념] 왜 실패를 먼저 확인하나요?**
> 테스트를 작성한 뒤 "통과하는지"가 아니라 먼저 "실패하는지"를 확인하는 이유는, **테스트 코드 자체가 잘못 쓰여서 무엇을 넣어도 항상 통과하는 무의미한 테스트**가 되는 것을 막기 위해서입니다. 제대로 실패하는 것을 본 다음에 통과시켜야, 그 통과가 "진짜로 기능이 동작해서"라고 믿을 수 있습니다.

### 슬라이스가 끝날 때마다 하는 일

기능(User Story) 하나가 끝날 때마다 다음 세 가지를 합니다.

1. **브라우저에서 직접 확인** — AI의 보고가 아니라 내 눈으로
2. **작업 보고서 작성** — `docs/task-reports/`에 무엇이 완료되었는지 기록
3. **progress.md 갱신** — 다음 세션이 이어받을 수 있게

```
Claude:
책 읽기 기록 기능이 완성됐습니다. 실제로 실행해서 확인해보시겠어요?
```

> **[주의] "확인해보시겠어요?"에 반드시 응하십시오**
> 전체가 다 끝날 때까지 기다렸다가 확인하면, 문제가 생겼을 때 원인 후보가 수십 개가 됩니다. 슬라이스 하나가 끝난 직후에 확인하면 원인 후보는 방금 만든 것 하나뿐입니다. 이것이 버티컬 슬라이스를 택하는 실질적인 이유입니다.

# 4부. AI-VC를 떠받치는 개발 규율

> **이 부에서 답하는 질문**

> 3. 커밋 이력은 나에게 무슨 소용인가?

## 4.1 TDD — 비전공자를 위한 설명

**TDD(Test-Driven Development, 테스트 주도 개발)**는 "기능을 만들기 전에, 그 기능이 제대로 됐는지 판정할 검사 절차를 먼저 만든다"는 개발 방식입니다.

> **[개념] 시험 문제를 먼저 내는 것**
> 학생을 가르치기 전에 기말시험 문제를 먼저 출제한다고 생각해 보십시오. 이상해 보이지만, 이렇게 하면 두 가지가 확실해집니다. 첫째, **무엇을 가르쳐야 하는지가 분명해집니다.** 둘째, **가르친 뒤에 "잘 됐다"고 착각할 수 없습니다.** 시험을 치르면 되기 때문입니다. TDD가 하는 일이 정확히 이것입니다.

### 비전공자에게 TDD가 왜 중요한가

전공자에게 TDD는 "품질 관리 기법"입니다. 그러나 **비전공자에게 TDD는 "유일한 검증 수단"**입니다. 여러분은 코드를 읽고 옳고 그름을 판단할 수 없습니다. 여러분이 확인할 수 있는 것은 오직 두 가지입니다.

1. 브라우저에서 직접 눌러보기 (수동 확인)
2. 테스트 실행 출력 보기 (자동 확인)

수동 확인은 기능이 늘어날수록 감당할 수 없게 됩니다. 기능이 6개면 매번 6개를 다 눌러봐야 하는데, 실제로는 방금 만든 것만 눌러보고 넘어갑니다. 그래서 **자동 확인이 필요합니다.**

> **[실전] 테스트가 실제로 막아낸 사고**
> 선행 프로젝트에서 가장 중요했던 버그는 **백그라운드 작업이 실제 운영 데이터베이스를 건드리는 문제**였습니다. 화면상으로는 아무 이상이 없었습니다. 만약 "되는 것 같으니 넘어가자"는 태도로 진행했다면, 이 버그는 서비스가 배포되고 **사용자 데이터가 뒤섞인 뒤에야** 발견되었을 가능성이 높습니다. 테스트를 먼저 쓰고, 새 기능을 만들 때마다 **전체 테스트를 다시 돌려보는 습관**이 이 문제를 개발 단계에서 잡아냈습니다.

### "테스트를 못 짜는데 어떡하죠?"

이 질문이 TDD를 포기하는 가장 흔한 이유입니다. 답은 간단합니다.

> **여러분이 테스트 코드를 직접 짤 필요는 없습니다. AI에게 "먼저 실패하는 테스트를 써줘"라고 요청하는 것 자체는, 문법을 몰라도 할 수 있는 요청입니다.**

중요한 것은 문법을 아는 것이 아니라 **"테스트 없이 다음 단계로 넘어가지 않는다"는 습관**, 그리고 AI에게 그 습관을 명시적으로 요구하는 것입니다.

## 4.2 RED-GREEN-REFACTOR의 실제 모습

### 세 단계

```
① RED      아직 없는 기능에 대한 테스트를 쓴다 → 실행 → 실패 확인
              "독서 기록을 저장하면 목록에 나타나야 한다" (아직 저장 기능 없음 → 실패)
                    │
② GREEN    실패한 테스트를 통과시키는 최소한의 코드를 쓴다 → 실행 → 통과 확인
              저장 기능 구현 → 테스트 통과
                    │
③ REFACTOR 동작을 바꾸지 않고 코드를 정리한다 → 실행 → 여전히 통과 확인
              중복 제거, 이름 정리 → 테스트 여전히 통과
```

### 왜 세 번을 따로 커밋하는가

세 단계를 각각 별도 커밋으로 남기면 **git 이력만 봐도 이 기능이 어떤 순서로 만들어졌는지**가 드러납니다. 선행 프로젝트의 커밋 이력에서는 `test:` → `feat:` → `refactor:` 순서가 6개 슬라이스 모두에서 예외 없이 반복됩니다. 이것이 우연이 아니라 **헌장에 '양보 불가(NON-NEGOTIABLE)'로 못 박혀 있었기 때문**에 가능했습니다.

### 비전공자가 확인할 지점

| 시점 | 확인할 것 | 확인 방법 |
|---|---|---|
| RED 직후 | 테스트가 **정말 실패했는지** | 실행 출력에 `FAILED` 또는 `1 failed`가 보이는가 |
| GREEN 직후 | 테스트가 **통과했는지** | 실행 출력에 `passed`가 보이는가 |
| REFACTOR 직후 | 여전히 통과하는지 | 전체 테스트 수가 줄지 않았는가 |

> **[주의] "전체 테스트 수"를 기록해 두십시오**
> 테스트 수가 45개였다가 갑자기 42개가 되었다면, 어딘가에서 테스트가 삭제되었거나 실행되지 않고 있다는 뜻입니다. 코드를 못 읽어도 이 숫자는 누구나 셀 수 있습니다. 이것이 비전공자가 쓸 수 있는 가장 강력한 검증 도구입니다.

## 4.3 버티컬 슬라이스 vs 수평 레이어

### 두 방식의 실제 차이

같은 6개 기능을 만들 때 두 방식의 진행 상황을 비교하면 다음과 같습니다.

| 경과 | 수평 레이어 | 버티컬 슬라이스 |
|---|---|---|
| 1주차 | 6개 기능의 데이터 구조 완성 (눈에 보이는 것 없음) | 기능 1 완성 — **브라우저에서 사용 가능** |
| 2주차 | 6개 기능의 서버 로직 완성 (여전히 화면 없음) | 기능 2·3 완성 — 사용 가능 |
| 3주차 | 화면 작업 시작 | 기능 4·5 완성 |
| 4주차 | 전부 연결 — **여기서 처음으로 문제들이 한꺼번에 드러남** | 기능 6 완성 + 마무리 |

### 장단점 정리

| 항목 | 버티컬 슬라이스 | 수평 레이어 |
|---|---|---|
| 첫 실물 확인 시점 | 빠름 (기능 1 완료 시) | 느림 (전체 완료 시) |
| 문제 발견 시점 | 이르고 분산됨 | 늦고 한꺼번에 |
| 원인 특정 난이도 | 쉬움(방금 만든 것) | 어려움(후보 다수) |
| 반복 작업 효율 | 낮음(같은 종류 작업을 오감) | 높음 |
| 중도 포기 시 남는 것 | **동작하는 일부 기능** | 동작하지 않는 부품들 |
| 비전공자 적합성 | **높음** | 낮음 |

> **[개념] 케이크 비유**
> 수평 레이어는 케이크를 층별로 만드는 것입니다 — 빵 여섯 장을 다 굽고, 크림 여섯 겹을 다 만들고, 마지막에 쌓습니다. 버티컬 슬라이스는 **한 조각씩 완성해서 맛보는 것**입니다. 첫 조각을 먹어보고 "너무 달다"는 걸 알면 나머지 다섯 조각을 고칠 수 있습니다.

### 예외 — Foundational Phase

버티컬 슬라이스에도 예외가 있습니다. 모든 기능이 공통으로 딛고 서는 기반(사용자 인증, 데이터베이스 연결, AI 클라이언트 등)은 **먼저 만들어야 합니다.** 이것이 `tasks.md`의 Phase 2(Foundational)입니다.

> **[주의] Foundational이 크면 방법론의 이점이 사라집니다**
> 기반 작업이 3일 걸리면 3일 동안 아무것도 눈에 보이지 않습니다. 승인 게이트에서 **"Foundational Phase에 몇 개 Task가 들어 있습니까? 이걸 더 줄일 수 있습니까?"**라고 물어보십시오. 정말 공통으로 필요한 것만 남기는 것이 좋습니다.

## 4.4 커밋 컨벤션과 이력 추적

### 커밋이란

> **[개념] 문서의 '버전 저장'**
> 워드 문서를 작업하다가 `보고서_최종.docx`, `보고서_최종_진짜최종.docx`를 만들어본 적이 있으실 겁니다. git의 커밋은 그 일을 자동으로, 그리고 **"무엇이 왜 바뀌었는지 설명을 붙여서"** 하는 것입니다. 언제든 과거 시점으로 되돌아갈 수 있습니다.

### 커밋 메시지 형식

AI-VC는 다음 형식을 표준으로 삼습니다.

```
{type}: {제목} - {TDD단계} ({작업번호})

예)
test: reading-record - RED (T007)
feat: reading-record - GREEN backend (T009)
feat: reading-record - GREEN frontend (T011)
refactor: reading-record - REFACTOR (T012)
docs: pivot constitution to AI Code Learning Platform (v2.0.0)
```

| type | 의미 |
|---|---|
| `feat` | 새 기능 |
| `test` | 테스트 추가·수정 |
| `refactor` | 동작 변경 없는 코드 정리 |
| `fix` | 버그 수정 |
| `docs` | 문서 변경 |
| `chore` | 설정·의존성 등 잡무 |

### 이력이 나에게 주는 것

`git log` 한 줄만 봐도 "이게 테스트인지 구현인지 정리인지, 몇 번 작업에 속하는지"가 바로 보입니다. 선행 프로젝트는 초기화 커밋부터 총 94개의 커밋을 통해 완성되었고, 각 커밋 해시로 그 순간에 정확히 무엇이 바뀌었는지 확인할 수 있습니다.

> **[실전] 비전공자가 쓸 수 있는 git 명령 3개**
> 1. `git log --oneline` — 지금까지 무엇을 했는지 한 줄씩 보기
> 2. `git status` — 지금 무엇이 바뀌어 있는지 보기
> 3. `git show <해시>` — 그 커밋에서 정확히 무엇이 바뀌었는지 보기
> 이 세 개만 알아도 "AI가 무엇을 했는지" 스스로 확인할 수 있습니다. 나머지는 AI에게 시키면 됩니다.

## 4.5 DEVIATION을 기록하는 문화

AI-VC가 다른 절차와 구별되는 지점 하나가 **"못 지킨 것을 정직하게 남긴다"**는 태도입니다.

| 상황 | 나쁜 대응 | AI-VC의 대응 |
|---|---|---|
| 헌장에 PostgreSQL을 쓰기로 했는데 설치가 안 됨 | 조용히 SQLite로 바꾸고 넘어감 | Constitution Check에 DEVIATION으로 표시, 사유·대안·복구 방법 기록 |
| 체크리스트 23개 중 2개를 답할 수 없음 | 대충 체크하고 넘어감 | 미체크로 남기고 Phase 9 추적 항목으로 등록 |
| 테스트를 이 환경에서 실행할 수 없음 | "통과했습니다"라고 보고 | "실행하지 못했습니다. 직접 확인해주십시오"라고 보고 |

> **[개념] 왜 이것이 중요한가**
> 기록되지 않은 미완성은 **완성으로 오인됩니다.** 몇 달 뒤 이 프로젝트를 운영 환경에 올리려는 사람(그것이 미래의 여러분일 수도 있습니다)은 "PostgreSQL을 쓰기로 했었지"라고 믿고 작업을 시작할 것입니다. DEVIATION 기록 한 줄이 그 사고를 막습니다.

# 5부. 사람의 기술 — 결정자 훈련

> **이 부에서 답하는 질문**
> 1. 좋은 기획서는 어떻게 쓰는가?
> 2. 승인 게이트에서 무엇을 봐야 하는가?
> 3. AI의 보고를 어떻게 검증하는가?

## 5.1 좋은 입력 자료가 좋은 결과를 만든다

### 기획서가 결과 품질의 대부분을 결정합니다

다시 강조합니다. **바이브코딩에서 결과물의 품질은 "프롬프트 한 줄의 정교함"보다 "얼마나 좋은 입력 자료를 미리 준비했는가"에 더 크게 좌우됩니다.** 선행 프로젝트에서 사용자가 2단계에 입력한 것은 단 한 줄이었지만, 그 한 줄이 가리킨 파일은 A4 10페이지 분량의 기획서였습니다.

### 기획서에 반드시 들어가야 할 7가지

| 항목 | 쓰는 요령 | 분량 |
|---|---|---|
| ① 한 줄 정의 | "누가, 무엇을 하면, 무엇을 얻는 서비스" | 1문장 |
| ② 왜 필요한가 | 지금 사람들이 겪는 불편을 구체적 장면으로 | 0.5쪽 |
| ③ 핵심 사용 흐름 | 사용자가 처음부터 끝까지 겪는 순서 | 1쪽 |
| ④ 화면 스케치 | 손그림·표·텍스트 배치 무엇이든 | 2~3쪽 |
| ⑤ 데이터 예시 | 실제로 들어갈 값을 지어서라도 적기 | 1~2쪽 |
| ⑥ 하지 않을 것 | 이번 범위에서 제외할 것 | 0.5쪽 |
| ⑦ 판단이 필요한 지점 | 내가 아직 못 정한 것 | 0.5쪽 |

> **[실전] ④번과 ⑤번이 결정적입니다**
> 화면 스케치와 데이터 예시가 있으면 AI는 추측을 멈춥니다. 예를 들어 독서활동 서비스라면 "책 제목: 데미안 / 저자: 헤르만 헤세 / 인상 깊은 구절: '새는 알에서 나오려고 투쟁한다' / 내 생각: ..." 처럼 **실제 값을 하나 지어서 적어두는 것**만으로도 데이터 구조 설계의 절반이 끝납니다.

### 기획서를 AI와 함께 쓰는 방법

기획서 자체를 AI와 함께 써도 됩니다. 다만 순서가 중요합니다.

```
1) 사람이 ①②③을 손으로 씁니다 (여기는 대체 불가)
2) AI에게: "이 초안을 읽고, 빠진 게 뭔지 질문 10개만 해줘"
3) 그 질문에 답합니다
4) AI에게: "내 답변을 반영해 기획서를 정리해줘. 단, 내가 말하지 않은 건 추가하지 마"
5) 사람이 ⑥⑦을 마지막에 직접 추가합니다
```

> **[주의] 4번의 단서 조항이 핵심입니다**
> "내가 말하지 않은 건 추가하지 마"를 빼면, AI는 그럴듯한 기능을 스스로 채워 넣습니다. 그 기능은 여러분이 원한 것이 아니지만 명세에 들어가고, 나중에 개발 시간을 잡아먹습니다.

## 5.2 승인 게이트에서 무엇을 봐야 하나 — 3문 3답

승인 요청을 받았을 때 물어야 할 질문을 세 개로 압축했습니다.

### 질문 1 — "이걸 안 하면 어떻게 되나요?"

각 결정의 **필요성**을 확인합니다. 답변이 "그러면 이러이러한 상황에서 문제가 생깁니다"처럼 구체적이면 필요한 것이고, "일반적으로 많이 씁니다" 정도면 다시 물어야 합니다.

### 질문 2 — "나중에 이걸 바꾸려면 얼마나 어렵나요?"

**되돌리기 비용**을 확인합니다. "설정 한 줄만 바꾸면 됩니다"와 "데이터를 전부 옮겨야 합니다"는 승인의 무게가 다릅니다. 후자라면 더 신중해야 합니다.

### 질문 3 — "이 선택으로 돈이 나가나요?"

**비용 발생 지점**을 확인합니다. AI API 호출, 클라우드 서비스, 유료 도구가 여기 해당합니다. "얼마나 나가는지 대략 계산해서 보여주세요"까지 요구하십시오.

| 상황 | 판단 |
|---|---|
| 세 질문에 모두 구체적 답이 온다 | 승인해도 좋습니다 |
| 한 질문이라도 답이 두루뭉술하다 | 그 항목만 다시 설명을 요구하십시오 |
| 답이 내 상황과 안 맞는다 | "제 상황은 이런데 그래도 그 선택이 맞나요?"라고 되물으십시오 |

## 5.3 AI의 보고를 검증하는 질문 5개

코드를 읽지 못해도 쓸 수 있는 검증 질문입니다.

1. **"실행한 명령과 그 결과를 그대로 보여주세요."** — 제2원칙의 실행. 가장 중요합니다.
2. **"전체 테스트를 다시 돌리면 몇 개가 통과합니까?"** — 새 기능이 기존 기능을 깨뜨렸는지 확인.
3. **"이번에 바뀐 파일 목록을 보여주세요."** — 예상보다 많은 파일이 바뀌었다면 이유를 물어야 합니다.
4. **"이 기능이 안 되는 경우는 어떤 경우입니까?"** — AI가 스스로 한계를 말하게 합니다.
5. **"방금 작업을 `progress.md`에 기록했습니까?"** — 제3원칙의 실행.

> **[실전] 5번 질문의 효과**
> 이 질문 하나로 세션 인계 실패를 대부분 막을 수 있습니다. 작업이 길어지면 AI도 기록을 잊습니다. 슬라이스가 끝날 때마다 이 질문을 던지는 것을 습관으로 만드십시오.

## 5.4 "예"라고 답해도 되는 때와 안 되는 때

선행 프로젝트 기록을 보면 사용자의 답변이 "예", "예. 그리고 수정안대로 수정해줘"처럼 매우 짧습니다. 이것은 아무 생각 없는 승낙이 아니었습니다. **AI가 먼저 상황을 정리하고 추천안과 근거를 분명히 제시했기 때문에, 사람은 짧게 답해도 충분히 의미 있는 결정을 내릴 수 있었던 것**입니다.

| "예"라고 답해도 되는 때 | "예"를 미뤄야 하는 때 |
|---|---|
| AI가 선택지와 근거를 함께 제시했다 | 근거 없이 "이렇게 하겠습니다"라고만 한다 |
| 되돌리기 비용이 낮다고 확인했다 | 되돌리기 비용을 물어보지 않았다 |
| 모르는 용어가 없다 | 모르는 용어가 하나라도 있다 |
| 비용 발생 여부를 확인했다 | 비용을 확인하지 않았다 |
| 내 기획 의도와 일치한다 | 뭔가 다른 것 같은데 설명이 안 된다 |

## 5.5 AI가 틀렸을 때 되돌리는 법

### 상황별 대응

| 상황 | 대응 |
|---|---|
| 방금 만든 것이 마음에 안 든다 | "직전 변경을 되돌리고, 이유는 ~입니다"라고 말하십시오. AI가 되돌립니다. |
| 여러 단계 전으로 돌아가야 한다 | `git log --oneline`으로 시점을 찾아 "이 커밋 상태로 되돌려줘"라고 요청 |
| 문서(명세·계획)가 잘못되었다 | 코드보다 문서를 먼저 고칩니다. 문서가 원본이기 때문입니다. |
| AI가 같은 실수를 반복한다 | 헌장에 조항을 추가하거나 `progress.md` ⑥번(알아둘 함정)에 기록 |
| 무엇이 잘못됐는지 모르겠다 | "지금 상태에서 무엇이 기대와 다른지 목록으로 정리해줘"라고 요청 |

> **[주의] 되돌리기 전에 반드시 커밋 상태를 확인하십시오**
> 커밋하지 않은 변경사항이 있는 상태에서 과거로 되돌리면 그 변경사항이 사라질 수 있습니다. "지금 커밋 안 된 변경이 있습니까?"를 먼저 물어보는 습관을 들이십시오.

### 실패를 기록으로 바꾸기

되돌린 사실 자체도 기록할 가치가 있습니다. `progress.md`의 ⑥번 블록(알아둘 함정)에 "OO 방식으로 시도했다가 XX 이유로 되돌림"이라고 한 줄 남기면, 다음 세션에서 AI가 같은 시도를 반복하지 않습니다.

# 6부. 기록과 연속성

> **이 부에서 답하는 질문**
> 1. AI가 어제 일을 왜 기억하지 못하는가?
> 2. 무엇을 어디에 남겨야 이어서 할 수 있는가?
> 3. 세션 시작·종료 루틴은 어떻게 만드는가?

## 6.1 맥락 유실 문제

### 왜 일어나는가

AI는 **대화창(세션) 단위로 기억합니다.** 새 대화를 시작하거나 `/clear`를 하면 이전 내용을 전혀 기억하지 못합니다. 또한 한 대화 안에서도 내용이 아주 길어지면 앞부분이 요약·압축되면서 세부 사항이 사라집니다.

| 상황 | AI가 기억하는 것 | AI가 잃는 것 |
|---|---|---|
| 같은 대화 계속 | 대부분 | (매우 길어지면 초반 세부) |
| 대화 중 압축 발생 | 요약된 줄거리 | 구체적 결정 근거·수치 |
| 새 대화 시작 | 아무것도 | 전부 |
| 며칠 뒤 재개 | 아무것도 | 전부 |
| 다른 기기에서 접속 | 아무것도 | 전부 |

### 예전 방식의 문제

기록 체계가 없으면, 사람이 매번 "우리가 어디까지 했더라"를 다시 설명해야 합니다. 그런데 사람도 정확히 기억하지 못합니다. 결국 **부정확한 설명 → 부정확한 이해 → 잘못된 작업**의 연쇄가 일어납니다.

> **[개념] 설명하는 사람이 바뀌었습니다**
> AI-VC의 제3원칙이 바꾼 것은 방향입니다. 예전에는 **사람이 AI에게** 맥락을 설명했지만, 이제는 **AI가 기록을 읽고 사람에게 요약해 확인받습니다.** 사람은 "예"라고만 답하면 됩니다. 부정확한 기억에 의존하지 않게 되었다는 점이 핵심입니다.

### 각 블록의 작성 요령

| 블록 | 좋은 예 | 나쁜 예 |
|---|---|---|
| ① 현재 위치 | 완료/진행 중/미착수를 User Story 단위로 | "거의 다 됐음" |
| ② 한 일 | 무엇을, 어느 파일에서, **왜** | "토론 기능 작업함" |
| ③ 증거 | 실제 실행 명령과 출력 | "테스트 잘 됨" |
| ④ **다음 할 일** | 즉시 실행 가능한 문장 + 체크박스 | "토론 기능 마무리" |
| ⑤ 막힌 것 | 결정이 필요한 사안과 각 선택의 비용 | (비워둠) |
| ⑥ 함정 | 반복해서 걸린 문제와 해결법 | (비워둠) |

> **[주의] ④번을 모호하게 쓰면 기록이 무의미해집니다**
> "토론 기능 마무리"는 다음 세션의 AI가 읽어도 무엇을 해야 할지 모릅니다. **파일 경로·함수 이름·확인 방법까지 적으십시오.** 좋은 ④번의 판별법은 이것입니다 — *"이 문장을 그대로 복사해 새 대화창에 붙여넣으면 작업이 시작되는가?"*

### 언제 갱신하는가

다음 중 하나라도 해당하면 자동으로 갱신합니다.

1. "오늘은 여기까지", "그만하자" 등 종료 의사를 밝혔을 때
2. 기능(User Story) 하나가 끝났을 때
3. 승인을 기다리며 대화가 길어질 때
4. 대화가 길어져 맥락이 압축될 조짐이 보일 때

## 6.3 작업 보고서(task-reports)

`progress.md`가 "지금 어디까지"라면, 작업 보고서는 **"완료된 기능이 어떤 상태로 끝났는지"**의 스냅샷입니다. 기능 하나가 끝날 때마다 `docs/task-reports/` 폴더에 한 건씩 남깁니다.

| 항목 | 내용 |
|---|---|
| 기능명·작업 번호 범위 | US2 AI 내용 정리 (T014~T021) |
| 구현 범위 | 무엇을 만들었고 무엇은 만들지 않았는지 |
| 테스트 결과 | 실행 명령과 출력 |
| 발견한 문제와 해결 | 트러블슈팅 기록 |
| 남은 과제 | 후속으로 미룬 것 |
| 관련 커밋 | 해시 목록 |

> **[개념] progress.md와 task-reports의 차이**
> `progress.md`는 **한 개 파일을 계속 덮어쓰는 현재 상태판**입니다. `task-reports/`는 **완료 시점마다 새 파일이 쌓이는 이력 보관소**입니다. 전자는 "지금 어디"를, 후자는 "그때 무엇을"을 답합니다.

## 6.4 세션 시작·종료 루틴

### 종료 루틴 (2분)

1. AI에게: **"오늘은 여기까지. `progress.md` 갱신해줘."**
2. AI가 6블록을 갱신하면 ④번만 직접 읽어봅니다.
3. ④번이 모호하면 "④번을 더 구체적으로, 파일 경로까지 적어줘"라고 요청합니다.
4. 커밋되지 않은 변경이 있는지 확인하고 커밋합니다.

### 시작 루틴 (2분)

1. AI에게: **"AI바이브코딩 최신버전 작동"** (또는 여러분이 정한 시작 문구)
2. AI가 `progress.md`를 읽고 요약 보고합니다.
3. 요약이 내 기억과 다르면 그 자리에서 바로잡습니다.
4. "예, 이어서 진행해줘"로 재개합니다.

> **[실전] 두 마디가 전부입니다**
> 끝낼 때 **"저장해줘"**, 시작할 때 **"작동"**. 이 두 마디로 세션 연속성이 유지됩니다. 습관이 되기까지 2주 정도 걸리지만, 한 번 몸에 붙으면 다시는 "우리 어디까지 했더라"를 겪지 않습니다.

### 프로젝트 지침 파일(CLAUDE.md)로 자동화하기

프로젝트 폴더 루트에 `CLAUDE.md`라는 파일을 두면, AI가 세션 시작 시 이 파일을 자동으로 읽습니다. 여기에 시작 루틴을 적어두면 매번 지시하지 않아도 됩니다.

```markdown
# 프로젝트 작업 지침

## 세션 시작 시 반드시 할 것
1. docs/progress.md 를 먼저 읽고 진행 상황을 요약 보고할 것
2. 요약 후 "여기서 이어서 진행할까요?"라고 확인받을 것

## 이 프로젝트에서 지킬 것
1. 테스트 없이 구현하지 않는다
2. 완료 보고 시 반드시 실행 출력을 함께 제시한다
3. .env 파일은 절대 커밋하지 않는다
4. 파일 삭제는 사전 확인 후 실행한다
```

# 7부. 도구 지형 — Cowork와 Claude Code

> **이 부에서 답하는 질문**
> 1. 내가 써본 Cowork로 어디까지 할 수 있는가?
> 2. 언제 Claude Code로 넘어가야 하는가?
> 3. 그 너머에는 무엇이 있는가?

## 7.1 두 도구의 성격 차이

이 책의 독자는 Claude Cowork를 써본 경험이 있다고 전제했습니다. 그렇다면 가장 먼저 정리할 것은 **"내가 아는 그 도구로 어디까지 되는가"**입니다.

| 항목 | Claude Cowork | Claude Code |
|---|---|---|
| 실행 환경 | 앱 화면 안 | 컴퓨터의 터미널(명령창) |
| 주 용도 | 문서·자료·데이터 작업 | 소프트웨어 개발 |
| 파일 접근 | 연결한 폴더 | 프로젝트 폴더 전체 |
| 프로그램 실행 | 제한적 | 서버 실행·테스트 실행 등 자유 |
| git 사용 | 제한적 | 표준 |
| 확장(스킬·MCP 등) | 지원 | 지원 |
| 진입 난이도 | 낮음 | 중간(터미널 사용 필요) |
| AI-VC 적용 | 1~3단계까지 실용적 | **전 단계 가능** |

> **[개념] 왜 개발에는 터미널이 필요한가**
> 소프트웨어를 만든다는 것은 코드를 쓰는 일만이 아니라 **그것을 실행하고, 테스트를 돌리고, 오류 메시지를 읽고, 다시 고치는 순환**입니다. 이 순환에는 프로그램을 직접 실행할 수 있는 환경이 필요합니다. 터미널이 그 환경입니다. Claude Code는 그 터미널 안에서 AI가 직접 명령을 실행하고 결과를 읽을 수 있게 해줍니다 — 이것이 제2원칙(증거 기반 보고)이 가능한 물리적 이유입니다.

## 7.2 Cowork로 할 수 있는 것과 없는 것

### Cowork로 충분히 할 수 있는 것

1. **1단계 헌장 초안 작성** — 규칙 문장을 정리하는 일은 문서 작업입니다.
2. **기획서(`plan_specify.md`) 작성** — 이 책이 가장 중요하다고 강조한 작업이며, Cowork가 가장 잘하는 일입니다.
3. **2단계 명세 초안** — User Story·FR·SC를 문서로 정리하는 것까지는 가능합니다.
4. **3단계 명확화 연습** — "이 명세에서 애매한 지점 5개만 질문해줘"라고 요청할 수 있습니다.
5. **자료 조사** — 유사 서비스 조사, 용어 정리, 참고 자료 수집.

### Cowork로는 어려운 것

1. 서버를 실행하고 브라우저에서 확인하기
2. 테스트를 실행하고 그 출력을 근거로 판단하기
3. git 커밋 이력을 쌓고 특정 시점으로 되돌리기
4. 여러 파일에 걸친 코드 수정을 연속으로 수행하기

> **[실전] 권장 진입 경로**
> Cowork에서 **기획서와 헌장 초안까지 만들어 두고**, Claude Code로 옮겨가 그 파일을 입력값으로 삼아 2단계부터 진행하는 방식을 권합니다. 실제로 선행 프로젝트도 사람이 미리 준비한 `my_constitution.md`와 `plan_specify.md` 두 파일에서 출발했습니다. 이 두 파일은 터미널 없이도 만들 수 있습니다.

## 7.3 전환 시점과 전환 방법

### 전환 신호

다음 중 하나라도 해당하면 Claude Code로 넘어갈 때입니다.

1. 기획서와 헌장 초안이 완성되었다
2. "실제로 실행되는 것"을 보고 싶다
3. 파일이 10개를 넘어가기 시작했다
4. 되돌리기(버전 관리)가 필요해졌다

### 전환 절차 요약

```
1) 컴퓨터에 프로젝트 폴더를 만든다        예) C:\Users\사용자\reading-activity
2) 그 폴더에 Cowork에서 만든 두 파일을 넣는다
       my_constitution.md   (헌장 초안)
       plan_specify.md      (서비스 기획서)
3) 터미널을 열고 그 폴더로 이동한다        cd C:\Users\사용자\reading-activity
4) Claude Code를 실행한다                  claude
5) 첫 지시:
   "이 폴더의 my_constitution.md 를 읽고 프로젝트 헌장을 세워줘."
```

상세한 설치 절차는 **제2권 8부**에서 화면 단위로 안내합니다.

## 7.4 다섯 가지 확장 도구 개요

Claude Code에는 기능을 넓히는 다섯 가지 장치가 있습니다. 지금 당장 다 쓸 필요는 없지만, 무엇이 있는지 알아두면 나중에 "이건 어떻게 하지?" 싶을 때 방향을 잡을 수 있습니다.

| 도구 | 한 줄 정의 | 언제 쓰나 | 발동 방식 |
|---|---|---|---|
| **스킬(Skill)** | 반복 절차를 지침 묶음으로 저장 | 같은 절차를 3번 이상 설명하고 있을 때 | AI가 대화 내용을 보고 자동 판단 |
| **서브에이전트(Subagent)** | 독립된 작업자에게 통째로 위임하고 결과만 받음 | 무겁고 과정은 몰라도 되는 작업 | 메인이 호출 |
| **MCP 서버** | 외부 서비스(노션·메일 등)에 연결하는 표준 플러그 | 외부 도구와 연동할 때 | 설정 파일에 등록 |
| **Hooks** | 특정 사건이 생기면 **승인 없이 무조건** 실행 | 항상 지켜야 할 방어 장치 | 조건 충족 시 자동 |
| **Plugins** | 위 넷을 하나로 묶어 배포하는 패키지 | 남에게 통째로 나눠줄 때 | 설치 명령 |

> **[주의] Hooks만 성격이 다릅니다**
> 스킬·서브에이전트는 "AI가 판단해서 부르는 것"이지만, **Hooks는 조건이 맞으면 확인 없이 즉시 실행됩니다.** 승인 게이트가 없습니다. 그래서 파일을 삭제하거나 외부로 데이터를 보내는 Hook은 특히 신중해야 하며, 초보자는 **"막고 경고만 하는" 방어적 Hook부터** 시작하는 것을 권합니다.

### 다섯 가지가 함께 쓰이는 모습

이 다섯 가지는 서로 배타적이지 않습니다. 실제 프로젝트에서는 섞어 씁니다.

```
독서활동 확장판 예시

  스킬          book-report-formatter   (제출 양식 정리 절차)
  서브에이전트   book-analyst 외 5종      (분석·추천·토론·집필·검수)
  MCP 서버      notion, gmail            (포트폴리오 저장·알림 발송)
  Hooks         check_pii.py             (개인정보 저장 전 자동 차단)
        ↓
  Plugins       reading-activity-toolkit (위 전부를 한 번에 설치)
```

각각의 실제 정의 파일과 사용법은 **제2권 19부**에서 독서활동 서비스를 예로 다룹니다.

## 7.5 여기까지의 정리

지금까지 다룬 것을 한 장으로 정리합니다.

| 층위 | 내용 |
|---|---|
| **문제 인식** | 바이브코딩의 네 가지 함정 — 결정이 파일로 남지 않는다 |
| **방법론** | AI-VC 7단계 — 되돌리기 비용이 싼 결정부터 |
| **원칙** | ① 승인 게이트 ② 증거 기반 보고 ③ 기록 연속성 |
| **규율** | TDD, 버티컬 슬라이스, 커밋 컨벤션, DEVIATION 기록 |
| **사람의 기술** | 기획서 작성, 3문 3답, 검증 질문 5개 |
| **도구** | Cowork(기획) → Claude Code(구현) → 다섯 가지 확장 |

다음 8부에서는 이 전체 흐름을 아주 작은 예제 하나로 **30분 안에 한 바퀴** 돌아봅니다. 제2권의 본격적인 실습에 들어가기 전, 절차 전체의 감각을 잡기 위한 워밍업입니다.

# 8부. 30분 미니 실습 — 작게 한 바퀴 돌아보기

> **이 부에서 답하는 질문**
> 1. 7단계를 아주 작은 예제로 돌리면 어떤 모습인가?
> 2. 각 단계에 실제로 몇 분이 걸리는가?
> 3. 제2권의 본격 실습 전에 무엇을 감각으로 익혀야 하는가?

## 8.1 이 실습의 목적

제2권에서는 기능 6개짜리 서비스를 몇 주에 걸쳐 만듭니다. 그 전에 **아주 작은 것 하나를 30분 안에 끝까지 돌려보는 것**이 큰 도움이 됩니다. 절차의 전체 모양을 몸으로 익히는 것이 목적이며, 결과물의 완성도는 중요하지 않습니다.

만들 것은 **"한 줄 가계부"**입니다.

> **[구성 예시] 한 줄 가계부**
> 오늘 쓴 돈을 한 줄로 적으면(예: "점심 9,000원") 목록에 쌓이고, 오늘 총액과 이번 달 총액이 화면 위에 표시되는 아주 작은 웹 도구. 로그인도 없고 카테고리도 없습니다.

## 8.2 왜 이 예제인가

| 조건 | 충족 여부 |
|---|---|
| 설명이 필요 없을 만큼 단순한가 | ○ |
| 기능이 3개 이하인가 (입력·목록·합계) | ○ |
| 데이터 구조가 표 하나로 끝나는가 | ○ |
| 외부 서비스(AI·결제 등)가 필요 없는가 | ○ |
| 완성 여부를 눈으로 즉시 알 수 있는가 | ○ |

제1권 1.6절의 **3·3·3 기준**으로 보면 이 예제는 **유형 A(경량 적용)**입니다. 그럼에도 7단계를 다 밟아보는 이유는, 각 단계가 무엇을 하는지 몸으로 알기 위해서입니다.

## 8.3 30분 배분

|---|---|---|
| 준비 | 3분 | 폴더 생성, Claude Code 실행 |
| 1 헌장 | 2분 | 규칙 4개 |

| 3 명확화 | 3분 | 질문 2~3개 답변 |
| 4 계획 ★ | 4분 | 기술 확인 후 승인 |
| 5 작업분해 ★ | 3분 | Task 6개 확인 후 승인 |
| 6 분석 | 2분 | 보고서 확인 |
| 7 구현 | 8분 | RED→GREEN→REFACTOR, 브라우저 확인 |

## 8.4 단계별 실행

### 준비

```
mkdir oneline-budget
cd oneline-budget
claude
```

첫 지시로 제1권 부록 1-D의 "0. 프로젝트 시작 전" 프롬프트를 그대로 붙여넣습니다.

### 1단계 — 헌장 (2분)

```
사용자:
이 프로젝트의 헌장을 만들어줘. 아주 작은 연습 프로젝트다.
규칙은 4개만:
 1) 테스트를 구현보다 먼저 쓴다
 2) 비밀 값은 저장소에 올리지 않는다
 3) 완료 보고 시 실행한 명령과 출력을 함께 제시한다
 4) 내가 요청하지 않은 기능은 추가하지 않는다
```

> **[실전] 4번 조항이 이 실습의 핵심입니다**
> 작은 예제일수록 AI가 "이왕이면" 하고 기능을 덧붙이기 쉽습니다. 카테고리 분류, 그래프, 예산 설정 같은 것이 요청 없이 생깁니다. 4번 조항을 넣어두고, 실제로 그것이 지켜지는지 관찰해 보십시오.

### 2단계 — 명세 (5분)

```
사용자:
명세를 만들어줘. 기술 이름은 쓰지 마.

만들 것: 한 줄 가계부
 - 오늘 쓴 돈을 한 줄로 적으면 목록에 쌓인다
 - 화면 위에 오늘 총액과 이번 달 총액이 보인다
 - 잘못 적은 항목은 지울 수 있다
로그인·카테고리·그래프·예산 설정은 만들지 않는다.
```

만들어지는 명세의 뼈대는 다음과 같습니다.

| 구분 | 내용 |
|---|---|
| US1 (P1) | 사용자는 지출 내용과 금액을 한 줄로 입력해 기록할 수 있다 |
| US2 (P1) | 사용자는 오늘 총액과 이번 달 총액을 확인할 수 있다 |
| US3 (P2) | 사용자는 잘못 입력한 항목을 삭제할 수 있다 |
| FR-001 | 시스템은 지출 내용(문자)과 금액(숫자)을 입력받아 저장해야 한다 |
| FR-002 | 시스템은 금액이 0보다 큰 정수인지 검증해야 한다 |
| FR-003 | 시스템은 기록을 최신순으로 목록에 표시해야 한다 |
| FR-004 | 시스템은 당일 합계와 당월 합계를 계산해 표시해야 한다 |
| FR-005 | 시스템은 개별 기록을 삭제할 수 있어야 한다 |
| SC-001 | 저장 후 1초 이내에 목록과 합계가 갱신된다 |
| SC-002 | 100건까지 기록해도 목록이 정상 표시된다 |

### 3단계 — 명확화 (3분)

전형적으로 다음과 같은 질문이 나옵니다.

```
Claude:
Q1. 금액에 소수점을 허용할까요? (권장: 정수만 — 원 단위)
Q2. 삭제는 즉시 처리할까요, 확인 후 처리할까요? (권장: 확인 후)
Q3. "이번 달"의 기준은 달력 월입니까, 최근 30일입니까? (권장: 달력 월)

사용자:
1) 정수만  2) 확인 후  3) 달력 월
```

> **[실전] Q3 같은 질문을 눈여겨보십시오**
> "이번 달"이라는 말을 우리는 아무 생각 없이 씁니다. 그런데 달력 월(8월 1일~31일)과 최근 30일은 완전히 다른 결과를 냅니다. **일상어의 모호함을 잡아내는 것**이 3단계의 진짜 역할입니다.

### 4단계 — 계획 ★ (4분)

```
Claude:
다음과 같이 제안합니다.
 - 데이터 저장: SQLite (파일 하나, 설치 불필요)
 - 서버: Python FastAPI
 - 화면: 단일 HTML 페이지 (별도 화면 프레임워크 없이)
   이유: 화면이 하나뿐이라 프레임워크 도입이 과합니다.
 - 데이터 표 1개: Expense(내용, 금액, 작성일시)
이대로 진행할까요?

사용자:
예. 그런데 나중에 화면이 늘어나면 어떻게 되나요?

Claude:
화면이 3개를 넘어가면 프레임워크 도입을 권합니다.
그 전환은 서버 쪽 변경 없이 화면만 교체하는 작업이라
난이도는 '중간'입니다. plan.md 에 이 전환 조건을 적어두겠습니다.

사용자:
그럼 승인합니다.
```

> **[실전] 이 대화가 승인 게이트의 축소판입니다**
> 사용자가 한 것은 **되돌리기 비용을 물은 것** 하나뿐입니다. 그 질문 하나로 "화면 3개"라는 전환 기준이 문서에 남았습니다.

### 5단계 — 작업분해 ★ (3분)

| Task | TDD | 내용 |
|---|---|---|
| T001 | — | 프로젝트 구조·의존성 |
| T002 | RED | 인수 시나리오 3건을 실패 테스트로 |
| T003 | GREEN | Expense 모델 |
| T004 | GREEN | 저장·목록·삭제 API |
| T005 | GREEN | 합계 계산 |
| T006 | GREEN | 화면(입력·목록·합계) |
| T007 | REFACTOR | 정리 |

> **[실전] Foundational이 없습니다**
> 기능이 사실상 하나뿐이라 공통 기반을 따로 뺄 필요가 없습니다. 이것이 유형 A의 특징입니다. 반대로 제2권의 독서활동 서비스는 로그인·DB연결·AI클라이언트라는 공통 기반이 있어 Foundational Phase가 필요했습니다.

### 6단계 — 분석 (2분)

[MEDIUM-2] FR-002(금액 검증) 실패 시 사용자 안내 문구가 미정의입니다.
[LOW-1] "이번 달" 기준(달력 월)이 spec.md 본문에는 반영되었으나
        data-model.md 설명에는 누락되어 있습니다.
CRITICAL 없음. 수정할까요?

사용자:
예, 수정해주세요.
```

```

## 8.5 이 실습에서 확인할 5가지

실습이 끝나면 다음을 스스로 점검해 보십시오. 이것이 이 부의 실질적 결론입니다.

| # | 확인할 것 | 왜 중요한가 |
|---|---|---|
| 1 | 명세에 기술 이름이 정말 하나도 없었는가 | 2단계의 규율 |
| 2 | 3단계 질문 중 하나라도 "미리 물어보길 잘했다" 싶은 것이 있었는가 | 명확화의 가치 |
| 3 | 승인할 때 되돌리기 비용을 물었는가 | 게이트의 실질화 |
| 4 | RED 단계에서 `failed`를 실제로 눈으로 봤는가 | 증거 기반 보고 |
| 5 | 요청하지 않은 기능이 생기지는 않았는가 | 헌장의 작동 여부 |

> **[주의] 5번에서 "생겼다"면 그것이 가장 큰 수확입니다**
> 헌장에 명시했는데도 기능이 추가되었다면, 여러분은 **AI가 규칙을 어기는 지점을 직접 관찰한 것**입니다. 그 경험이 제2권에서 훨씬 큰 프로젝트를 다룰 때 감시 지점을 알려줍니다. `progress.md` ⑥번 블록에 기록해 두십시오.

## 8.6 미니 실습에서 본 실습으로

| 항목 | 미니 실습(가계부) | 본 실습(독서활동) |
|---|---|---|
| User Story | 3개 | 6개 |
| 데이터 표 | 1개 | 8개 |
| Task | 7개 | 60여 개 |
| Foundational | 없음 | 있음 |
| 외부 서비스 | 없음 | AI API |
| 비용 | 없음 | 발생 |
| 소요 | 30분 | 2~4주 |
| 승인 게이트 | 2회 | 3회 이상 |

두 실습의 **절차는 완전히 같습니다.** 달라지는 것은 규모뿐입니다. 이것을 확인했다면 제2권으로 넘어갈 준비가 된 것입니다.

## 8.7 제1권을 마치며

> **바이브코딩은 "빨리 만드는 기술"이 아니라, "무엇을, 왜, 어떻게 검증하며 만드는지를 AI와 함께 끝까지 책임지고 따라가는 기술"입니다.**

제1권이 지도였다면, 제2권은 그 지도를 들고 실제로 걸어가는 기록입니다. 이제 **독서활동 서비스**라는 하나의 실제 프로젝트에 이 모든 것을 적용해 보겠습니다.

# 부록 1-D. 단계별 프롬프트 템플릿 모음

각 단계에서 그대로 복사해 쓸 수 있는 지시문입니다. 대괄호 `[ ]` 부분만 여러분의 내용으로 바꾸십시오.

## 0. 프로젝트 시작 전

```
나는 프로그래밍 비전공자다. 앞으로 이 프로젝트는 AI-VC 방식으로 진행한다.
지켜야 할 세 가지 원칙은 다음과 같다.

1) 승인 게이트 — 계획 단계와 작업분해 단계를 마치면 반드시 내 승인을 받고
   진행할 것. 내가 "예"라고 답하기 전에는 다음 단계로 넘어가지 말 것.
2) 증거 기반 보고 — 실제로 실행하지 않은 것을 "통과했다", "동작한다"고
   말하지 말 것. 완료를 보고할 때는 실행한 명령과 그 출력을 함께 제시할 것.
3) 기록 연속성 — 기능 하나가 끝날 때마다, 그리고 내가 "저장해줘"라고 하면
   docs/progress.md 를 6블록 형식으로 갱신할 것.

또한 기술 용어를 처음 쓸 때는 반드시 일상적인 비유로 한 문장 설명을 붙일 것.
```

## 1. 헌장 단계

```
이 프로젝트의 헌장(Constitution)을 만들어줘.
서비스 성격: [예: 학생이 독서 기록을 남기면 AI가 정리·토론해주는 웹서비스]
반드시 포함할 규칙:
 - 테스트를 구현보다 먼저 쓴다 (양보 불가)
 - API 키·비밀번호는 절대 저장소에 올리지 않는다
 - 기능 완료 시마다 결과를 문서로 남긴다
 - 커밋 메시지는 {type}: {제목} - {TDD단계} ({작업번호}) 형식을 따른다
 - [내가 추가하고 싶은 규칙]
조항은 12개를 넘지 말고, 각 조항은 지켰는지 안 지켰는지 판별 가능한
문장으로 써줘.
```

## 2. 명세 단계

```
@[내_기획서.md] 를 읽고 명세(spec.md)를 작성해줘.

지켜야 할 조건:
 - 프로그래밍 언어·데이터베이스·프레임워크 이름은 한 번도 등장시키지 말 것
 - User Story 는 우선순위 P1/P2/P3 를 매길 것
 - 기능 요구사항은 FR-001 부터 번호를 붙이고 "시스템은 ~해야 한다" 형식으로
 - 성공 기준은 SC-001 부터 번호를 붙이고 반드시 숫자를 포함할 것
 - "이번 범위에서 제외할 것"을 가정(Assumptions) 절에 명시할 것
 - 내가 기획서에 쓰지 않은 기능은 임의로 추가하지 말 것
```

## 3. 명확화 단계

```
지금까지 작성한 spec.md 를 다시 읽고,
구현 전에 반드시 확정해야 할 애매한 지점을 최대 5개 찾아 질문해줘.

질문할 때 각각에 대해 다음을 함께 알려줘.
 - 선택지 2~4개
 - 네가 추천하는 답과 그 이유
 - 이 결정을 나중에 바꾸려면 얼마나 어려운지 (되돌리기 비용)
```

## 4. 계획 단계

```
/speckit.plan 을 진행해줘.

조건:
 - 기술 선택마다 "왜 그것을 골랐는지"를 research.md 에 근거와 함께 기록할 것
 - 내 컴퓨터 환경에서 실제로 설치·실행 가능한 것만 고를 것
 - 헌장을 못 지키는 항목은 DEVIATION 으로 표시하고,
   사유·대체 수단·나중에 원래대로 돌리는 방법을 함께 적을 것
 - .env 파일은 빈 틀만 만들 것. API 키 값은 내가 직접 넣는다.
 - quickstart.md 는 내가 완성 후 직접 눌러볼 시나리오로 써줄 것

계획이 끝나면 요약해서 보여주고, 내 승인을 받은 뒤에 다음 단계로 넘어가.
설명할 때 전문 용어는 일상 비유를 붙여줘.
```

## 5. 작업분해 단계

```
/speckit.tasks 를 진행해줘.

조건:
 - 버티컬 슬라이스 방식으로 구성할 것.
   기능(User Story) 하나를 데이터→API→화면→확인까지 완결한 뒤 다음으로 넘어갈 것
 - 다만 각 슬라이스 안에서는 반드시 RED(테스트) → GREEN(구현) → REFACTOR 순서를
   지킬 것 (헌장 TDD 조항 준수)
 - 모든 슬라이스가 공통으로 필요한 것만 Foundational 로 묶고, 최소한으로 유지할 것
 - 각 Task 에 완료 판정 기준과 커밋 메시지를 미리 지정할 것
 - 병렬 진행 가능한 작업에는 [P] 표시

목록이 끝나면 Phase 별 개수를 요약해 보여주고 내 승인을 받아.
```

## 6. 분석 단계

```
/speckit.analyze 를 실행해줘.
발견한 문제를 CRITICAL / HIGH / MEDIUM / LOW 로 분류해 보고서만 먼저 보여줘.
내가 승인하기 전에는 어떤 파일도 수정하지 마.
```

## 7. 구현 단계 — 시작

```
/speckit.implement 를 시작해줘.

조건:
 - Task 를 하나씩 진행하고, 각 RED/GREEN/REFACTOR 마다 별도로 커밋할 것
 - 각 Task 완료 시 실행한 명령과 그 출력을 함께 보여줄 것
 - 슬라이스(User Story) 하나가 끝나면 멈추고, 내가 브라우저에서 확인할 수 있게
   실행 방법을 알려줄 것
 - 슬라이스 완료 시 docs/progress.md 와 docs/task-reports/ 를 갱신할 것
```

## 8. 검증 요청

```
방금 완료했다고 한 작업에 대해 다음을 보여줘.
 1) 실제로 실행한 명령과 그 출력 전문
 2) 전체 테스트를 다시 돌린 결과 (통과 개수)
 3) 이번에 변경된 파일 목록
 4) 이 기능이 동작하지 않는 경우(한계·예외)
```

## 9. 세션 종료

```
오늘은 여기까지. docs/progress.md 를 6블록 형식으로 갱신해줘.
특히 ④번(다음 세션이 할 일)은 파일 경로와 확인 방법까지 적어서,
그 문장만 복사해 붙여넣으면 바로 작업이 시작될 수 있게 써줘.
커밋 안 된 변경이 있으면 알려주고, 커밋 메시지를 제안해줘.
```

## 10. 세션 재개

```
docs/progress.md 를 읽고 지금까지의 진행 상황을 요약해줘.
그리고 "다음 세션이 할 일"에 적힌 첫 항목부터 이어서 진행할지 물어봐.
```

## 기능 요구사항(FR) 패턴

| 애매한 문장 | 명확한 문장 |

## 성공 기준(SC) 패턴

| 유형 | 틀 | 예 |
|---|---|---|
| 시간 | ~ 이내에 ~할 수 있다 | 저장 후 5분 이내에 완성된 분석을 확인할 수 있다 |
| 개수 | 항상 N개 이상 M개 이하 | 추천 도서는 3권 이상 5권 이하로 제시된다 |
| 용량 | N건까지 정상 동작한다 | 기록 100건까지 목록이 정상 표시된다 |
| 비율 | N% 이상 ~한다 | 입력 검증 오류 시 100% 안내 문구가 표시된다 |
| 범위 | N~M 사이 | 담론 초안은 1,500자 이상 2,500자 이하로 생성된다 |

> **[주의] 숫자가 안 나오는 기준은 "미정"으로 남기십시오**
> "중학생이 이해할 수 있는 수준" 같은 항목은 억지로 숫자를 붙이면 오히려 잘못된 기준이 됩니다. 정직하게 미정으로 두고 체크리스트에 점검 질문으로 남기는 것이 정답입니다.

## 인수 시나리오(Given-When-Then) 패턴

| 유형 | 틀 |
|---|---|
| 정상 | Given [정상 상태] / When [정상 조작] / Then [기대 결과] |
| 검증 실패 | Given [정상 상태] / When [잘못된 입력] / Then [거부 + 안내] |
| 권한 없음 | Given [타인 데이터] / When [접근 시도] / Then [차단] |
| 경계값 | Given [상한/하한 상태] / When [조작] / Then [정의된 동작] |
| 외부 실패 | Given [정상 상태] / When [외부 서비스 실패] / Then [실패 안내 + 복구 경로] |

> **[실전] 뒤의 세 유형을 빠뜨리기 쉽습니다**
> 대부분의 사람이 "정상" 시나리오만 씁니다. 그런데 실제 문제는 **권한 없음·경계값·외부 실패**에서 터집니다. User Story마다 이 세 가지 중 최소 하나는 쓰는 것을 규칙으로 삼으십시오.
