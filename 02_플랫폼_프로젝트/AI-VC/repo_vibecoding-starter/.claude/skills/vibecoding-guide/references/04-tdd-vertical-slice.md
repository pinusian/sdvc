# TDD + 버티컬 슬라이스 — 작업 조직과 구현 규율

## TDD 사이클: RED → GREEN → REFACTOR

| 단계 | 하는 일 | 커밋 예시 |
|---|---|---|
| RED | 기능이 해야 할 일을 검증하는 테스트를 먼저 쓰고, **실패하는 것을 확인**한다 | `test: task-upload - RED (T007)` |
| GREEN | 테스트를 통과시키는 **최소한의** 구현을 한다 | `feat: task-upload - GREEN backend (T009)` |
| REFACTOR | 동작을 바꾸지 않고 코드를 정리한 뒤, 테스트가 여전히 통과하는지 확인한다 | `refactor: task-upload - REFACTOR (T013)` |

**세 단계는 반드시 별도 커밋**으로 남긴다. 나중에 git log만 봐도 어떤 순서로 만들어졌는지 그대로 드러난다.

**왜 RED(실패)를 먼저 확인하나?** 테스트 자체가 잘못 쓰여서 '무엇을 넣어도 항상 통과'하는 무의미한 테스트가 되는 것을 막기 위해서다. 제대로 실패하는 걸 본 다음에 통과시켜야, 그 통과가 '진짜로 기능이 동작해서'라고 믿을 수 있다.

**초보자 조언**: 테스트 코드를 직접 짤 줄 몰라도 된다. AI에게 "먼저 실패하는 테스트를 써줘"라고 요청하는 것 자체는 누구나 할 수 있다. 중요한 것은 문법이 아니라 '테스트 없이 다음 단계로 넘어가지 않는다'는 습관, 그리고 AI에게 그 습관을 명시적으로 요구하는 것이다.

## 버티컬 슬라이스 vs 수평 레이어

| 방식 | 장점 | 단점 |
|---|---|---|
| 수평 레이어 (모델 전부 → API 전부 → 화면 전부) | 같은 종류 작업을 몰아서 하니 빠른 느낌 | 기능 하나가 끝까지 동작하는 걸 보려면 전체가 다 끝나야 함 — 중간 검증 불가 |
| **버티컬 슬라이스 (기능 하나를 모델~화면까지 완결)** | 기능이 끝날 때마다 동작을 눈으로 확인. 우선순위 낮은 기능을 미뤄도 앞 기능은 이미 완성 | 비슷한 코드를 기능마다 조금씩 반복할 수 있음 |

**초보자에게는 버티컬 슬라이스를 권장한다.** 첫 슬라이스만 끝나도 '동작하는 최소 제품(MVP)'을 브라우저에서 볼 수 있어 동기부여와 조기 검증이 모두 된다. 수평 레이어였다면 모든 화면이 완성될 때까지 아무것도 볼 수 없다.

## 슬라이스와 TDD의 결합 (충돌 해결 절충안)

"모델→API→화면→테스트" 순서는 TDD(테스트 먼저)와 정면 충돌한다. 절충안:
- 슬라이스(기능 단위 세로 자르기)는 유지하고,
- **슬라이스 안에서는 RED(테스트) → GREEN(모델→API→화면) → REFACTOR** 순서를 지킨다.

## tasks.md의 Phase 구조 (실제 완주 프로젝트의 형태)

```
Phase 1: Setup           — 폴더·의존성 확인
Phase 2: Foundational    — 모든 슬라이스가 공유하는 기반 (공통 모델, 외부 API 클라이언트, 라우터 뼈대)
                           ※ CRITICAL: 이게 끝나기 전엔 어떤 슬라이스도 시작 불가
Phase 3~N: 슬라이스들     — User Story 하나 = 슬라이스 하나 (우선순위 순서대로)
                           각각 RED → GREEN(백엔드) → GREEN(API) → GREEN(프론트) → REFACTOR
Phase 마지막: Polish      — 커버리지·린트 최종 점검, 작업보고서, 남겨둔 숙제 재검토
```

- 서로 다른 파일을 건드리고 의존성이 없는 작업은 **[P]**(병렬 가능)로 표시한다.
- 각 Task에는 ID(T001…)와 커밋 메시지 형식을 미리 정해둔다.

## 커밋 컨벤션

```
{type}: {제목} - {TDD단계} ({작업ID})
```
- type: `test`(RED) / `feat`(GREEN) / `refactor`(REFACTOR) / `docs` / `chore`
- 예: `test: task-trash - RED (T040)`, `feat: task-trash - GREEN frontend (T043)`

git log 한 줄만 봐도 '테스트인지 구현인지 정리인지, 몇 번 작업인지'가 바로 보인다.

## 테스트를 통과해도 의심하라 — SessionLocal 버그 교훈

실제 완주 프로젝트에서 겪은 가장 중요한 버그: 백그라운드 작업 코드가 DB 세션 팩토리(SessionLocal)를 **직접 import**해서, 테스트가 가짜(테스트용) DB를 주입해도 실제 운영 DB를 건드리고 있었다. 테스트는 통과하는 것처럼 보였지만 '진짜로 옳은 것'을 테스트하고 있지 않았다.

- 교훈 1: 의존성(DB 연결 등)은 직접 import하지 말고 주입(inject)받게 설계하라.
- 교훈 2: **테스트가 통과해도 '진짜로 옳은 것을 테스트했는지' 항상 의심하라.** 전체 테스트를 자주 다시 돌리고, 실제 실행으로도 교차 확인하라.
- 이 버그를 배포 후에 만났다면 사용자 데이터가 뒤섞인 뒤에야 발견됐을 것이다. 테스트 먼저 습관이 개발 단계에서 미리 잡아냈다.
