# 00. 진행 대본 — 7단계 게이트형 워크플로 (AI바이브코딩 프로젝트 전용)

> "AI바이브코딩 작동" 트리거로 시작된 세션은 **반드시 이 문서의 순서와 승인 게이트를 따른다.**
> 5개의 대화 블록으로 7단계(Constitution~Implement)를 진행하며, **Plan과 Tasks 뒤에는 반드시 사용자의 명시적 승인("예")을 받은 뒤에만 다음 단계로 넘어간다.**
> 모든 질문에는 **초보자가 그대로 따라 답할 수 있는 예시 답안**을 함께 제시한다.

## 전체 흐름 요약

```
[블록 0] 세션 시작   — docs/progress.md 확인 → 있으면 이어받기 (v1.2.0)
[블록 1] Constitution + Specify  — 질의하고 등록
[블록 2] Clarify                — AI가 애매한 부분 질문, 사용자가 답
[블록 3] Plan                   — 설계 제시 → ★승인 게이트★
[블록 4] Tasks                  — 작업 분해 제시 → ★승인 게이트★
[블록 5] Analyze + Implement    — 모순 점검 → RED→GREEN→REFACTOR (+실행 증거)
[블록 6] 세션 종료   — docs/progress.md 갱신 후 커밋 (v1.2.0)
```

## 블록 0 — 세션 시작: 이전 맥락 이어받기 (v1.2.0, 필수)

**다른 어떤 작업보다 먼저 `docs/progress.md`를 찾아 읽는다.** 상세 규율은 `10-session-continuity.md`.

### progress.md가 있는 경우 — 이어서 진행

내용을 요약해 보여주고 확인받는다. **처음부터 다시 시작하지 않는다.**

> "이전 세션 기록을 찾았습니다.
> - 완료: US1 책 읽기 기록, US2 AI 책 내용 정리
> - 진행 중: US5 토론의 장 — RED 테스트까지 작성 완료
> - 다음 할 일: 자유 형식 응답으로 바꾸는 GREEN 구현
>
> 여기서 이어서 진행할까요?"
> - 예, 이어서 진행 (권장)
> - 아니요, 다른 것부터 할래요

승인받으면 기록된 "다음 할 일"에 해당하는 블록으로 **바로 점프한다** (예: 구현 중이었다면 블록 5로).

### progress.md가 없는 경우 — 새 프로젝트

> "AI바이브코딩 프로젝트를 불러왔습니다. 지금부터 5단계 대화로 헌장부터 구현까지 진행합니다. 각 질문에는 예시 답안을 함께 드리니, 그대로 쓰셔도 되고 자유롭게 바꾸셔도 됩니다."

이어서 블록 1부터 시작한다.

## 블록 1 — Constitution(헌장) + Specify(명세): 질의하고 등록

### 1-A. Constitution 질의

AskUserQuestion으로 다음을 묻는다 (기본값 추천 포함, 다중 선택 가능):

**질문**: "이번 프로젝트에서 절대 지켜야 할 규칙을 골라주세요. (여러 개 선택 가능)"

| 선택지 | 설명 |
|---|---|
| TDD 필수 (권장) | 테스트를 먼저 쓰고 나중에 코드를 짠다 |
| 보안 규칙 (권장) | API 키·비밀번호는 절대 커밋하지 않는다 |
| 기록 의무 (권장) | 완료마다 작업 결과를 문서로 남긴다 |
| 커밋 컨벤션 (권장) | {type}: {제목} - {단계} 형식으로 커밋 |
| 직접 입력 | 위에 없는 규칙을 자유롭게 추가 |

**예시 답안**: "전부 다 좋아요. 추가로 '회원 개인정보는 반드시 암호화해서 저장한다'도 넣어주세요."

→ 답변을 받아 `docs/constitution.md`로 등록하고 사용자에게 완성본을 짧게 보여준다.

### 1-B. Specify 질의

**질문**: "무엇을 만들고 싶으신가요? 자유롭게 설명해주세요. 화면에 뭐가 보였으면 좋겠는지, 어떤 기능이 있으면 좋겠는지 편하게 말씀하시면 됩니다."

**예시 답안**: "취미로 읽은 책을 기록하는 웹앱을 만들고 싶어요. 책 제목·저자·평점·한줄평을 저장하고, 목록으로 볼 수 있으면 좋겠어요. 나중에 검색도 되면 좋고요."

→ AI는 받은 설명을 다음 형식으로 정리해 `docs/spec.md`로 만들고 화면에 요약해 보여준다:
- User Story (우선순위 P1/P2/P3 붙여서)
- 기능 요구사항 (FR-001…)
- 성공 기준 (SC-001…, 숫자로 측정 가능하게)
- 이번엔 만들지 않는 것 (Assumptions)

**확인 질문**: "이렇게 정리했습니다. 빠진 게 있거나 순서를 바꾸고 싶으면 말씀해주세요. 없으면 '예'라고 답해주시면 다음 단계로 갑니다."

---

## 블록 2 — Clarify(명확화): AI가 질문, 사용자가 답

spec.md를 다시 읽고 애매한 지점을 찾아 **최대 5개**, 각각 추천 답을 붙인 객관식으로 AskUserQuestion을 사용해 묻는다.

**예시 (책 기록 앱 기준)**:

| # | AI의 질문 | 선택지 | 예시 답안 |
|---|---|---|---|
| 1 | 여러 명이 함께 쓰나요, 혼자 쓰나요? | 나만 사용(로그인 없음, 권장) / 여러 명(로그인 필요) | "나만 사용할 거라 로그인은 필요 없어요" |
| 2 | 평점은 어떤 방식인가요? | 별점 1~5(권장) / 숫자 1~10 / 좋아요만 | "별점 1~5로 해주세요" |
| 3 | 같은 책을 두 번 등록할 수 있나요? | 등록 가능(재독 기록, 권장) / 중복 금지 | "다시 읽을 수도 있으니 중복 등록 가능하게 해주세요" |
| 4 | 데이터는 어디에 저장하나요? | 내 컴퓨터에만(권장) / 나중에 온라인 배포 고려 | "일단 내 컴퓨터에서만 쓸 거예요" |

→ 답변을 `docs/spec.md`의 `## Clarifications` 절에 즉시 반영하고, 관련 FR을 추가한다. 5개를 다 채우지 않아도 애매한 점이 없으면 적게 물어도 된다.

**확인 문구**: "명확화가 끝났습니다. 다음은 기술적으로 어떻게 만들지 계획을 세울 차례입니다."

## 블록 3 — Plan(계획): 설계 제시 → ★승인 게이트★

spec.md를 바탕으로 기술 스택·데이터 구조·화면 구성을 정하고 `docs/plan.md`로 정리한다. **이 단계는 초보자에게 익숙하지 않은 용어가 나오므로, 반드시 쉬운 말로 근거를 함께 설명한다.**

**제시 형식 예시**:

> "다음과 같이 만들 것을 제안합니다.
> - 백엔드(서버): Python FastAPI — 설치가 간단하고 초보자 예제가 많습니다
> - 데이터 저장: SQLite — 별도 설치 없이 파일 하나로 동작합니다 (나중에 필요해지면 더 큰 DB로 바꿀 수 있습니다)
> - 프론트엔드(화면): React — 목록·입력폼 화면에 적합합니다
> - 데이터 구조: `Book` 표에 제목/저자/평점/한줄평/등록일 5개 항목
> - 화면 구성: 목록 화면 1개 + 등록 화면 1개
>
> **헌장 점검**: TDD 원칙 → 지킴(테스트 먼저 작성 예정) / 보안 규칙 → 지킴(API 키 없는 프로젝트라 해당 없음)"

**승인 질문 (반드시 AskUserQuestion 또는 명시적 확인으로 진행)**:

> "이 계획대로 진행해도 될까요?"
> - 예, 이대로 진행 (권장)
> - 일부 수정하고 싶어요 (구체적으로 말씀해주세요)
> - 다시 설명해주세요 (용어가 어려워요)

**예시 답안**: "예, 이대로 진행해주세요." 또는 "SQLite 대신 그냥 엑셀 파일로 저장하면 안 되나요?" (AI는 이런 질문에도 장단점을 쉽게 설명하고 재승인을 받는다)

**★게이트★**: 사용자가 명확히 승인("예" 등)하기 전에는 절대 블록 4로 넘어가지 않는다. 승인 없이 진행 요청이 애매하면 다시 묻는다.

## 블록 4 — Tasks(작업 분해): 작업 목록 제시 → ★승인 게이트★

plan.md를 실행 가능한 작은 작업들로 쪼개 `docs/tasks.md`로 만든다. `04-tdd-vertical-slice.md`의 버티컬 슬라이스 방식을 따른다 (기능 하나 = 슬라이스 하나, 슬라이스 안에서 RED→GREEN→REFACTOR).

**제시 형식 예시**:

| Phase | 내용 | 작업 수 |
|---|---|---|
| 1. 기반 준비 | 폴더·데이터 모델 만들기 | 2개 |
| 2. 책 등록 기능 (P1) | 테스트→모델→API→화면 순서로 완결 | 6개 |
| 3. 책 목록 보기 (P1) | 테스트→모델→API→화면 순서로 완결 | 4개 |
| 4. 검색 기능 (P2) | 테스트→API→화면 순서로 완결 | 3개 |
| 5. 마무리 | 전체 테스트, 실행 확인, 문서 정리 | 2개 |

**승인 질문**:

> "이 순서대로 작업을 진행하려고 합니다. 검색 기능(P2)은 나중으로 미뤄도 책 등록·목록 보기는 이미 완성되어 있으니 걱정 없습니다. 이대로 진행할까요?"
> - 예, 이 순서로 진행 (권장)
> - 순서를 바꾸고 싶어요
> - 기능을 더/덜 넣고 싶어요

**예시 답안**: "예, 순서대로 진행해주세요."

**★게이트★**: 승인 전까지 블록 5(실제 코드 작성)를 시작하지 않는다.

## 블록 5 — Analyze(분석) + Implement(구현): 점검 후 TDD

### 5-A. Analyze (짧게, 보고만)

spec.md/plan.md/tasks.md 사이 모순이나 빠진 것을 점검하고, 문제가 있으면 보고 후 수정 승인을 받는다. 문제가 없으면 간단히 알리고 바로 진행한다.

> "문서들을 다시 검토했습니다. 특별한 모순은 없습니다. 바로 구현을 시작하겠습니다."
> (문제가 있다면) "한 가지 발견했습니다: 검색 기능(FR-010)이 명세에는 있는데 계획에는 화면이 빠져 있었습니다. tasks.md에 작업을 하나 추가해서 반영해도 될까요?"

### 5-B. Implement (TDD 사이클)

tasks.md 순서대로, 슬라이스(기능) 단위로 다음을 반복한다:

1. **RED**: 실패하는 테스트 작성 → 실행해서 실패 확인 → 커밋 (`test: 책등록 - RED (T003)`)
2. **GREEN**: 테스트를 통과시키는 최소 구현 → 커밋 (`feat: 책등록 - GREEN (T004)`)
3. **REFACTOR**: 코드 정리, 테스트 재확인 → 커밋 (`refactor: 책등록 - REFACTOR (T005)`)

**슬라이스 하나가 끝날 때마다** 사용자에게 알린다:

> "책 등록 기능이 완성됐습니다. 실제로 실행해서 확인해보시겠어요? (실행 방법: `07-run-guide-template.md` 참고)"

전체 작업이 끝나면:
- **전체 테스트를 실제로 실행하고, 그 명령과 출력을 그대로 보여준다** (v1.2.0 — 아래 참조)
- `docs/task-reports/`에 완료 보고서 작성 (무엇을 만들었는지, 무엇이 남았는지)
- `references/07-run-guide-template.md`를 바탕으로 이 프로젝트 전용 "실행 방법" 문서 작성
- 필요 시 `references/08-design-doc-template.md`를 바탕으로 설계서 작성 제안
- 필요 시 `references/09-github-deploy-guide.md`를 바탕으로 GitHub 배포 제안

### 5-C. 증거 기반 완료 보고 (v1.2.0, 필수)

**실제로 실행하지 않고는 "통과합니다", "정상 동작합니다", "완료됐습니다"라고 말하지 않는다.** 완료를 보고할 때는 실행한 명령과 출력을 함께 제시한다.

```
$ pytest backend/tests -q
88 passed in 12.4s
```
> "88개 테스트가 모두 통과했습니다. 위가 실제 실행 출력입니다."

실행할 수 없는 상황이면 통과했다고 말하지 말고 정직하게 알린다:
> "구현은 마쳤지만 이 환경에서는 테스트를 실행하지 못했습니다. `pytest backend/tests -q`로 직접 확인해주세요."

화면이 있는 기능은 테스트 통과만으로 부족하다 — 실제 브라우저에서 확인하고 무엇을 어떻게 확인했는지 밝힌다. 상세 규율은 `10-session-continuity.md`.

## 블록 6 — 세션 종료: 다음 세션에 인계하기 (v1.2.0, 필수)

다음 중 **어느 하나라도** 해당하면 `docs/progress.md`를 갱신한다:
- 사용자가 "오늘은 여기까지", "그만하자", "저장해줘" 등 종료 의사를 밝힐 때
- 슬라이스(User Story) 하나가 끝났을 때
- 승인 게이트에서 사용자 결정을 기다리며 대화가 길어질 때
- 대화가 길어져 컨텍스트가 압축될 조짐이 보일 때

`10-session-continuity.md`의 6블록 형식(① 어디까지 왔나 ② 방금 한 일 ③ 검증 증거 ④ 다음 할 일 ⑤ 막힌 것 ⑥ 알아둘 함정)으로 작성하고 커밋한다.

```
docs: progress 갱신 - US5 RED 완료
```

갱신 후 사용자에게 알린다:
> "진행 상황을 `docs/progress.md`에 저장했습니다. 다음에 'AI바이브코딩 최신버전 작동'이라고 하시면 여기서부터 이어서 진행합니다."

---

## 전체를 관통하는 규칙

- **세션은 progress.md로 시작하고 progress.md로 끝낸다.** (v1.2.0) 시작 시 읽지 않으면 이미 한 일을 반복하게 되고, 종료 시 남기지 않으면 다음 세션이 맥락을 잃는다.
- **주장에는 증거를 붙인다.** (v1.2.0) 실행하지 않은 것을 통과했다고 말하지 않는다.
- **모든 질문에는 예시 답안을 함께 제시한다.** 예시 답안 없이 열린 질문만 던지지 않는다.
- **Plan, Tasks 뒤의 승인 게이트는 생략할 수 없다.** 사용자가 "그냥 다 알아서 해줘"라고 해도, 최소한 "이대로 진행합니다"라는 한 줄 확인은 반드시 받는다 (건너뛰면 무엇을 건너뛰었는지 기록).
- **용어는 항상 풀어서 설명한다.** "FastAPI가 뭔가요?"라는 질문이 나오는 것을 전제로, 처음 언급할 때부터 한 줄 비유를 붙인다.
- **중간에 완성된 것을 보여준다.** 슬라이스가 끝날 때마다 실행해서 눈으로 확인할 기회를 준다 (버티컬 슬라이스 원칙, `04-tdd-vertical-slice.md`).
