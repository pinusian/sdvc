# 10. 세션 연속성과 증거 기반 완료 보고 (v1.2.0 신규)

> 이 문서는 두 가지 규율을 정의한다. 둘 다 **선택이 아니라 기본 동작**이다.
> ① **세션 인계**: 대화가 끊겨도 다음 세션이 맥락을 잃지 않도록 `progress.md`를 남긴다.
> ② **증거 기반 완료 보고**: "완료했다"는 주장에 반드시 실제 실행한 명령과 그 출력을 근거로 붙인다.

## 왜 필요한가

AI는 세션이 바뀌면 이전 대화를 전혀 기억하지 못한다. `/clear`를 하거나 새 대화를 시작하면 진행 맥락이 사라지고, 사람이 "우리가 어디까지 했는지"를 매번 다시 설명해야 한다. 기능이 여러 개이고 작업이 여러 날에 걸치는 프로젝트에서는 이것이 가장 큰 낭비이자 오류의 원인이 된다.

또한 AI는 "테스트가 통과합니다", "구현이 완료됐습니다"라고 **실제로 실행해보지 않고도** 말할 수 있다. 이것이 바이브코딩의 3번째 함정("동작하는지 확인할 방법이 없다")이 가장 교묘하게 되살아나는 지점이다. 주장에 증거를 붙이는 규율이 이를 막는다.

---

## ① 세션 인계 — progress.md

### 위치

프로젝트 루트의 `docs/progress.md` (없으면 새로 만든다). 이 파일은 **항상 최신 상태 하나만** 유지한다 — 이력은 git 커밋이 담당하므로 파일 자체는 계속 덮어쓴다.

### 세션 시작 시 (필수 — 다른 어떤 작업보다 먼저)

1. `docs/progress.md`가 있으면 **읽는다.**
2. 있으면 사용자에게 요약해 확인받는다:

> "이전 세션 기록을 찾았습니다. 마지막 작업은 '토론 기능 RED 테스트 작성'까지였고, 다음 할 일은 'GREEN 구현'으로 되어 있습니다. 여기서 이어서 진행할까요?"
> - 예, 이어서 진행 (권장)
> - 아니요, 새로 시작할래요

3. 없으면 새 프로젝트로 보고 `00-guided-session-script.md`의 블록 1부터 시작한다.

### 세션 종료 시 (필수)

다음 중 **어느 하나라도** 해당하면 `docs/progress.md`를 갱신한다:
- 사용자가 "오늘은 여기까지", "그만하자", "저장해줘" 등 종료 의사를 밝힐 때
- 슬라이스(User Story) 하나가 끝났을 때
- 승인 게이트에서 사용자의 결정을 기다리며 대화가 길어질 때
- 대화가 길어져 컨텍스트가 압축될 조짐이 보일 때

### progress.md 형식 (6블록)

```markdown
# 진행 상황

> 마지막 업데이트: 2026-08-29 · 프로젝트: 독서활동 · 현재 단계: Implement (US5)

## 1. 지금 어디까지 왔나
- 완료: US1 책 읽기 기록, US2 AI 책 내용 정리, US3 유사 도서 추천
- 진행 중: US5 토론의 장 — RED 테스트까지 작성 완료, GREEN 미착수
- 미착수: US6 담론 출판

## 2. 방금 세션에서 한 일
- 토론 응답이 강제 JSON 형식 때문에 깨지는 버그를 발견
- 실패 테스트 작성 후 커밋 (5d88f89 "test: ... - RED")

## 3. 검증 증거 (실제 실행한 명령과 결과)
$ pytest backend/tests -q
88 passed in 12.4s

## 4. 다음 세션이 이어서 할 일
- [ ] discussion 응답을 자유 형식 텍스트로 바꾸는 GREEN 구현
- [ ] 구현 후 pytest 재실행하여 88개 전체 통과 확인
- [ ] 통과하면 "fix: ... (GREEN)" 형식으로 커밋

## 5. 막힌 것 / 사용자 결정 대기
- 없음 (또는: "담론 출판 시 토론 내용을 몇 개까지 포함할지 미결정")

## 6. 알아둘 함정
- .env의 API 키를 바꾼 뒤에는 반드시 백엔드 서버를 재시작해야 반영된다
- 백엔드는 8000 포트, 프론트는 5174 포트 (5173은 구버전)
```

### 작성 원칙

- **다음 세션의 나(또는 다른 사람)가 읽는다고 생각하고 쓴다.** "그거 고쳤음" 같은 표현 금지 — 무엇을, 어느 파일에서, 왜 고쳤는지 적는다.
- **4번(다음 할 일)은 체크박스로, 즉시 실행 가능한 문장으로 쓴다.** "토론 기능 마무리" (X) → "discussion 응답을 자유 형식으로 바꾸는 GREEN 구현" (O)
- **3번(검증 증거)에는 실제 출력을 붙인다.** 아래 ②의 규율과 동일하다.
- 갱신 후에는 커밋한다: `docs: progress 갱신 - US5 RED 완료`

## ② 증거 기반 완료 보고

### 금지 사항

다음은 **실제로 실행하지 않고는 절대 말하지 않는다**:
- "테스트가 모두 통과합니다"
- "정상 동작합니다" / "잘 됩니다"
- "구현이 완료되었습니다"
- "N개 테스트 통과" 같은 구체적 숫자

### 필수 형식

완료를 보고할 때는 **실행한 명령과 그 출력**을 함께 제시한다.

```
$ pytest backend/tests -q
88 passed in 12.4s
```

> "88개 테스트가 모두 통과했습니다. 위가 실제 실행 출력입니다."

### 실행하지 못했을 때

실행할 수 없는 상황(환경 미구성, 사용자가 서버를 꺼둠 등)이라면 **통과했다고 말하지 말고, 실행하지 못했다고 정직하게 말한다.**

> "구현은 마쳤지만 이 환경에서는 테스트를 실행하지 못했습니다. 다음 명령으로 직접 확인해주세요: `pytest backend/tests -q`"

### 화면이 있는 기능은 실행 확인까지

테스트 통과만으로는 부족하다. 화면이 있는 기능은 실제로 브라우저에서 동작하는 것까지 확인하고, 무엇을 어떻게 확인했는지 밝힌다.

> "브라우저에서 실제로 확인했습니다: 회원가입 → 로그인 → 독서기록 생성 → AI 정리 생성까지 진행했고, 마지막 요청이 201 Created로 응답하며 화면에 결과가 표시되는 것을 확인했습니다."

### 사용자 보고서·문서에도 동일 적용

작업보고서나 설계서에 "N개 테스트 통과", "커버리지 N%" 같은 수치를 쓸 때도 그 수치는 **실제 실행 출력에서 가져온 것이어야 한다.** 기억이나 추정으로 숫자를 쓰지 않는다.

---

## 두 규율의 연결

`progress.md`의 3번 블록(검증 증거)이 곧 ②의 산출물이다. 세션을 마칠 때 "무엇을 실행해서 무엇을 확인했는지"를 그대로 남기면, 다음 세션은 **어디까지가 검증된 사실이고 어디부터가 미검증인지**를 정확히 알고 시작할 수 있다. 이것이 맥락 유실과 품질 비결정성을 동시에 막는 가장 저렴한 방법이다.
