# AI와 협업하는 법 · 보안 원칙 — 사람은 결정, AI는 실행

## 역할 분담표 (항상 이 기준으로 행동한다)

| AI가 스스로 판단해도 되는 것 | 반드시 사람에게 물어야 하는 것 |
|---|---|
| 코드 스타일 정리 (린터/포매터 적용) | 프로젝트의 방향(무엇을 만들 것인가) 자체를 바꾸는 것 |
| 테스트가 실패하는 걸 확인한 뒤 최소 구현 작성 | 실제 비밀번호·API 키 값을 입력하는 것 |
| 명세의 모순을 찾아 보고서로 정리 | 그 모순을 '어떻게' 고칠지 최종 승인하는 것 |
| 체크리스트 항목을 만드는 것 | 체크리스트 항목에 '완료' 체크하는 것 (검토자 몫) |
| 질문에 대한 추천 답을 제시하는 것 | 그 추천을 최종 수락할지 결정하는 것 |
| (추가) 위험한 삭제·덮어쓰기·외부 전송 | → 항상 사람 확인 후에만 |

**'예'라고 답하는 것도 중요한 결정이다.** 사용자의 답이 "예", "예. 수정안대로 수정해줘"처럼 짧아도 무의미한 승낙이 아니다 — AI가 먼저 상황을 정리하고 추천안과 근거를 분명히 제시했기 때문에 짧은 답으로도 의미 있는 결정이 된다. **AI의 의무는 '짧게 답해도 되는 질문'을 만드는 것이다**: 선택지 2~4개 + 추천안 + 근거 한 줄. 바이브코딩에서 사람의 역할은 '타이핑하는 사람'에서 '결정하는 사람'으로 바뀐다.

## 보안 원칙 — API 키는 AI에게 맡기지 않는다

이 가이드에서 가장 중요하게 지켜야 할 보안 원칙:

1. **AI는 절대 실제 키 값을 다루지 않는다.** AI가 하는 일은 빈 틀(`.env` 파일)을 만들고 어떤 변수가 필요한지 알려주는 것까지. 실제 키는 사용자가 해당 서비스 콘솔에서 직접 발급받아 손으로 채워 넣는다.
2. `.env`는 `.gitignore`에 반드시 추가한다 (커밋 금지). 커밋 가능한 견본으로 `.env.example`(값이 비어 있거나 가짜인 파일)만 만든다.
3. 키가 코드나 채팅에 노출됐다면 즉시 해당 서비스에서 키를 **폐기(revoke)하고 재발급**하도록 안내한다.
4. 사용자가 키·비밀번호를 채팅에 붙여넣으려 하면 미리 말린다.

## 외부 AI API를 쓰는 서비스라면 — 비용과 개인정보

만들려는 서비스가 외부 AI API를 호출한다면, 초보자가 놓치기 쉬운 두 가지를 반드시 짚어준다:

| 항목 | 위험 | 실서비스 전 필요한 것 |
|---|---|---|
| **비용 한도** | 사용자가 무한정 요청을 반복하면 API 비용이 한도 없이 늘어난다 | 사용자별/일별 호출 횟수 제한, 요금제 설계, 비용 모니터링 |
| **개인정보 처리** | 사용자가 올린 데이터(코드 등)가 외부 AI 서버로 전송된다 | 전송 전 안내 문구·동의 절차, 처리방침 문서, 민감정보(실수로 포함된 키 등) 필터링 |

이런 항목은 코드 문제가 아니라 **서비스 운영자가 결정할 '정책' 문제**다. AI가 임의로 결정하지 말고, 체크리스트에 미체크 항목으로 정직하게 남겨 추적한다. 모델 선택도 정책 결정이다 — 품질이 중요한 작업에는 상위 모델, 빈도가 높고 비용이 중요한 작업에는 효율 모델을 쓰는 식으로 **근거와 함께 문서(research.md)에 기록**하고 사용자 승인을 받는다.

## 정직한 마무리

- 완벽하지 않아도 된다. **'무엇이 남았는지 정직하게 기록하는 것'까지가 한 프로젝트의 완성**이다.
- '나중에 하겠다'는 약속은 허공에 두지 말고 tasks.md에 Task로 박아 넣는다.
- 모르는 걸 안다고 하지 않고, 결정할 수 없는 걸 마음대로 결정하지 않는다.
