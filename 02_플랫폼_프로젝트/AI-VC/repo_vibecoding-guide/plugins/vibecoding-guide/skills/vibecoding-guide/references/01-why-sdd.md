# 왜 절차가 필요한가 — 바이브코딩과 명세 기반 개발(SDD)

> 이 문서는 사용자가 "왜 이렇게까지 해야 하나요?"라고 물을 때 설명 자료로 활용한다.
> 출처: 『바이브코딩 실전 교육교재 — SpecKit로 기획부터 구현까지』 1부·7부

## 바이브코딩이란

개발자가 코드를 한 줄씩 타이핑하는 대신, AI에게 '무엇을 만들고 싶은지'를 자연어로 설명하면 AI가 실제 코드를 작성해주는 개발 방식. 프로그래밍을 배우지 않은 사람도 웹사이트·앱·서비스를 만들 수 있게 되었지만, 함정이 있다.

## 바이브코딩의 3가지 함정

1. **무엇을 만들지 애매하게 요청하면 → AI도 애매하게 만든다.** 요구사항이 명확하지 않으면 결과물도 예측 불가능하다.
2. **완성된 결과물이 제대로 동작하는지 확인할 방법이 없다.** 테스트 없이 '되는 것 같으니 끝'으로 넘어가기 쉽다.
3. **왜 이렇게 만들어졌는지 기록이 남지 않는다.** 몇 주 뒤에 다시 보면 '이게 왜 이렇게 되어 있지?' 상태가 된다.

**요리 비유**: 지금의 바이브코딩은 셰프(AI)가 요리를 다 만들어줘서 맛있게 먹었지만, 나중에 간이 안 맞으면 어디를 고쳐야 할지 모르는 상황과 같다. 절차를 지키면 셰프가 '이 재료는 이래서 넣었고, 이 순서로 해야 이 맛이 나요'라고 설명해주는 것과 같아서, 나중에 내 입맛대로 수정할 수 있다.

## 명세 기반 개발(Spec-Driven Development)의 진짜 가치

'더 좋은 코드'가 아니라 **'나중에 무엇을 왜 그렇게 만들었는지 언제든 되짚어볼 수 있게 해주는 것'**이다. 절차를 지키면 4개의 문서 계층이 남는다:

| 문서 | 이것만 보면 알 수 있는 것 |
|---|---|
| spec.md | 이 기능이 '무엇을' 하기로 되어 있는지 (코드 한 줄 안 보고) |
| plan.md + research.md | '왜' 이 기술을 골랐는지, 기각된 대안은 무엇인지 |
| tasks.md + git 커밋 이력 | '어떤 순서로' 만들어졌는지 |
| docs/task-reports/ | 완료된 기능이 어떤 상태였는지 요약 |

AI는 대화가 길어지거나 새 세션이 시작되면 맥락을 잃는다. 이 문서들이 있으면 AI도 사람도 언제든 같은 기준으로 작업을 이어갈 수 있다.

## 왜 이렇게까지 해야 하나 — 핵심 4가지

1. 규모가 커질수록 '한 번에 다 만들어줘'는 실패한다. (교재의 예제 프로젝트도 6개 기능, 52개 작업으로 쪼개서 진행했다)
2. AI도 사람처럼 맥락을 잃어버린다. 명세서·계획서·작업 목록이라는 기록이 있어야 며칠이 지나도 같은 기준으로 판단한다.
3. 테스트가 없으면 '고쳤다고 착각'하기 쉽다. (교재 프로젝트에서는 테스트 덕분에 배경 작업이 운영 DB를 건드리는 심각한 버그를 구현 중간에 발견했다)
4. 나중에 사람이 코드를 이어받거나 검토할 때, 명세서와 커밋 이력만 봐도 이유를 알 수 있다.

**한 줄 요약**: 바이브코딩이 '즉흥 연주'라면, 절차를 갖춘 바이브코딩은 '악보를 보며 하는 즉흥 연주'다. AI의 창의성과 속도는 그대로 쓰면서, '무엇을 만들지'와 '어떻게 검증할지'를 사람이 계속 통제한다.

바이브코딩은 '빨리 만드는 기술'이 아니라 **'무엇을, 왜, 어떻게 검증하며 만드는지 AI와 함께 끝까지 책임지고 따라가는 기술'**이다.
